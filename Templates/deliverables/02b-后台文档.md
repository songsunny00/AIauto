# 后台文档模板

## 0. 使用说明

- **上游输入**：
  - `docs/02-详细设计文档.md`（架构、模块、功能流程、接口清单概览、路由与接口映射表）
  - 必要时回看 `docs/01-需求文档.md`、`docs/01b-数据流转设计.md`、`docs/01c-原型文档.md`
  - 必读参考示例：`framework/examples/OmicsDB-V1.0.0/04-详细设计文档.md` 第 6 / 7 / 8 / 9 / 10 / 11 章
- **下游消费者**：
  - 后端开发工程师（接口实现、表结构、配置、部署）
  - `docs/02c-前端文档.md`（可选，若已生成，前端按本文档的接口字段名、错误码、响应结构对接）
  - `docs/03-测试用例文档.md`（按本文档的字段、错误码、状态码写接口用例与异常用例）
- **产出原则**：
  1. 02b 是**后端落地细节的唯一事实源**。02 详细设计只给「接口清单概览」（方法/路径/权限/简述），完整的接口定义、数据库、安全、缓存、日志、错误码、部署细节全部在本文档展开。
  2. 任何接口或表结构变更**先改本文档**，再同步 02 详细设计第 6 章接口清单概览表和第 7 章引用关系；接口的请求参数、响应字段、错误码不允许在 02 里出现第二份。
  3. 字段命名遵循框架命名规范：API 前缀 `/api/v1`，REST 路径使用 kebab-case 或资源复数形式（如 `/api/v1/oa-orders`），JSON 字段使用 camelCase（如 `oaNo`/`taskNo`/`applyTime`），数据库字段使用 snake_case（如 `oa_no`/`task_no`/`apply_time`），角色编码使用大写英文（`ADMIN`/`DELIVERY`/`SALES`/`CUSTOMER`），权限编码使用 `module:action` 小写格式（如 `insights:view`、`menu:tasks`）。
  4. 本文档的示例片段仅用于说明写法，**禁止将示例的业务事实（如 OmicsDB 的 OA 单、`t_task` 表、`OA2024001` 等）原样复制到新项目正文**。
  5. 任何接口在本文档必须包含完整的 8 个部分：HTTP 方法 / 路径 / 权限 / 请求参数表 / 响应字段表 / 请求示例 JSON / 响应示例 JSON / 错误码列表，缺一不可。
- **命名约定**：输出到 `docs/02b-后台文档.md`。

## 1. 接口规范说明

> **填写指引**：本章节定义全局接口规范，是后续所有接口必须遵守的共同前提。必须明确：基础 URL、版本前缀、Content-Type、认证方式、时间格式、统一响应结构、分页响应结构、分页请求参数。任何接口都不得偏离本节定义的全局格式（如响应外壳字段、分页字段名）。
>
> **字段清单**：
>
> | 字段名 | 类型 | 必填 | 说明 | 示例值 |
> |---|---|---|---|---|
> | 基础 URL | String | 是 | host + 端口 | `http://{host}:8080` |
> | 版本前缀 | String | 是 | 路径前缀 | `/api/v1/` |
> | Content-Type | String | 是 | 默认请求/响应类型 | `application/json; charset=UTF-8` |
> | 认证方式 | String | 是 | Header 格式 | `Authorization: Bearer {accessToken}` |
> | 时间格式 | String | 是 | 全局日期时间格式 | `yyyy-MM-dd HH:mm:ss` |
> | 响应外壳 | Object | 是 | code/message/traceId/data | 见 1.3 |
> | 分页外壳 | Object | 是 | total/list/page/pageSize/totalPages | 见 1.4 |
> | 分页参数 | Object | 是 | page/pageSize 默认值 | page=1, pageSize=10 |
>
> **示例片段**（摘自 `framework/examples/OmicsDB-V1.0.0/04-详细设计文档.md` 6.1 节统一响应结构）：
>
> ```json
> {
>   "code": "0",
>   "message": "success",
>   "traceId": "abc123",
>   "data": {}
> }
> ```
>
> **常见错误**：
> - 不同接口出现不同的响应外壳字段名（如 `errCode` vs `code`、`msg` vs `message`），破坏前端统一拦截。
> - 时间字段一会儿用 `yyyy-MM-dd HH:mm:ss`、一会儿用时间戳数字，未统一。
> - 分页字段名漂移（`pageNo` vs `page`、`size` vs `pageSize`），前端解析失败。
> - 认证 Header 写成 `token: xxx` 而非标准的 `Authorization: Bearer xxx`。

### 1.1 基础约定

| 项目 | 值 |
|:---|:---|
| 基础 URL | `http://{host}:{port}` |
| 版本前缀 | `/api/v1/` |
| Content-Type | `application/json; charset=UTF-8` |
| 认证方式 | `Authorization: Bearer {accessToken}` |
| 时间格式 | `yyyy-MM-dd HH:mm:ss` |
| 字符集 | UTF-8 |

### 1.2 鉴权说明

- 所有业务接口默认需要认证，除「白名单接口」（见第 4.3 节）。
- Token 通过 `Authorization` 请求头携带；Token 过期/失效/在黑名单中均返回 HTTP 401 + 业务错误码。

### 1.3 统一响应结构

```json
{
  "code": "0",
  "message": "success",
  "traceId": "{requestUuid}",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| code | String | `"0"` 表示成功，其他为业务错误码 |
| message | String | 提示信息 |
| traceId | String | 链路追踪 ID（MDC 注入） |
| data | Object \| Array \| null | 业务数据，无数据时为 null |

### 1.4 分页响应结构

```json
{
  "code": "0",
  "data": {
    "total": 100,
    "list": [],
    "page": 1,
    "pageSize": 10,
    "totalPages": 10
  }
}
```

### 1.5 分页请求参数

| 参数 | 类型 | 默认值 | 说明 |
|:---|:---|:---|:---|
| page | Integer | 1 | 页码（从 1 开始） |
| pageSize | Integer | 10 | 每页条数（建议上限 100） |

> - JSON 字段命名混用 snake_case 与 camelCase；响应字段表写 camelCase，示例 JSON 写 snake_case。

## 4. 安全设计

> **填写指引**：本章节给出认证安全、授权安全、白名单接口、传输安全四方面的实现方式。每条安全措施都要明确「实现方式」而非泛泛而谈。Token 有效期、密码加密算法及强度因子、登录失败锁定策略要给具体参数。
>
> **字段清单**：
>
> | 字段名 | 类型 | 必填 | 说明 | 示例值 |
> |---|---|---|---|---|
> | 密码加密算法 | String | 是 | 算法 + 强度因子 | `BCrypt(strength=10)` |
> | Token 算法 | String | 是 | 签名算法 | `JWT (HS256)` |
> | accessToken TTL | Duration | 是 | 秒/小时 | `7200s（2小时）` |
> | refreshToken TTL | Duration | 是 | 秒/天 | `604800s（7天）` |
> | 登录失败锁定 | Policy | 是 | N 次失败锁定 M 分钟 | `5次失败锁定30分钟` |
> | 白名单路径 | List | 是 | 免认证路径 | `/api/v1/auth/login` |
> | 数据传输安全 | String | 是 | HTTPS / CORS / CSRF | `生产环境强制 HTTPS` |
>
> **示例片段**（摘自示例 8.1 认证安全）：
>
> | 安全措施 | 实现方式 |
> |:---|:---|
> | 密码存储 | BCrypt 加密（强度因子 10），杜绝明文存储 |
> | Token 认证 | JWT（JJWT 0.12.3），HMAC-SHA256 签名 |
> | Token 黑名单 | 登出时将 Token jti 写入 Redis，TTL = Token 剩余有效时间 |
> | 登录限流 | 5次失败锁定30分钟（Redis 计数器） |
>
> **常见错误**：
> - Token 有效期写「合理」「较短」等模糊词，未给秒数。
> - 白名单只写一句「登录、注册接口免认证」，未列具体路径，给运维难以维护。
> - 漏写 CORS、CSRF、HTTPS 的明确策略。
> - 密码算法只写 BCrypt，未给强度因子（10/12 实际安全性差异很大）。

### 4.1 认证安全

| 安全措施 | 实现方式 |
|:---|:---|
| 密码存储 | `BCrypt`（强度因子 {10}），禁止明文 / MD5 存储 |
| Token 认证 | JWT（{HS256}），Header.Payload.Signature |
| Token 黑名单 | 登出写入 Redis，TTL = Token 剩余有效期 |
| accessToken 有效期 | `{7200}` 秒 |
| refreshToken 有效期 | `{604800}` 秒 |
| 登录失败锁定 | `{5}` 次失败锁定 `{1800}` 秒（Redis 计数器） |

### 4.2 授权安全

| 安全措施 | 实现方式 |
|:---|:---|
| 方法级权限 | `@PreAuthorize("hasAnyRole(...)")` / `hasAuthority('module:action')` |
| 数据权限 | Service 层根据当前用户角色动态注入查询条件 |
| 角色层级 | 通过 `{managed_by}` 等字段控制可见数据范围 |
| CORS | 仅允许配置的前端域名跨域 |

### 4.3 白名单（免认证）接口

```yaml
permit-urls:
  - /api/v1/auth/login
  - /api/v1/auth/refresh
  - /actuator/health
  - /swagger-ui/**
  - /v3/api-docs/**
```

### 4.4 数据传输安全

- 生产环境强制 HTTPS（HSTS 开启）。
- 敏感字段（密码、Token、手机号、邮箱）在日志中按第 6.4 节脱敏规则处理。
- 防 CSRF：JWT + SameSite Cookie 策略；无状态 API 默认关闭 CSRF Filter。

## 5. 缓存设计

> **填写指引**：本章节列出所有 Redis Key 的命名规范、TTL、用途，并定义缓存防护策略（穿透、雪崩、击穿）。Key 必须使用项目统一前缀；TTL 必须给具体秒数，禁止「视情况而定」。
>
> **字段清单**：
>
> | 字段名 | 类型 | 必填 | 说明 | 示例值 |
> |---|---|---|---|---|
> | Key 前缀 | String | 是 | 项目级前缀 | `{project}:portal:` |
> | Key | String | 是 | 完整 Key 模板（含占位符） | `token:blacklist:{token}` |
> | TTL | Duration | 是 | 秒数或「随 Token 同步」 | `600s` |
> | 用途 | String | 是 | 简述 | 筛选选项缓存 |
> | 防护策略 | Text | 是 | 穿透/雪崩/击穿 | 见 5.2 |
>
> **示例片段**（摘自示例 9.1 Redis Key 规范）：
>
> | Redis Key | TTL | 用途 |
> |:---|:---|:---|
> | `token:blacklist:{token}` | Token 剩余有效期 | 登出 Token 黑名单 |
> | `user:token:{userId}` | 与 Token 同步 | 用户-Token 关联（单端登录） |
> | `cache:filter:options` | 600s | 筛选选项缓存 |
> | `login:fail:{username}` | 1800s | 登录失败次数计数 |
> | `login:lock:{username}` | 1800s | 账号锁定标记 |
>
> **常见错误**：
> - Key 缺前缀，与其他业务共享 Redis 时冲突。
> - TTL 写「永久」，导致内存泄漏。
> - 漏写缓存穿透防护，空值缓存策略缺失。

### 5.1 Redis Key 规范

所有 Key 以 `{project}:portal:` 为前缀。

| Redis Key | TTL | 用途 |
|:---|:---|:---|
| `token:blacklist:{token}` | Token 剩余有效期 | 登出黑名单 |
| `user:token:{userId}` | 与 Token 同步 | 单端登录控制 |
| `cache:{module}:{key}` | `{N}` 秒 | 业务数据缓存 |
| `login:fail:{username}` | `{1800}` 秒 | 登录失败计数 |
| `login:lock:{username}` | `{1800}` 秒 | 账号锁定标记 |

### 5.2 缓存防护策略

- **穿透**：缓存空值（值为 `{}` 或 `null`），TTL 设为较短（如 60s）。
- **雪崩**：TTL 加随机抖动（基础 TTL ± 10%）。
- **击穿**：热点 Key 加分布式锁（Redisson `lock:{cacheKey}`）防止并发回源。
- **一致性**：写库后主动失效相关缓存（Cache-Aside）。

## 6. 日志设计

> **填写指引**：本章节定义日志框架、格式、输出目标和敏感字段脱敏规则。必须包含 traceId（链路追踪 ID）注入方式，前端、网关、应用三层共享同一个 traceId。敏感字段脱敏规则必须给具体替换格式。
>
> **字段清单**：
>
> | 字段名 | 类型 | 必填 | 说明 | 示例值 |
> |---|---|---|---|---|
> | 日志框架 | String | 是 | 框架名 + 版本 | `SLF4J + Logback` |
> | 日志格式 | String | 是 | Pattern | 见 6.2 |
> | traceId | String | 是 | MDC 字段 | `%X{traceId}` |
> | 输出目标 | Table | 是 | 控制台 / 文件 / 级别 | 见 6.3 |
> | 敏感脱敏 | Table | 是 | 字段 / 脱敏规则 | 见 6.4 |
>
> **示例片段**（摘自示例 10.2 日志格式）：
>
> ```
> %d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] [%X{traceId}] %-5level %logger{50} - %msg%n
> ```
>
> 示例行：
> ```
> 2026-03-06 10:30:00.123 [http-nio-8080-exec-1] [abc-uuid-123] INFO  c.o.p.c.OAOrderController - List OA orders: {page=1, pageSize=10}
> ```
>
> **常见错误**：
> - 日志格式缺 traceId，定位线上问题时无法串起多条请求。
> - 敏感字段（密码、手机号、邮箱）原文输出到日志。
> - 同时使用 `System.out.println` 与 SLF4J，输出格式不一致。
> - 文件路径未配置滚动策略，磁盘被打爆。

### 6.1 日志规范

- 框架：`{SLF4J + Logback}`，禁止 `System.out.println`。
- traceId：每次请求生成 UUID，写入 MDC，并在响应外壳 `traceId` 字段返回。
- 级别约定：DEBUG 仅开发环境；生产默认 INFO；异常用 ERROR 并打印堆栈。

### 6.2 日志格式

```
%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] [%X{traceId}] %-5level %logger{50} - %msg%n
```

### 6.3 日志输出目标

| 目标 | 路径 | 级别 | 滚动策略 |
|:---|:---|:---|:---|
| 控制台 | - | DEBUG（开发） | - |
| 文件 | `logs/{project}-portal.log` | INFO（生产） | 按天滚动，保留 30 天 |
| 错误文件 | `logs/{project}-portal-error.log` | ERROR | 按天滚动，保留 60 天 |

### 6.4 敏感字段脱敏规则

| 字段 | 脱敏规则 | 示例 |
|:---|:---|:---|
| `password` | 整字段替换为 `***` | `***` |
| `phone` | 中间 4 位用 `*` | `138****1234` |
| `email` | `@` 前保留首尾字符 | `z***g@example.com` |
| `idCard` | 中间 8 位 `*` | `110101********1234` |
| `accessToken` / `refreshToken` | 只保留前 8 后 4 | `eyJhbGci...kc2A` |

## 7. 错误码定义

> **填写指引**：本章节是错误码的**唯一事实源**。所有接口在第 2 章引用错误码必须在此声明；本章每个错误码必须给出 HTTP 状态码、业务码、触发场景。错误码采用模块化前缀（如 `AUTH_xxx`、`PARAM_xxx`、`BUSINESS_xxx`）。新增错误码必须先入册本章，再在接口处引用。
>
> **字段清单**：
>
> | 字段名 | 类型 | 必填 | 说明 | 示例值 |
> |---|---|---|---|---|
> | HTTP 状态码 | Integer | 是 | 标准 HTTP 状态 | 401 |
> | 业务错误码 | String | 是 | 模块前缀 + 序号 | `AUTH_001` |
> | 模块前缀 | String | 是 | 模块标识 | `AUTH` / `PARAM` / `BUSINESS` |
> | 含义 | String | 是 | 一句话说明 | 用户名或密码错误 |
> | 触发场景 | String | 是 | 何时返回 | 登录时账号或密码不匹配 |
>
> **示例片段**（摘自示例 11.2 业务错误码）：
>
> | 错误码 | 说明 |
> |:---|:---|
> | `0` | 成功 |
> | `AUTH_001` | 用户名或密码错误 |
> | `AUTH_002` | 账号已被锁定 |
> | `AUTH_004` | Token 已过期 |
> | `AUTH_005` | Token 已失效（在黑名单中） |
> | `PARAM_001` | 请求参数校验失败 |
> | `BUSINESS_001` | 用户名已存在 |
>
> **常见错误**：
> - 接口出现的错误码本章未声明（孤立错误码）。
> - 同一错误用不同业务码（如同一处「Token 过期」既出现 `AUTH_004` 又出现 `TOKEN_EXP`）。
> - HTTP 状态码与业务码不匹配（参数校验失败返回 500）。
> - 错误码字符串前后空格、大小写不一致（`AUTH_001` vs `auth_001`）。

### 7.1 HTTP 状态码

| HTTP 状态码 | 说明 |
|:---:|:---|
| 200 | 请求成功 |
| 400 | 请求参数错误（Validation 失败） |
| 401 | 未认证（Token 无效 / 过期 / 在黑名单） |
| 403 | 无权限（角色或权限不足） |
| 404 | 资源不存在 |
| 409 | 冲突（如唯一约束已存在） |
| 500 | 服务器内部错误 |

### 7.2 业务错误码（`ApiResult.code`）

| 错误码 | HTTP | 含义 | 触发场景 |
|:---|:---:|:---|:---|
| `0` | 200 | 成功 | 正常返回 |
| `AUTH_001` | 401 | 用户名或密码错误 | 登录校验失败 |
| `AUTH_002` | 401 | 账号已被锁定 | 失败次数超阈值 |
| `AUTH_003` | 401 | 账号已被禁用 | `t_user.status = 0` |
| `AUTH_004` | 401 | Token 已过期 | accessToken 超期 |
| `AUTH_005` | 401 | Token 已失效 | 在黑名单中 |
| `PARAM_001` | 400 | 请求参数校验失败 | Bean Validation 失败 |
| `BUSINESS_001` | 409 | 资源已存在 | 唯一约束冲突 |
| `BUSINESS_002` | 400 | 业务校验失败 | 业务规则不通过 |
| `404` | 404 | 资源不存在 | 实体未查询到 |
| `500` | 500 | 系统内部错误 | 兜底异常 |
