# 需求文档模板

## 0. 使用说明

- **上游输入**：`docs/00-全局公共说明.md`（项目系统级公共规范基线：角色权限/全局规则/非功能基线）、用户原始需求、业务方访谈记录、竞品调研、原始流程材料。
- **下游消费者**：数据流转设计、原型文档、详细设计文档、前端文档、测试用例文档。
- **产出原则**：只描述「业务要做什么」与「为什么」，不写「技术怎么实现」；字段、状态、角色一旦在本文档定义，必须贯穿下游所有文档不变形。每个功能点必须有稳定的需求编号，编号一经创建不得复用；全量需求文档必须标明每个功能点的引入版本、最近变更版本、需求类型和当前状态，便于增量需求追溯与测试用例关联。
- **业务语言优先**：正文优先使用业务语言和用户可理解的表达，例如“启用状态的产品”“当前项目为 WGS/WES 时展示入口”。不要在 01 中直接写 `status = 1`、`projectCode === 'XOME'`、前端变量名、接口字段名、数据库字段名、菜单 ID、内部状态码等实现细节；这类技术信息应下沉到详细设计文档或实现文档。
- **增量更新规则**：如本次是在既有基线之上更新全量 01，必须基于现有全量需求文档直接更新正文；不能脱离现有 01 另起一份并行需求正文。更新完成后，必须核对所有受影响功能点的`需求类型`、`引入版本`、`最近变更版本`、`当前状态`、`关联验收编号`，并同步检查附录 A. 需求功能点追踪矩阵是否完成更新。
- **命名约定**：输出到 `docs/01-需求文档.md`；文档正文中文，代码标识/接口字段/数据库字段/角色编码/权限编码使用英文。

## 5. 功能清单

> **填写指引**：用功能点编号列出本期所有功能，这是下游详细需求、详细设计、测试用例的索引。每个功能点必须有唯一且稳定的编号，编号格式按页面层级选择：
>
> - 一级页面功能：`REQ-{模块编码}-{一级页面编码}-{序号}`，如 `REQ-INSIGHT-LIST-001`
> - 二级页面 / Tab / 弹窗 / 抽屉功能：`REQ-{模块编码}-{一级页面编码}-{二级页面编码}-{序号}`，如 `REQ-SYSTEM-USER-DIALOG-001`

>
> **字段清单**：
>
> | 字段名 | 类型 | 必填 | 说明 | 示例值 |
> |---|---|---|---|---|
> | 功能点编号 | string | 是 | 稳定追踪 ID | `REQ-INSIGHT-LIST-001` |
> | 菜单名 | string | 是 | 一级菜单 | 数据洞察中心 |
> | 一级页面 | string | 是 | 页面或主入口 | OA单列表 |
> | 二级页面/区域 | string | 否 | Tab/弹窗/抽屉/详情区 | 详情抽屉 |

> | 功能描述 | string | 是 | 一句话业务能力 | 查看 OA 单基础信息和任务信息 |
> | 需求类型 | enum | 是 | 新增 / 修改 / 删除 / 废弃 | 新增 |

## 6. 模块详细需求

> **填写指引**：按「功能清单」中的功能点编号逐个展开。每个功能点必须以编号作为小节标题，格式为 `#### {功能点编号} {功能名称}`。每个功能点至少包含：版本信息、功能说明、业务规则、交互逻辑、验收关联；业务字段、业务状态按需要补充。禁止出现没有编号的功能描述。优先写中文业务名称与用户可感知含义，不要直接把前端变量名、接口字段名、数据库字段名、状态码数字或内部枚举值写进 01。页面级异常、空状态、失败分支统一在这里展开，不要回写到第 4 章主流程。对于弹窗配置、Tab 切换、选项勾选这类 UI 结构较强的功能，可优先使用“页面展示说明”“选项映射”“提交内容说明”等更直观的小节，不必机械套用业务字段表。若原始需求中已经给出关键字段展示示例、颜色/高亮/红字、只读/禁用、按钮文案、提示语、空态文案等验收口径，必须同步写回对应功能点，不能只贴原型图或在整理时遗漏。涉及展示类或统计类字段时，要把数据来源、计算公式、汇总关系写清楚，不留给下游自行猜测。
>
> **简单功能点可使用轻量骨架**：当一个功能点同时满足以下条件时，可减少小节、减少重复文字，不必强行套用完整骨架：
> - 页面或交互结构简单，通常只有单一入口、单一动作或单一结果；
> - 交互分支少，文字描述已足够说明，不需要额外画交互路径图；
> - 不存在需要单独展开说明的业务字段、业务状态或异常处理。
>
> 采用轻量写法时，建议至少保留：`版本与状态`、`功能说明`、`页面展示说明`或`交互逻辑`、`关联验收编号`；其余小节按需要补充即可。
>
> 涉及数据加载、多步骤操作或接口调用的功能点，可按复杂度补充：
> - **交互路径图（可选）**（`##### 交互路径图`）：当交互逻辑较多、分支较多，或仅靠文字不易理解时，补充 ASCII 流程图，帮助说明正常路径、空状态、加载失败等关键分支；各终态可注明关键 UI 约束（如按钮禁用）。
> - **异常场景**（`##### 异常场景`）：bullet 格式，每条写明触发条件、系统响应和降级方案；按当前功能实际相关性补充主要异常场景即可，不枚举所有技术错误码，也不机械追求固定条数。
>
> **字段清单**（每个功能点的元信息）：
>
> | 字段名 | 类型 | 必填 | 说明 | 示例值 |
> |---|---|---|---|---|
> | 功能点编号 | string | 是 | 与第 5 章一致 | `REQ-INSIGHT-LIST-001` |
> | 功能名称 | string | 是 | 与第 5 章一致 | OA单列表查询 |
> | 需求类型 | enum | 是 | 新增 / 修改 / 删除 / 废弃 | 修改 |
> | 引入版本 | string | 是 | 首次加入版本 | V1.0.0 |
> | 最近变更版本 | string | 是 | 本次/最近变更版本 | V1.1.0 |
> | 当前状态 | enum | 是 | 草稿 / 已确认 / 已实现 / 已废弃 | 已确认 |
> | 关联验收编号 | string[] | 是 | 第 10 章验收编号 | [A01] |
>
> **可选表达方式**（按功能择一或组合使用）：
>
> 1. **业务字段表**：适合列表、表单、详情类功能。
>
> | 字段名 | 类型 | 必填 | 业务含义 | 示例值 |
> |---|---|---|---|---|
> | {业务字段中文名} | string/number/date | 是 | {含义} | {示例} |
>
> 2. **页面展示说明**：适合弹窗配置、Tab 切换、选项勾选类功能，用 bullet 说明页面各区域展示什么、用户先看到什么。
>
> 3. **选项映射/提交内容说明**：适合描述“某分组下有哪些可选项”“保存时提交什么结果”，比直接写 object / array 更易懂。
>
> 4. **分组字段表**：适合新增/编辑弹窗、配置表单、详情分组等字段较多的场景；按“基础信息 / 付费信息 / 配额区”这类分组分别用小表格展示，会比长 bullet 更清晰，也更利于测试提取字段规则。
>
> 5. **区域字段表**：适合查询区、主列表、展开明细区、抽屉汇总区、用量明细表、历史变更表这类“字段很多但结构清楚”的场景；优先按“字段 / 控件或形式 / 说明 / 约束”组织成小表格，比单纯罗列字段名更利于评审和测试引用。
>
> 6. **引入路径/原型对应（可选）**：适合弹窗、Tab、抽屉、详情区等嵌套区域较强的功能点，用 1-2 句说明该功能点位于页面哪个区域、对应哪张原型示意，帮助读者快速定位。若该功能点已有“页面展示说明”小节，优先把“原型对应”直接写在该小节下，而不是只在第 4.2 章统一挂图。
>
> 7. **字段展示示例**：适合原始需求已经给出明确展示口径或示例值的字段，用“字段展示示例为……”的方式保留，避免整理时丢失。
>
> 8. **交互约束说明**：适合颜色/高亮/红字、只读/禁用、显隐、互斥、分页、按钮文案、成功提示、二次确认提示语等直接影响验收的界面行为。
>
> 9. **分类规则表**：当同一功能点业务规则较多（如超过 5 条），或同时涉及来源、范围、计算、汇总、历史记录等多个维度时，优先按分类或表格组织，而不是堆叠长 bullet。
>
> 10. **提示语与结果文案**：操作类交互（如启用、禁用、删除、提交、保存）要写明具体提示语或结果文案；查看态不强行补提示语。
