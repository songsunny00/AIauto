# Templates — 需求开发测试一体化模板中心

## 1. 目标

`Templates/` 用于沉淀“需求 → 设计 → 开发 → 测试”一体化协同过程中的标准模板、追踪治理模板和原型脚手架。

本目录面向两个目标：

1. **流程治理**：让需求、详细设计、测试用例等正式交付物有统一编号和稳定结构。
2. **平台复用**：让 AI / skill / agent 在固定模板之上稳定生成文档、测试骨架和追踪资产。

## 2. 目录结构

```text
Templates/
├─ deliverables/           # 正式交付物模板
│  ├─ 00-全局公共说明.md

│  ├─ 01b-数据流转设计.md
│  ├─ 01c-原型文档.md
│  ├─ 02-详细设计文档.md
│  ├─ 02b-后台文档.md
│  ├─ 02c-前端文档.md
```

## 3. 编号规则

### 3.1 正式交付物

- `00-全局公共说明.md`：项目级公共基线
- `01-需求文档.md`：全量需求基线
- `01b-数据流转设计.md`：可选，复杂数据流 / 状态机 / 权限过滤时使用
- `01c-原型文档.md`：可选，页面 / 交互 / 原型评审时使用
- `02-详细设计文档.md`：开发前主设计文档
- `02b-后台文档.md`：可选，后端实现细化文档
- `02c-前端文档.md`：可选，前端实现细化文档
- `03-测试用例文档.md`：测试设计文档
- `04-测试执行记录.md`：系统级版本测试执行记录
- `05-变更记录.md`：系统级版本正式变更说明
- `INDEX.md`：模块叶子目录索引模板
- `Tests-ui-README.md`：UI 自动化目录说明模板
- `Tests-api-README.md`：API 自动化目录说明模板

### 3.2 编号原则

- `01` 系列都属于需求侧基线与补充材料。
- `01b / 01c` 是条件触发型可选文档，不是所有需求都强制产出。
- 进入开发实施阶段后，编号从 `02` 收敛。
- `04 / 05` 是系统级版本文档，放在 `Prds/` 根目录下的版本目录中使用。
- **正式交付物进入编号体系；生成工艺和实施说明不进入编号体系。**

## 4. 推荐文档链路

### 4.1 全新或复杂需求

```text
00 → 01 → 01b（按需）→ 01c（按需）→ 02 → 02b/02c（按需）→ 03
```

### 4.2 版本需求

```text
00 → 01 → 01b（按需）→ 01c（按需）→ 02 → 02b/02c（按需）→ 03 → 04 → 05（按需）
```

补充说明：

- `01` 始终是正式需求的唯一稳定基线；版本目录默认直接维护 `01-需求文档.md`。
- `01b` 只在数据流、状态机、权限过滤复杂时产出。
- `01c` 只在已有专门原型页面、页面结构复杂、交互规则需要单独说明时产出。
- `02b / 02c` 是开发阶段按需补充的实现文档，不阻塞 `03` 产出。
- `prototypes/html-scaffold/` 仅作为产品原型前端脚手架资源，不进入正式交付文档编号体系。

## 5. 各目录职责

### 5.1 `deliverables/`

放正式模板。所有会进入项目产物编号体系的文档，都在这里维护。

### 5.2 `governance/`

放追踪治理模板，包括 `TRACE.yaml`、`prd-to-code.yaml`。这类文件不进入 01/02/03 编号体系，但属于项目实施过程中的正式治理资产。

### 5.3 `prototypes/`

放原型脚手架资源，如 HTML 静态原型基础目录、可复用样例等。该目录服务于产品原型搭建，不属于正式交付物模板。

### 5.4 单实例入口文档与可复用模板的区别

以下资产虽然与模板体系强相关，但更适合作为仓库中的单实例入口文档直接维护，而不是放进 `Templates/` 里重复复用：

- 仓库根 `README.md`
- `Prds/README.md`
- `docs/traceability-matrix.md`
- `docs/delivery-status-board.md`
- `skills/README.md`

建议原则：

- 会在多个模块/目录重复创建的，优先放进 `Templates/`
- 只会在仓库中存在一份、承担导航或总览职责的，直接在实际路径维护

## 6. 产出文件命名建议

项目落地时，推荐按“**Prds 代表单个系统项目根目录；一级目录为系统功能模块；稳定基线文档下沉到模块叶子目录，版本资产放在 Prds 根目录下的系统级版本目录**”组织，例如：

```text
Prds/
├─ README.md
├─ CHANGELOG.md
├─ V1.5.4.1/
│  ├─ 01-需求文档.md               # 系统级版本正式需求
│  ├─ 04-测试执行记录.md
│  └─ 05-变更记录.md
├─ LOGIN-登录/
│  ├─ INDEX.md
│  ├─ TRACE.yaml
│  ├─ 01-需求文档.md
│  ├─ 01b-数据流转设计.md          # 可选
│  ├─ 01c-原型文档.md              # 可选
│  ├─ 02-详细设计文档.md
│  └─ 03-测试用例文档.md
├─ CONFIG-配置中心/
│  └─ REPORTCFG-报告配置/
│     └─ TYPECFG-报告类别配置/
│        ├─ INDEX.md
│        ├─ TRACE.yaml
│        ├─ 01-需求文档.md
│        ├─ 01b-数据流转设计.md    # 可选
│        ├─ 01c-原型文档.md        # 可选
│        ├─ 02-详细设计文档.md
│        └─ 03-测试用例文档.md
└─ SAMPLE-样本中心/
   └─ ...
```

说明：
- `Prds/` 表示单个系统项目的需求资产根目录，一级目录就是系统功能模块。
- `01-需求文档.md`、`01b`、`01c`、`02`、`03` 等稳定基线文档建议放在功能模块叶子目录。
- `01-需求文档.md`、`04-测试执行记录.md`、`05-变更记录.md` 建议放在 `Prds/` 根目录下的系统级版本目录中，不挂在某个模块下面。
- `TRACE.yaml` 建议常驻功能模块叶子目录，作为该模块的主追踪文件。
- `prd-to-code.yaml` 建议放在 `Codes/mappings/`，按业务模块拆分维护。
- 测试关联关系建议直接通过 `03-测试用例文档.md`、测试点编号和脚本编号维护，不再单独维护映射文件。
- `CHANGELOG.md` 作为系统级持续变更台账常驻 `Prds/` 根目录。

## 7. 使用原则

- 正文优先用中文业务表达，代码标识 / 接口字段 / 角色编码 / 权限编码保留英文。
- 功能点编号由需求文档统一定义，下游文档必须沿用，不得自造编号。
- 版本需求默认直接维护在版本目录下的 `01-需求文档.md`，避免并行维护额外需求正文。
- 所有模板都应服务于“路径主线 + 功能点编号主线”的双轨追踪。
- 原型脚手架资源不能替代正式交付物说明文档。
