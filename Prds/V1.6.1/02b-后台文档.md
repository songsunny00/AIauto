# 付费配额-后台管理接口详细设计（前端 AI 自动化测试用）

> 版本：v1.0　|　日期：2026-07-13　|　适用服务：**omics-core**（端口 8081，经 omics-gateway 8080 路由）
> 覆盖范围：仅「后台管理接口」——`/base/quota/contract`（合同管理）+ `/base/quota/usage`（用量统计）两个 Controller。
> 服务间接口 `/openapi/quota/v1/*`（halos→omics，FixedToken）与内部接口 `/exchange/quota/v1/remain` 不在本文档范围，前端测试不涉及。
> 数据来源：本文档字段、校验、枚举、错误码均**取自 omics-core 实际代码**（`com.bgi.omicsone.base.quota.*`），非设计稿臆测。

## 0. 阅读前必看：实现与早期设计稿的差异

`docs/proposal.md` / `docs/design.md` 是早期方案，**实际代码已演进**，前端请以本文档为准。关键差异：

| 项 | 早期设计稿 | 实际实现（本文档基准） |
|---|---|---|
| 「分析套餐」概念 | 有独立 `base_quota_analysis_package` 表 + 套餐字典 CRUD | **已去除**。合同页直接内嵌配额行，配额行=「检测项目×产品套餐 + 行配额」。无套餐字典接口。 |
| 合同类型 | 区分基础 `BASIC` / 增值 `VALUE_ADDED` | **已去除**。统一为一种合同，扣减改为「同机构命中行按 end_date ASC 逐行 CAS、可跨行跨合同拆分」。DTO/VO 均无 `contractType` 字段。 |
| 后台 Controller 数量 | 4~5 个（package/contract/line/institution/usage） | **2 个**：`QuotaContractController`（合同+内嵌行+覆盖候选）、`QuotaUsageController`（汇总+明细+变更历史+导出）。配额行不再有独立 Controller，随合同级联保存。 |
| 合同变更历史数据源 | `base_operate_log`（操作日志） | **专用表 `base_quota_contract_change_log`**（参数级前后快照 JSON），`history` 接口读此表。 |
| 用量明细 | summary/history/export 三接口 | **四接口**：summary / detail（任务级消耗明细，新增）/ history / export。 |
| 按钮权限 `@OperationPermissions` | 启用，仅 `platform_admin` | **当前全部注释掉**（见各 Controller 方法上被注释的 `//@OperationPermissions`）。即暂无按钮级权限拦截，凡持有有效登录 token 的用户均可调用。前端测试时无需准备特定 buttonId 权限。 |
| 合同状态颜色 | `statusColor` + `statusText` 落库返回 | 改为返回**派生枚举 code** `displayStatus`（不落库），颜色由前端按 code 自渲染。 |

## 1. 通用约定

### 1.1 鉴权与访问入口

| 项 | 说明 |
|---|---|
| 网关 | `omics-gateway`（8080），OAuth2 资源服务器，动态 Nacos 路由 |
| 服务 | `omics-core`（8081），路径前缀即 Controller 的 `@RequestMapping` |
| 完整路径示例 | `POST {网关基址}/base/quota/contract/page` |
| 鉴权 | **登录用户 token**（OAuth2，经网关校验）。请求头携带平台约定的 Authorization token（与平台其他后台接口一致）。 |
| 按钮权限 | `@OperationPermissions` 当前**注释未启用**，无按钮级拦截（见 §0）。后续若启用，buttonId 见各接口说明。 |
| 租户上下文 | 后台接口内部对配额公共库做了 `forcePublicSchema` 强制走公共库处理，前端**无需**特殊处理租户头；查询/写入以请求体里的 `instCode` 为逻辑隔离键。 |

### 1.2 统一响应结构 `ResultMessage<T>`

所有接口（导出除外）统一返回 `ResultMessage<T>`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `requestId` | string | 链路追踪 ID |
| `retCode` | int | **0=成功**；非 0=业务错误码（见 §1.5） |
| `retInfo` | string | 提示信息，成功为 `"success"`；失败为对应文案（走 i18n，中/英） |
| `result` | T | 业务数据载荷，失败时为 null |

成功示例：
```json
{
  "requestId": "a1b2c3d4",
  "retCode": 0,
  "retInfo": "success",
  "result": { /* 业务数据 */ }
}
```
失败示例：
```json
{
  "requestId": "a1b2c3d4",
  "retCode": 10022004,
  "retInfo": "合同不存在",
  "result": null
}
```

> ⚠️ **必填校验的特殊返回**：DTO 上 `@NotEmpty` / `@NotNull` / `@Valid` 注解触发的校验失败（如 `contractNo` 为空），由 Spring `@Validated` 抛出，**可能以 HTTP 400 返回**（具体是否被全局异常处理器包装成 `ResultMessage` 取决于 `GlobalExceptionHandler`）。前端 AI 测试对「必填缺失」用例应同时兼容 400 与 `retCode≠0` 两种断言；业务规则校验（周期/编号唯一/行配额和等）一定走 `ResultMessage.retCode`。

### 1.3 分页约定

**分页请求**（继承 `CommonPage`，作为请求体字段的一部分）：

| 字段 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `pageNum` | int | 是 | 1 | 当前页码 |
| `pageSize` | int | 是 | 10 | 每页条数 |
| `sortName` | string | 否 | `""` | 排序字段（后台多数接口内部固定按 `create_time` DESC，忽略此字段） |
| `sortOrder` | string | 否 | `DESC` | `DESC` / `ASC` |

**分页响应有两种结构，按接口区分（重要）**：

- **MyBatis-Plus `Page<T>`**（合同分页 `page` 接口用）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `records` | array<T> | 当前页数据列表 |
| `total` | long | 总记录数 |
| `current` | long | 当前页码 |
| `size` | long | 每页条数 |
| `pages` | long | 总页数 |

- **PageHelper `PageInfo<T>`**（变更历史 `history` 接口用）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `list` | array<T> | 当前页数据列表（注意是 `list` 不是 `records`） |
| `total` | long | 总记录数 |
| `pageNum` | int | 当前页码 |
| `pageSize` | int | 每页条数 |
| `pages` | int | 总页数 |
| `hasPreviousPage` | boolean | 是否有上一页 |
| `hasNextPage` | boolean | 是否有下一页 |

### 1.4 枚举字典

#### 1.4.1 合同落库状态 `status`（`QuotaStatusEnum`）

写入与查询均用此码值，存于 `base_quota_contract.status`。

| code | 含义 | 可逆性 | 说明 |
|---|---|---|---|
| `ENABLED` | 启用 | 可逆→DISABLED | 可参与扣减反查、计入可用额度 |
| `DISABLED` | 停用 | 可逆→ENABLED | 管理员手动暂停，不计入可用额度 |
| `TERMINATED` | 终止 | **不可逆（终态）** | 合同被提前结束；不可再启用/停用 |

#### 1.4.2 合同展示状态 `displayStatus`（`QuotaContractStatusEnum`，派生不落库）

`page` / `detail` 返回的 `displayStatus` 字段，由后端按 `status` + 到期日**查询时派生**，前端据此渲染颜色徽标。`page` 接口的 QO `displayStatus` 筛选也用这 4 个 code。

| code | 含义 | 派生规则（按优先级自上而下命中） |
|---|---|---|
| `DISABLED` | 已停用 | `status = DISABLED` 或 `status = TERMINATED`（停用与终止合并展示） |
| `EXPIRED` | 已到期 | `status = ENABLED` 且 `endDate < 今天` |
| `EXPIRING_SOON` | 即将到期 | `status = ENABLED` 且 `今天 ≤ endDate ≤ 今天+30天`（含两端） |
| `NORMAL` | 正常 | `status = ENABLED` 且 `endDate > 今天+30天` |

> 边界口径：`endDate == 今天` 视为**未过期**（仍可用于扣减），落入「即将到期」窗口；`今天+30天` 含入「即将到期」；`今天+31天` 起为「正常」。`endDate` 为空兜底 `NORMAL`（数据异常场景）。

#### 1.4.3 变更日志操作类型 `opType`（`base_quota_contract_change_log.op_type`）

| code | 含义 | 触发接口 |
|---|---|---|
| `CREATE` | 新增 | `POST /base/quota/contract/add` |
| `EDIT` | 编辑 | `POST /base/quota/contract/edit` |

> `history` 接口的 QO `operType` 即按此 code 过滤。

### 1.5 错误码清单（`QuotaMsgCodeDefinition`，8 位 `10022xxx`）

下表「后台管理是否触发」标注该码在本文档覆盖的 2 个 Controller 中是否会被抛出。

| 错误码 | 常量 | 含义 | 后台管理是否触发 | 典型触发场景 |
|---|---|---|---|---|
| 10022001 | QUOTA_NO_COVERAGE | 产品未配置有效付费配额套餐覆盖 | ❌ 否（仅 /openapi reserve） | — |
| 10022002 | QUOTA_INSUFFICIENT | 样本分析次数余额不足 | ❌ 否（仅 /openapi reserve） | — |
| 10022003 | QUOTA_PARAM_INVALID | 参数错误 | ✅ 是 | 见下方详细清单 |
| 10022004 | QUOTA_CONTRACT_NOT_FOUND | 合同不存在 | ✅ 是 | detail/edit/toggle/terminate 传了不存在的 contractId |
| 10022005 | QUOTA_TASK_NOT_FOUND | 预扣记录不存在 | ❌ 否（仅 /openapi confirm/refund） | — |
| 10022006 | QUOTA_LINE_OVERLAP | 配额行覆盖范围冲突 | ⚠️ 已定义但当前 add/edit 保存路径**未抛出** | 定义保留，前端测试不应期望此码 |
| 10022007 | QUOTA_CONTRACT_DATE_INVALID | 合同日期非法 | ✅ 是 | add/edit 的 `endDate < startDate` |
| 10022008 | QUOTA_INST_DISABLED | 机构已禁用 | ❌ 否（当前后台保存路径未校验） | — |
| 10022009 | QUOTA_STATE_CONFLICT | 扣减状态冲突 | ✅ 是 | 对已终止合同调 toggle |

**10022003 QUOTA_PARAM_INVALID 在后台管理接口的详细触发清单**（`retInfo` 会带具体原因）：

- `contractId 不能为空`（edit/toggle/terminate/detail 路径或体里 contractId 缺失）
- `生效日/截止日不能为空`、`样本分析总次数不能为空`（add/edit）
- `合同编号已存在: <contractNo>`（add/edit 同 instCode 下 contractNo 重复）
- `各行配额之和(<sum>)超过合同总配额(<total>)`（add/edit Σ lines.sampleQuota > sampleTotalQuota）
- `行配额(<x>)不能小于已用次数(<y>)`（edit 改行配额低于该行已确认 usedCount）
- `目标状态只能为 ENABLED/DISABLED`（toggle 传了 TERMINATED 或其他值）
- `合同展示状态不合法: <displayStatus>`（page 传了非 4 个枚举 code 的 displayStatus）

> 另：用量导出失败抛 `FILE_DOWNLOAD_ERROR`（`BaseMsgCodeDefinition`，非配额段码值，前端按 retInfo 断言即可）。

## 2. 合同管理接口 `/base/quota/contract`

> 类：`QuotaContractController`，`@Api(tags = "付费配额-合同")`。
> 合同页采用「**内嵌管行**」：新增/编辑合同时，请求体直接携带嵌套配额行 `lines[]`（每行含 `sampleQuota` + 覆盖范围多选 `coverages[]`），后端事务内级联保存合同本体 + 行 + 覆盖明细，无需分步调独立的行接口。

### 2.1 分页查询合同 `POST /base/quota/contract/page`

**用途**：合同列表展示。返回合同字段（含派生 `displayStatus`）+ 每个合同下配额行的覆盖明细（用于列表「检测项目」列）。

**请求体** `QuotaContractQO`（继承 `CommonPage`，含分页字段）：

| 字段 | 类型 | 必填 | 校验/说明 |
|---|---|---|---|
| `pageNum` | int | 是 | 当前页，默认 1 |
| `pageSize` | int | 是 | 每页条数，默认 10 |
| `instCode` | string | 否 | 机构编码，精确匹配 |
| `keyword` | string | 否 | 合同编号或名称，**模糊**匹配（任一命中） |
| `status` | string | 否 | 落库状态筛选：`ENABLED`/`DISABLED`/`TERMINATED`（精确） |
| `displayStatus` | string | 否 | 展示状态筛选：`NORMAL`/`EXPIRING_SOON`/`EXPIRED`/`DISABLED`；非法值抛 10022003。与 `status` 可同时传（AND） |
| `projectCode` | string | 否 | 检测项目编码；命中「合同下任一配额行覆盖明细含此 projectCode」的合同即返回 |
| `productNo` | string | 否 | 产品套餐编号；命中「合同下任一配额行覆盖明细含此 productNo」的合同即返回。与 `projectCode` 可同时传（同一明细行 AND） |

> `projectCode`/`productNo` 不是合同表字段，后端用 EXISTS 子查询下钻到 `base_quota_line_coverage` 过滤。

**响应** `ResultMessage<Page<QuotaContractVO>>`，`records[]` 元素结构见 §2.1.1。

#### 2.1.1 `QuotaContractVO` 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `contractId` | long | 合同主键 |
| `contractNo` | string | 合同编号 |
| `instCode` | string | 机构编码 |
| `instName` | string | 机构名（冗余） |
| `contractName` | string | 合同名称 |
| `sampleTotalQuota` | int | 样本分析总次数（合同级上限） |
| `storageDays` | int | 数据存储期限（天，本期仅配置不拦截） |
| `downloadLimit` | int | 单样本下载次数（本期仅配置不拦截） |
| `startDate` | string | 生效日，`yyyy-MM-dd HH:mm:ss` |
| `endDate` | string | 截止日，`yyyy-MM-dd HH:mm:ss` |
| `status` | string | 落库状态：`ENABLED`/`DISABLED`/`TERMINATED` |
| `terminated` | int | 是否已终止：`0` 否 / `1` 是（便于前端判终态） |
| `displayStatus` | string | 派生展示状态：`NORMAL`/`EXPIRING_SOON`/`EXPIRED`/`DISABLED` |
| `remark` | string | 备注 |
| `createUser` | string | 创建者 |
| `createTime` | string | 创建时间（全局 `yyyy-MM-dd HH:mm:ss`） |
| `updateUser` | string | 更新者 |
| `updateTime` | string | 更新时间 |
| `lines` | array | 配额行列表（含覆盖明细），结构见 §2.1.2 |

#### 2.1.2 `QuotaLineVO` 字段（`lines[]` 元素）

| 字段 | 类型 | 说明 |
|---|---|---|
| `lineId` | long | 配额行主键 |
| `contractId` | long | 所属合同 ID |
| `instCode` | string | 机构编码 |
| `sampleQuota` | int | 本行购买样本分析次数 |
| `usedCount` | int | 已确认扣减累计 |
| `frozenCount` | int | 预扣冻结（未确认） |
| `remain` | int | 可用剩余 = sampleQuota − usedCount − frozenCount |
| `coverages` | array | 覆盖范围列表，结构见下 |
| `createUser` | string | 创建者 |
| `createTime` | string | 创建时间 |

### 2.2 合同详情 `GET /base/quota/contract/{contractId}`

**用途**：编辑回显。返回合同字段 + 嵌套配额行（含覆盖明细）。

**路径参数**：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `contractId` | long | 是 | 合同主键 |

**响应** `ResultMessage<QuotaContractVO>`（结构同 §2.1.1，含完整 `lines[]`）。

**请求示例**：
```
GET /base/quota/contract/1789000001
```

**响应示例**：同 §2.1 响应示例中 `result.records[0]` 单个对象结构。

**测试场景**：

| # | 场景 | 入参 | 预期 |
|---|---|---|---|
| 1 | 正常详情 | 存在的 contractId | retCode=0，返回含 lines（含 coverages） |
| 2 | 合同不存在 | contractId=999999999 | retCode=10022004，retInfo「合同不存在」 |
| 3 | contractId 缺失 | GET /base/quota/contract/ | 路由不匹配（404）或框架默认处理 |
| 4 | 已删除合同 | 传 del_flag=1 的合同 id | retCode=10022004（getById 查不到，因逻辑删除） |

### 2.3 覆盖范围候选 `GET /base/quota/contract/coverage-candidates`

**用途**：合同页内嵌配额行的「检测项目 × 产品套餐」级联选择器 options。一级=检测项目，二级=该项目下产品套餐。无入参。

**响应** `ResultMessage<List<QuotaCoverageCandidateVO>>`：

| 字段 | 类型 | 说明 |

### 2.4 新增合同 `POST /base/quota/contract/add`

**用途**：新增合同 + 内嵌配额行 + 覆盖明细（事务级联），并写一条 `CREATE` 变更日志。

**请求体** `QuotaContractDTO`：

| 字段 | 类型 | 必填 | 校验/说明 |
|---|---|---|---|
| `contractId` | long | 否 | 新增留空 |
| `contractNo` | string | 是 | 同 instCode 下唯一 |
| `instCode` | string | 是 | 机构编码 |
| `instName` | string | 否 | 机构名（冗余展示） |

### 2.5 编辑合同 `POST /base/quota/contract/edit`

**用途**：编辑合同本体 + **整表覆盖**同步配额行（删/改/增）+ 覆盖明细，写一条 `EDIT` 变更日志。

**请求体** `QuotaContractDTO`（同 §2.4，但 `contractId` 必填）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `contractId` | long | **是** | 编辑必填，否则抛 10022003 |
| 其余字段 | — | — | 同 §2.4 |

**行同步语义（整表覆盖，重要）**：
- `lines[]` 中**带 `lineId`** 且命中旧行 → **更新**该行（校验：新 `sampleQuota` ≥ 该行已用 `usedCount`，否则抛 10022003「行配额...不能小于已用次数」）。

- DB 中有但 `lines[]` **未带**的旧行 → **删除**（逻辑删行 + 物理删覆盖明细）。
- 行的 `coverages` 走「先删后建」整行重建。

**业务校验**：同 add 的 1~4，另加：
- contractId 非空（否则 10022003）。
- 合同必须存在（否则 10022004）。
- 更新行：新 sampleQuota ≥ 该行 usedCount（否则 10022003）。

**响应** `ResultMessage<Boolean>`，`result=true`。

**请求示例**（保留一行、改配额、新增一行、删一行）：

```json
  "lines": [
    {
      "lineId": 1789100001,

      "coverages": [ { "projectCode": "NIPT", "productNo": "NIPT-STANDARD" } ]
    },
    {
      "sampleQuota": 500,
      "coverages": [ { "projectCode": "CNV", "productNo": "CNV-WHOLE" } ]
    }
  ]
}
```

**响应示例**：
```json
{ "requestId": "r-004", "retCode": 0, "retInfo": "success", "result": true }
```

**测试场景**：

## 5. AI 自动化测试总体建议

1. **数据准备顺序**：先调 `GET /coverage-candidates` 拿到合法 `projectCode`/`productNo` → 再 `POST /add` 建合同（带行）→ `POST /page` 或 `GET /{id}` 校验 → `POST /edit` 改配额 → `POST /usage/summary` 看汇总 → `POST /usage/history` 看变更日志。`detail`/`export` 依赖真实扣减流水（需投递链路产生 CONFIRMED 记录），无投递数据时 `detail`/`export` 返回空。

2. **日期格式**：合同 `startDate`/`endDate` 用 `yyyy-MM-dd HH:mm:ss`（时区 GMT+8）；变更历史 `startTime`/`endTime` 用 `yyyy-MM-dd HH:mm:ss`。格式不符会反序列化失败（400）。

3. **两种分页响应**：`page` 用 `records`，`history` 用 `list`，断言时勿混用。

4. **`displayStatus` 是派生态**：同一合同在不同日期查询可能返回不同 `displayStatus`（随到期日变化），测试「即将到期/已到期」用例需构造对应 `endDate` 的合同，避免依赖固定期望值。

5. **行同步是整表覆盖**：编辑合同时，未在 `lines[]` 中带出的旧行会被删除。测试「保留旧行」必须把旧行 `lineId` 原样回传。

6. **必填校验 vs 业务校验**：`@NotEmpty`/`@NotNull` 校验可能返回 HTTP 400（非 ResultMessage）；业务校验（周期/唯一/和/状态）一定返回 `ResultMessage.retCode`。负例断言建议两者兼容。

7. **权限**：当前 `@OperationPermissions` 未启用，无需准备 buttonId 权限；仅需有效登录 token。若后续启用，各接口 buttonId 前缀为 `quota:contract:*` / `quota:usage:*`（详见各方法注释）。

8. **幂等/终态**：`terminate` 幂等；`toggle` 对已终止合同抛 10022009；`edit` 改行配额不可低于已用 `usedCount`。

9. **配额口径**：`detail`/`export` 的 `sampleQuota`/`remainCount` 是产品套餐级、会在多任务行重复显示，属正常口径，非 bug。
