# detail-design-bootstrap

## 1. 目标与适用对象

把 `01-需求文档.md` + `02b-后台文档.md` + 前端模块代码目录三类输入，按 `Templates/deliverables/02-详细设计文档.md` 模板自动生成 `02-详细设计文档.md`，并同步产出独立的 `02-详细设计文档.证据表.md` 作为可追溯附录。

**适用对象**：项目开发管理人（同时承担开发与协调职责，能裁决需求 ↔ 代码差异）。

**三个核心约束（贯穿全流程，不可妥协）**：

1. 详设与前端代码实际实现**严格一致**。
2. 需求未提及时，提取并沿用**前端代码实际逻辑**写入详设。
3. **禁止凭空臆测**；仅当需求 + 代码均无相关实现时，才允许逻辑补充，且必须显式标注。

## 2. 触发条件（严格遵守）

- ✅ **触发**：用户显式调用，例如：
  - "根据 V1.6.1 生成详设"
  - "用 detail-design-bootstrap 生成 02"
  - "重新生成 billingConfig 模块的 02"
- ❌ **不触发**：未显式调用时，即使有人提到"详设"或修改了 `01` / `02b`，也**绝不擅自覆盖**既有 `02`。

> 该约束是硬性的：Skill 未被显式触发时不得运行、不得覆盖既有 02 文档。

## 3. 输入契约

| 输入             | 必需性                 | 路径示例                                            | 用途                                     |
| ---------------- | ---------------------- | --------------------------------------------------- | ---------------------------------------- |
| 需求文档         | 必需                   | `Prds/V1.6.1/01-需求文档.md`                        | REQ 编号、业务字段名、验收口径真源       |
| 后台接口 Spec    | 必需                   | `Prds/V1.6.1/02b-后台文档.md`                       | 接口路径、参数、错误码、响应结构         |
| 前端模块代码路径 | 必需（与 spec 二选一） | `D:\Codes\omics-web\src\views\Config\billingConfig` | 实际实现逻辑、字段映射、校验、文案       |
| 前端 spec        | 可选替代               | 暂不强制定义；后续扩展                              | 当代码不可读时作为退化输入               |
| 模板             | 必需                   | `Templates/deliverables/02-详细设计文档.md`         | 输出结构基线                             |
| 全局说明         | 可选                   | `Prds/V1.6.1/00-全局说明.md`                        | 验证详设不重复全局内容（附录 A 第 1 项） |

**说明**：本次先聚焦"前端模块代码路径"作为主输入；"前端 spec"留作占位，待后续用户澄清具体指 Playwright spec / Vitest 单测 / Storybook 后再扩展。

## 4. 探查流程（交互式确认清单）

```text
1. 读取 Prds/Vx.y.z/01-需求文档.md → 抽取 REQ 清单 + 每个 REQ 的主接口
2. 读取 Prds/Vx.y.z/02b-后台文档.md → 抽取接口路径 → 参数/响应/错误码
3. 扫描用户传入的前端模块根目录 → 列出所有 .vue/.ts/.js 文件
4. 解析每个文件 import 语句 → 跟踪引用文件（限 omics-web 项目内）
   跟踪范围建议（来自 Prds/AGENTS.md 约定）：
     - composables/（useTable/useForm/useDialog/usePermission）
     - components/business/（AppForm/AppTable/AppListPage）
     - api/modules/（接口适配层）
     - router/index.js（仅取该模块对应路由块）
     - stores/（仅取该模块相关 store）
     - constants/config.js + utils/validate.js（仅取相关常量/校验函数）
5. 输出「关联文件清单」给用户：
     | 文件路径 | 引用来源 | 推断用途 | 是否纳入扫描 |
     用户可勾选/裁减
6. 用户确认后，Skill 读取最终文件清单 → 进入解析阶段
```

**深度约束**：

- 递归跟踪最多 2 层（避免无限扩散）。
- utils 工具函数只读直接被调用的，不展开其内部依赖。
- 跟踪过程中若出现跨项目引用（如 `@/components/business/AppForm.vue` 实际指向 omics-web 项目外），跳过并标注"跨项目引用未纳入"。

## 5. 真源裁决策略

### 5.1 优先级链（从高到低）

1. **需求文档有明确说明** → 详设正文写需求版本；若代码实际与需求不一致，在证据表记录偏差，但**正文不写代码版本**。
2. **需求文档未提及，代码有实现** → 详设正文写代码实际实现；证据表标注来源 `[CODE]` + 文件路径#行号。
3. **需求 + 代码均无** → 允许 Skill 逻辑补充；正文写补充内容并附行内标记 `[DESIGN-SUPPLEMENT]`；证据表记录"补充依据"（如类似模块惯例、技术约束）。

### 5.2 特殊情况

- **前端实际文案 vs 需求预期文案不一致** → 正文写**需求预期文案**，证据表记录"代码实际文案"作为偏差项。
  - 历史教训：`FT-BILLCFG-FORM-003` 的"请输入字母、数字、-或\_" vs "合同编号仅支持字母、数字、连字符和下划线" 这类差异通过此规则自动沉淀到证据表，由人走变更流程。
- **前端代码 ↔ 后台 Spec 冲突** → 走需求优先；若需求未明确，**后台 Spec 优先于代码**（Spec 是后端契约真源，与 `Prds/AGENTS.md` "接口成功返回 `code: '0'`" 一致）。
- **枚举值/状态映射与需求不一致** → 当 01 明确定义字段枚举值（如「枚举值：启用、禁用」「合同状态枚举：正常/即将到期/已到期/即将生效」）或明确「删除 X、新增 Y」时，**正文枚举表必须严格按 01 的枚举值与数量书写**（正文不写后台 Spec/基线 02 的版本）；后台 Spec 或基线 02 中多出/不同的枚举值（如后端仍派生 `DISABLED`/`TERMINATED`、基线 02 仍含「已停用」）一律记入证据表第 3 节为「需求 ↔ 接口偏差」，**不得写入正文枚举表**。正文枚举表的"态数"（如 4 态/5 态）、行项与优先级链均以 01 为准。
- **交互流程完整性** → 当 01 用一段完整描述刻画某交互的全流程（如"点击 X 后确认成功，按钮切换为 Y，状态变更为 Z，主列表刷新"），02 正文对应步骤须完整反映"触发→确认→成功提示→按钮/状态双向翻转→列表刷新"全链路，不得只写初始展示或只写"刷新"而省略按钮与状态的双向变更。

### 5.3 增量版本失效概念处理

当生成增量版本 02（如 V1.6.3 基于 V1.6.1 基线）时：

1. **识别失效概念**：对比新旧版本 01 的字段表、交互逻辑、业务规则，识别被删除/变更的概念（如"配额行/添加一行/第 X 行"在新版中被"套餐模块"替代）。
2. **处理规则**：旧基线 02 中引用已失效概念的内容（校验文案、异常处理、字段说明）必须删除或调整为新版表述；不得盲目继承。
3. **记录偏差**：在证据表第 3 节记录"已删除失效概念"，标注旧概念与新概念的映射关系。
4. **退化输入警惕（枚举专项）**：当未提供前端代码路径、以「基线 02 + 后台对接文档」作为退化代码真源时，基线 02 的枚举表/状态映射最易盲目继承（典型：V1.6.1 基线为 5 态含「已停用」，V1.6.3 需求已删为 4 态；对接文档 `displayStatus` 派生仍含 `DISABLED`）。生成正文枚举表前，**必须先用 01 的枚举定义覆盖基线 02/对接文档的枚举**，正文态数与行项以 01 为准，差异项进证据表第 3 节；严禁把对接文档/基线 02 的枚举原样搬进正文。

### 5.4 字段命名原则（减少前后端不一致）

生成 02 §6.2"前端与后端字段不一致项及转换逻辑"时，遵循以下原则：

1. **接口字段优先用**：后端接口已有的字段，前端直接沿用后端字段名，不做不必要的重命名（如 `instCode` 不重命名为 `id`，`instName` 不重命名为 `orgName`）。
2. **减少转换**：仅在以下场景才允许前端字段与后端不一致：
   - 多选控件需要数组（后端 CSV → 前端 `string[]`）
   - 展示逻辑需要聚合（如多个状态计数聚合为 `statusCounts`）
   - 页面交互需要拆分（如 `storage.*` 分组）
3. **新增前端字段需标注**：为方便处理页面交互或展示逻辑新增的前端字段，须在转换逻辑列标注"展示逻辑需要"或"页面交互需要"。
4. **后端缺失字段罗列**：后端缺少的字段，在表格后新增"后端缺失字段清单"，罗列缺失字段、推荐字段名、用途、是否必要，由用户决定是否新增。

## 6. REQ 回溯策略（混合 + 交互裁决）

```text
Step 1: 从 01-需求文档.md 抽取 REQ → 主接口路径映射表
        e.g., REQ-CONFIG-BILLCFG-LIST-001 → POST /base/quota/contract/page
Step 2: 从代码提取接口调用（api/modules/*.ts 中函数 → 调用处 component/function）
Step 3: 按接口路径匹配：
        - 唯一匹配 → 自动归属
        - 多 REQ 复用同接口（如 GET /contract/{id} 用于编辑回显 + 明细抽屉）
          → 按调用上下文推断（编辑按钮触发 / 明细按钮触发）
        - 仍无法决定 → 加入交互清单让用户裁决
Step 4: 输出「REQ ↔ 接口 ↔ 调用处映射表」给用户确认
```

**约束**：

- REQ 编号严格继承自 01，**Skill 不自造 REQ 编号**（与 `prd-git-commit` 一致）。
- 01 中已废弃或已删除的 REQ 不出现在详设 4.1.4 中，但证据表记录"代码仍引用废弃 REQ"作为警告。

## 7. 输出契约

### 7.1 文件清单

| 输出     | 路径                                                   | 说明                           |
| -------- | ------------------------------------------------------ | ------------------------------ |
| 详设正文 | `Prds/Vx.y.z/02-详细设计文档.md`                       | 按模板生成；触发时覆盖旧文件   |
| 备份     | `Prds/Vx.y.z/02-详细设计文档.md.bak.{YYYYMMDD-HHmmss}` | 覆盖前自动备份                 |
| 证据表   | `Prds/Vx.y.z/02-详细设计文档.证据表.md`                | 独立文件，详设本体的可追溯附录 |

### 7.2 证据表结构

证据表模板见 `evidence-template.md`，固定 6 节：

1. 生成元信息（时间、Skill 版本、输入文件 hash、模板版本）
2. REQ 来源映射表（REQ 编号 / 章节 / 内容来源 / 代码引用 / 备注）
3. 需求 ↔ 代码偏差清单（REQ 编号 / 字段或规则 / 需求版本 / 代码实际版本 / 偏离原因推断）
4. 逻辑补充清单 `[DESIGN-SUPPLEMENT]`（REQ 编号 / 章节 / 补充内容 / 补充依据）
5. 一致性自检报告（附录 A 14 项 + 双向检查）
6. 关联文件清单（用户已确认）

### 7.3 详设正文约束

- 详设正文严格按 `Templates/deliverables/02-详细设计文档.md` 结构，**不引入新章节**。
- 正文**不带行内代码引用**（保持与现有 `Prds/V1.6.1/02-详细设计文档.md` 一致的清爽度）。
- 仅在 `[DESIGN-SUPPLEMENT]` 处用行内标签标注补充点。
- 全文禁止 "待定/TBD/暂略" 等占位符（与模板附录 A 第 14 项一致）。

## 8. 质量门（软门）

### 8.1 自检流程

1. 跑模板附录 A 的 14 项一致性检查（清单见 `extraction-checklist.md` §4）。
2. 跑额外的"需求 ↔ 代码双向一致性检查"（清单见 `extraction-checklist.md` §5）：
   - 需求有 REQ 但代码无任何相关实现 → 警告"代码未实现"
   - 代码有调用但需求未列入该 REQ 的接口清单 → 警告"代码超范围"
3. 跑"增量版本失效概念检查"：对比新旧版本 01，识别旧基线 02 中引用的已失效概念，确认是否已删除或调整；未处理的警告项写入证据表第 5 节。
4. 跑"枚举值基线优先检查"：逐个枚举表/状态映射表核对正文行项与态数是否与 01 一致；若 01 明确「删除 X/新增 Y」而正文仍含 X 或态数不符，记为警告并回写正文为 01 版本，差异进证据表第 3 节。
5. 蚝报项以列表形式写入证据表第 5 节。
6. **不阻塞产出** — 用户根据警告决定是否重生或手工修正。

### 8.2 退出条件

- 详设正文与证据表均已落盘 → 视为本次运行成功退出。
- 警告项不阻塞退出，但必须在证据表第 5 节可见。

## 9. 边界与不做

- ❌ 不修改 `01-需求文档.md`（偏差只在证据表记录，由人走变更流程）。
- ❌ 不盲目继承旧版本已失效的概念（增量版本生成时，必须识别并处理旧基线中引用的已失效概念，如"配额行/第 X 行/添加一行"）。
- ❌ 不修改 `02b-后台文档.md`。
- ❌ 不修改前端代码。
- ❌ 不替代 `testcase-generation` 生成 `03-测试用例文档.md`。
- ❌ 不生成 Playwright/UI 自动化脚本（由 `ui-automation-bootstrap` / `playwright-test-implementation` 负责）。
- ❌ 不处理图片素材（详设一般不含图）。
- ❌ 不在未显式触发时覆盖既有 `02`。

| 风险                                          | 缓解                                                                              |
