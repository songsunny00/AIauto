# version-archive

## 1. 目标

由版本负责人 / PM 角色在版本测试结束后触发，把版本目录下的正式交付物（01/02/03）回写为模块基线全量文档，并完成索引维护和一致性校验。

本 skill 遵循 `docs/需求开发测试一体化-落地蓝图版.md` 的目录体系、编号规则与变更记录约定，遵循 `docs/superpowers/specs/2026-08-13-version-archive-design.md` 的设计规范。

## 2. 触发条件

当用户指令包含以下意图时激活本 skill：

- **归档 V1.6.1 / 版本归档 / 回写基线 / 版本收尾归档**
- **archive V1.6.1**
- **归档 V1.6.1 --full**（强制全量覆盖模式）

缺少版本号时不推断"当前版本"，要求用户明确指定。

## 3. 前置检查

执行任何操作前，先完成以下检查：

### 3.1 版本目录检查

确认 `Prds/{版本号}/` 目录存在，且包含以下必要文件：

- `01-需求文档.md`（必须存在）
- `02-详细设计文档.md`（必须存在）
- `03-测试用例文档.md`（必须存在）

若任一文件缺失：停止并提示用户"版本目录 {路径} 缺少 {文件名}，请先补充"。

### 3.2 Git 环境检查

```powershell
git rev-parse --is-inside-work-tree
git config user.name
```

- 若不在 Git 仓库中：停止并提示用户。
- 记录 `user.name` 作为后续 INDEX.md 回写历史的"回写人"。

### 3.3 CHANGELOG 检查

读取 `Prds/CHANGELOG.md`，确认目标版本记录存在。若不存在：停止并提示"CHANGELOG 中未找到版本 {版本号} 的记录，请先在版本流程中创建"。

## 4. 模块识别与路径映射

### 4.1 识别本次版本涉及的模块

从以下来源交叉确认：

1. `01-需求文档.md` 中 REQ 清单表的 REQ 编号（提取所有 `{L1}-{L2}` 组合）
2. `05-变更记录.md` 中的模块列
3. 版本目录路径本身

**REQ 编号到物理路径的映射规则**：

REQ 编号格式为 `REQ-{L1}-{L2}-{L3}-{NNN}`（如 `REQ-CONFIG-BILLCFG-FORM-001`）。从中提取 `{L1}` 和 `{L2}`，在 `Prds/` 下按 `英文编码-中文名称` 命名规则定位物理路径：

```text
REQ-CONFIG-BILLCFG-xxx → Prds/CONFIG-配置中心/BILLCFG-商业化计费配置/
```

一级模块（L1）对应 `Prds/` 下的第一级目录，叶子模块（L2）对应一级模块下的第二级目录。L3 是功能域，不对应目录层级。

### 4.2 多模块版本处理

一份版本目录下的 01/02/03 可能包含多个模块的需求。skill 按 REQ 编号中的 `{L1}-{L2}` 将文档内容拆分到各自模块的基线目录：

1. 从 01 的 REQ 清单表提取所有 `{L1}-{L2}` 组合，去重后得到模块列表
2. 按模块拆分文档内容：
   - REQ 关联表格行：按 REQ 编号的 `{L1}-{L2}` 归属到对应模块
   - REQ 详情区块：按区块标题中的 REQ 编号归属到对应模块
   - 非 REQ 区块内容：不拆分到任何模块基线，留在版本目录
3. 逐模块独立判断归档模式（见第 6 节）
4. 逐模块独立回写

### 4.3 模块目录不存在时的处理

若目标模块目录不存在，skill 停止归档并提示用户按 `英文编码-中文名称` 命名规则手动创建目录后重新触发。skill 不自动创建模块目录。提示信息列出所有缺失的模块目录。

## 5. 一致性校验

校验在回写前执行，任一失败即停止。校验按模块分别执行：

| 校验项 | 规则 | 失败处理 |
|---|---|---|
| REQ 编号格式 | 匹配 `REQ-{L1}-{L2}-{L3}-{NNN}` | 阻断，输出不合规编号清单 |
| REQ 操作类型 | 01 REQ 清单表中已有「需求类型」列，值为 新增/修改/删除 之一 | 阻断，输出缺失或非法需求类型的 REQ 清单 |
| 需求类型一致性 | 01 REQ 清单表中的需求类型与 REQ 详情区块元信息表中的需求类型一致 | 阻断，输出不一致的 REQ 清单 |
| REQ 在 02 有对应 | 01 中操作类型为新增/修改的每个 REQ 在 02 详设中能找到引用 | 阻断，输出缺失清单 |
| REQ 在 03 有对应 | 01 中操作类型为新增/修改的每个 REQ 在 03 用例中能找到覆盖 | 阻断，输出未覆盖清单 |
| 测试编号格式 | 匹配 `FT/IT/PT/ET-{L1}-{L2}-{功能域}-{NNN}` | 阻断，输出不合规编号清单 |

**删除操作的校验豁免**：操作类型为"删除"的 REQ 不校验 02/03 对应。但 skill 需校验该 REQ 在对应模块的基线 01 中确实存在，否则提示"REQ-xxx 标记为删除但基线中不存在，请确认"。

校验方式：文本检索（grep 风格），不要求语义理解。只要编号字符串在目标文档中出现即视为"有对应"。

校验通过后进入第 6 节归档模式判断。

## 6. 归档模式判断

skill 根据每个模块基线目录的文件状态**分别**判断归档模式。一份版本目录下的 01/02/03 含多个模块时，不同模块可能走不同模式。用户也可通过 `--full` 强制所有模块走全量覆盖。

### 6.1 判断逻辑（按模块分别判断）

```text
用户指定 --full？
├─ 是 → 所有模块走全量覆盖模式
└─ 否 → 逐模块检查基线目录是否有 01/02/03 文件
   ├─ 没有（目录不存在或为空） → 该模块走首次沉淀模式（全量覆盖）
   └─ 有 → 该模块走增量合并模式（按 REQ 区块合并）
```

### 6.2 两种模式的差异

| 维度 | 首次沉淀模式 | 增量合并模式 |
|---|---|---|
| 触发条件 | 模块基线目录无 01/02/03 文件 | 模块基线目录已有 01/02/03 文件 |
| 回写方式 | 按模块拆分后全量覆盖 | 按 REQ 编号区块合并（新增/修改/删除） |
| 用户确认 | 不需要（无歧义） | 需要（不确定项交用户确认，见 8.7 节） |
| 版本标记头模式 | `首次沉淀` | `增量合并` |

## 7. 首次沉淀模式（全量覆盖）

**触发条件**：模块基线目录下不存在 01/02/03 文件，或用户指定 `--full` 参数。

### 7.1 文档内容分类与处理

文档内容分为四类，处理方式不同：

| 内容分类 | 包含内容 | 处理方式 |
|---|---|---|
| **REQ 关联表格** | 01 功能清单表、01 验收标准表、01 追踪矩阵、02 需求实现清单表、02 接口清单表、03 用例表 | 保留表头结构，按 REQ 编号的 `{L1}-{L2}` 归属提取该模块的行 |
| **REQ 详情区块** | 01 的 `#### REQ-xxx` 区块、02 的 `##### REQ-xxx` 区块 | 按 REQ 编号归属提取对应模块的区块 |
| **模块级公共内容** | 02 技术架构概述、02 页面路由与菜单入口、03 测试环境说明等 | 纳入基线（首次沉淀时基线为空，需要这些内容提供架构上下文） |
| **版本级公共内容** | 01 项目概述、01 本期范围与不做事项、01 角色与权限等 | **不纳入任何模块基线**，留在版本目录作为版本快照 |

### 7.2 用户确认

首次沉淀默认不需要用户确认。但如果 skill 无法判断某段内容是"模块级公共内容"还是"版本级公共内容"，触发 8.7 节的用户确认流程。

### 7.3 `--full` 模式

忽略模块基线目录已有文件，按上述拆分逻辑全量覆盖。

## 8. 增量合并模式（按 REQ 编号区块合并）

**触发条件**：模块基线目录下已存在 01/02/03 文件，且用户未指定 `--full`。

### 8.1 REQ 操作类型识别

从 01 的 REQ 清单表中已有的「需求类型」列读取：
- `新增`：基线中不存在该 REQ，需要添加
- `修改`：基线中已存在该 REQ，需要替换区块
- `删除`：基线中已存在该 REQ，需要移除区块

### 8.2 REQ 区块锚点

| 文档 | 区块锚点 | 示例 |
|---|---|---|
| `01-需求文档.md` | `#### REQ-{L1}-{L2}-{L3}-{NNN}` 四级标题 | `#### REQ-CONFIG-BILLCFG-LIST-001 列表查询与默认加载` |
| `02-详细设计文档.md` | `##### REQ-{L1}-{L2}-{L3}-{NNN}` 五级标题 | `##### 4.1.4.1 REQ-CONFIG-BILLCFG-LIST-001 列表查询与默认加载` |
| `03-测试用例文档.md` | 用例表中 `REQ-xxx` 列的关联行 | `FT-BILLCFG-LIST-001` 行关联 `REQ-CONFIG-BILLCFG-LIST-001` |

### 8.3 合并操作分类

| 操作类型 | REQ 在基线中的状态 | 合并操作 | 说明 |
|---|---|---|---|
| 新增 | 不存在 | **新增区块** | 将增量文档中该 REQ 的完整区块插入基线文档对应位置 |
| 新增 | 已存在 | **阻断** | 输出"REQ-xxx 标记为新增但基线中已存在，请确认操作类型应为修改" |
| 修改 | 已存在 | **替换区块** | 用增量文档中该 REQ 的区块替换基线文档中的同名区块 |
| 修改 | 不存在 | **阻断** | 输出"REQ-xxx 标记为修改但基线中不存在，请确认操作类型应为新增" |
| 删除 | 已存在 | **删除区块** | 从基线文档中移除该 REQ 的清单行、详情区块和相关测试用例 |
| 删除 | 不存在 | **阻断** | 输出"REQ-xxx 标记为删除但基线中不存在，请确认" |

### 8.4 各文档的具体合并方式

**01-需求文档.md 合并**：
1. **功能清单表**：新增→插入行；修改→替换同编号行；删除→移除行
2. **REQ 详情区块**（按 `#### REQ-xxx` 标题定位）：新增→插入到对应模块区块末尾；修改→替换区块内容；删除→移除整个区块
3. **验收标准表**（按验收点编号去重）：新增/修改→增量覆盖同编号行；删除→移除关联该 REQ 的验收点行
4. **追踪矩阵**：同功能清单表逻辑
5. **非 REQ 区块内容**：保留基线版本，不合并

**02-详细设计文档.md 合并**：
1. **需求实现清单表**：同 01 功能清单表逻辑
2. **REQ 详情区块**（按 `##### REQ-xxx` 标题定位）：同 01 详情区块逻辑
3. **接口清单表**（按接口路径去重）：新增/修改→增量覆盖同路径行；删除→从"关联需求编号"列解析该接口关联的所有 REQ，若该列中除被删除 REQ 外还包含其他未删除的 REQ，仅从该列移除被删除的 REQ 编号；若所有 REQ 均已被删除，则移除该接口行
4. **非 REQ 区块内容**：保留基线版本

**03-测试用例文档.md 合并**：
1. **用例表**（按测试编号处理）：新增/修改→增量覆盖同编号行；删除→移除关联被删除 REQ 的所有测试用例行
2. **非用例区块内容**：保留基线版本

### 8.5 合并后的区块排序

- REQ 详情区块按 REQ 编号自然序排列（LIST-001, LIST-002, LIST-003, FORM-001, FORM-002, DETAIL-001）
- 测试用例按测试编号自然序排列

### 8.6 删除操作的连带处理

删除一个 REQ 时，需要连带处理：
- 01：功能清单表行 + 详情区块 + 验收标准表行 + 追踪矩阵行
- 02：需求实现清单表行 + 详情区块 + 接口清单表行（从"关联需求编号"列解析，若该接口仍被其他未删除 REQ 引用则仅移除该 REQ 编号，否则移除整行）
- 03：关联该 REQ 的所有测试用例行

skill 输出删除清单，在合并预览中明确展示"将删除 REQ-xxx 及其关联的 {N} 条测试用例、{M} 个验收点"，经用户确认后执行。

### 8.7 不确定项交用户确认

遵循"不确定时交用户确认"原则：skill 输出自己的判断和理由，由用户确认后再执行。

**需要用户确认的场景**：

| 场景 | skill 的判断逻辑 | 用户确认方式 |
|---|---|---|
| 非 REQ 区块内容在增量文档中有变化 | 默认判断"保留基线版本，不合并"，但输出变化摘要 | "检测到非 REQ 区块有变化，默认保留基线版本，变化摘要：{摘要}。是否需要合并？[Y/N]" |
| REQ 区块内除了 REQ 编号相关内容外还有其他变动 | 默认判断"按 REQ 区块整体替换"，但提示用户注意 | "REQ-xxx 区块将整体替换，请注意该区块内还有以下非 REQ 内容变动：{变动清单}" |
| 增量文档中出现基线中不存在的新的表格/章节 | skill 无法判断是新增模块级内容还是版本临时内容 | "增量文档中出现新章节：{章节标题}，skill 无法判断是否应纳入基线。是否合并？[Y/N]" |

**确认流程**：
1. skill 完成所有自动判断后，汇总需要确认的项
2. 一次性输出确认清单（不逐项打断用户）
3. 用户逐项回复 Y/N，或统一回复"全部保留基线"/"全部按增量"
4. 用户确认后，skill 按确认结果执行合并

### 8.8 合并结果预览

合并写入前，skill 输出合并预览摘要：
- 每份文档的新增 REQ 区块数、替换 REQ 区块数、删除 REQ 区块数
- 非 REQ 区块的保留/合并决策
- 用户确认项的处理结果

用户确认预览后，skill 才写入基线文件。

### 8.9 合并冲突处理

| 场景 | 处理 |
|---|---|
| 增量文档中某 REQ 区块无法定位到完整边界 | 阻断，输出"REQ-xxx 区块边界无法识别，请检查文档格式" |
| 基线文档中某 REQ 区块格式异常 | 阻断，输出"基线文档中 REQ-xxx 区块格式异常，建议使用 --full 全量覆盖重置基线" |
| 删除 REQ 时基线中关联的测试用例/验收点无法定位 | 阻断，输出"REQ-xxx 删除时无法定位关联的 {测试用例/验收点}，请检查基线文档完整性" |

## 9. 版本标记头

无论哪种模式，回写后在文档原始标题行之前更新 HTML 注释标记，不影响 Markdown 渲染：

```text
<!-- 最后回写版本: V1.6.1 | 回写日期: 2026-08-13 | 来源: Prds/V1.6.1/01-需求文档.md | 模式: 首次沉淀/增量合并 -->
# 原始标题...
```

**标记头覆盖规则**：若文档头部已存在 `<!-- 最后回写版本:` 标记，替换为最新版本标记，不累积多条。

## 10. INDEX.md 维护

模块基线目录下的 `INDEX.md` 记录该模块的文档清单和回写状态：

```markdown
# {模块名称} 基线索引

## 文档清单

| 文档 | 文件名 | 最后回写版本 | 回写日期 | 来源 |
|---|---|---|---|---|
| 需求文档 | 01-需求文档.md | V1.6.1 | 2026-08-13 | Prds/V1.6.1/01-需求文档.md |
| 详细设计文档 | 02-详细设计文档.md | V1.6.1 | 2026-08-13 | Prds/V1.6.1/02-详细设计文档.md |
| 测试用例文档 | 03-测试用例文档.md | V1.6.1 | 2026-08-13 | Prds/V1.6.1/03-测试用例文档.md |

## 回写历史

| 版本 | 回写日期 | 回写人 | 说明 |
|---|---|---|---|
| V1.6.1 | 2026-08-13 | {git user.name} | 首次基线沉淀 |
```

**说明**：
- 首次沉淀：回写历史说明为"首次基线沉淀"
- 增量合并：回写历史说明为"增量合并：新增 {N} 个 REQ，修改 {M} 个 REQ，删除 {K} 个 REQ"
- 即使某模块本次仅有删除操作，INDEX.md 的最后回写版本也需更新为目标版本号

## 11. CHANGELOG 更新

更新 `Prds/CHANGELOG.md` 中目标版本记录的"主文档回写状态"列：

- 从 `待回写` 改为 `已回写`
- 不删除行、不修改其他列、不新增行
- 若目标版本有多行记录，全部更新为 `已回写`

**边界场景处理**：

| 场景 | 处理 |
|---|---|
| CHANGELOG 中不存在目标版本行 | 停止归档，提示"CHANGELOG 中未找到版本 {版本号} 的记录" |
| 目标版本行已经是 `已回写` | 幂等成功，跳过 CHANGELOG 更新但继续执行其余步骤 |
| 目标版本行为非 `待回写` 且非 `已回写` | 停止归档，提示"CHANGELOG 中 {版本号} 的主文档回写状态为 {当前值}，请人工确认" |

## 12. 归档报告

操作完成后，向用户返回归档报告：

```
## 归档结果

[版本信息]
- 版本号：V1.6.1
- 版本目录：Prds/V1.6.1/

[模块处理]
- 涉及模块：CONFIG/BILLCFG 商业化计费配置
- 归档模式：首次沉淀 / 增量合并
- （增量合并时）REQ 变更：新增 {N} 个，修改 {M} 个，删除 {K} 个

[一致性校验]
```

- 不自动推断当前版本
