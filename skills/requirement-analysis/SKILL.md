# requirement-analysis

## 1. 目标

把需求相关文档中的关键信息收敛为后续设计、开发、测试都能直接使用的结构化输入。

## 2. 适用输入

优先读取：

- `01-需求文档.md`
- `01b-数据流转设计.md`（如有）
- `01c-原型文档.md`（如有）
- `02-详细设计文档.md`（如已有）
- 模块 `TRACE.yaml`

## 3. 期望输出

至少输出：

1. 目标模块路径
2. `REQ-*` 清单
3. 每个 `REQ` 的需求摘要
4. 验收点 / 关键业务规则
5. 受影响资产清单
6. 缺失信息清单

## 4. 使用步骤

1. 先识别模块路径与目录编码。
2. 再提取或校验 `REQ-*` 编号。
3. 汇总每个 `REQ` 的目标、约束、验收条件。
4. 标记是否受版本 `01`、`01b/01c` 影响。
5. 给出后续需要传给 `02`、`03`、自动化骨架的最小信息集。

## 5. 输出格式建议

```markdown
## 模块信息
- 路径：
- 编码：

## REQ 清单
- REQ-...：

## 验收点
- REQ-...：

## 受影响资产
- 文档：
- 页面：
- API：
- 测试：

## 缺失信息
- 
```

## 6. 约束

- 不自造 `REQ` 编号。
- 若缺少验收条件，要显式指出。
- 若版本目录 `01` 与模块 `01` 的表达不一致，要显式指出。
- 输出优先服务后续 `02/03/UI/API 自动化`，不要写成泛泛摘要。
