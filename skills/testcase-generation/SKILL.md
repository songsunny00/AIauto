# testcase-generation

## 1. 目标

把 `01-需求文档.md` 与 `02-详细设计文档.md` 转成 `03-测试用例文档.md`，并确保：

1. **以 01 为基准** — `01-需求文档.md` 是测试用例的唯一基准，所有测试场景必须从 01 定义的功能点、字段、业务规则中派生；02 仅补充实现细节与文案，不扩展 01 未定义的场景；后端实现细节（字段恒为 null、展示"—"等）不继承到 03。
2. **功能范围一致** — 测试用例严格覆盖上游文档定义的功能点，不凭空增加上游未提及的功能（如按钮置灰、隐藏交互等须在 01/02 中有定义）。
3. **文案精确匹配** — 测试用例中的提示文案、校验消息、成功/失败 Toast 与 `02-详细设计文档.md` 严格逐字一致。
4. **表述专业且可读** — 面向多角色（产品、开发、测试、项目开发管理人），用通用业务术语描述状态与操作，技术枚举值在备注或括号中注明。
5. **正常场景优先** — 测试用例以正常业务场景为主，异常/边界场景仅覆盖 01/02 明确定义的规则；不引入后端实现细节、不臆测、不盲目继承失效概念。

## 2. 适用输入

| 输入                  | 必需性 | 用途                                                                          |
| --------------------- | ------ | ----------------------------------------------------------------------------- |
| `01-需求文档.md`      | 必需   | REQ 编号、功能范围、验收口径                                                  |
| `02-详细设计文档.md`  | 必需   | 接口路径、校验文案、状态映射、异常处理、**前端路由与菜单路径（第 2.3 节）**   |
| `02b-后台文档.md`     | 推荐   | 接口参数、错误码、retInfo 原文；**缺失影响接口用例（IT/ET）的完整度与准确度** |
| `01b-数据流转设计.md` | 如有   | 数据流转参考                                                                  |
| `01c-原型文档.md`     | 如有   | 交互细节参考                                                                  |

**输入优先级**：`01` 定义功能范围 → `02` 定义实现细节与文案 → `02b`（如有）定义接口契约。三者冲突时，按 `detail-design-bootstrap` 的真源裁决策略处理（需求优先 → 代码 → 补充）。

### 🔴 CHECKPOINT 0 · 输入完备性（开始前必须执行）

核对必需输入：`01-需求文档.md`、`02-详细设计文档.md`；核对推荐输入：`02b-后台文档.md`。

- 必需输入任一缺失 → **🛑 STOP**：列出缺失文档清单，向用户询问实际路径或确认是否继续；用户明确给出路径前不进入步骤 1。
- `02b` 缺失 → 不阻塞：向用户提示「接口用例（IT/ET）完整度与准确度将受影响」，确认后继续；IT/ET 相关处理按 §4.1 失败分支表执行。
- 必需输入齐全但找不到 `01b-数据流转设计.md` / `01c-原型文档.md` 等可选输入 → 正常继续，在 03 文档开头标注「未参考 XX（未提供）」。
- 禁止在输入缺失时凭旧版基线 03、记忆或臆测代写需求口径——宁可停，不可编。

## 3. 期望输出

`03-测试用例文档.md`，包含：

1. 测试范围与不测项（对齐 01 边界）
2. 测试环境与数据准备（**须含前端 URL、前端路由、前端入口（菜单路径）、后端 URL、测试账号矩阵、数据初始化要求**；路由/菜单取自 `02` 第 2.3 节）
3. 功能用例 `FT-*`（含操作步骤、预期结果、文案精确匹配；操作步骤与预期结果编号严格 1:1 对应；含「适用版本」列）
4. 接口用例 `IT-*`（含请求参数、正常/异常返回、边界值、适用版本列）
5. 权限用例 `PT-*`（含"直接路由访问"校验，路由取自第 2.1 环境信息；含「适用版本」列）
6. 异常分支用例 `ET-*`（**分散归入功能/接口用例表格，不再单独立章**；编号带功能域粒度 `ET-{MODULE}-{FEATURE}-{NNN}`，与所在 FT 表格域前缀一致，如 `ET-BILLCFG-LIST-001`；跨域异常用 `ET-{MODULE}-X-{NNN}`）
7. 回归测试清单
8. 需求与测试用例追踪矩阵
9. 一致性检查清单

## 4. 使用步骤

1. 读取 `01` 抽取 REQ 清单 + 每个 REQ 的功能点、字段表、业务规则与验收口径；**以 01 为基准识别正常测试场景**，每个场景必须能追溯到 01 的具体功能点/字段/规则。
2. 读取 `02` 抽取每个 REQ 的：接口清单、校验文案（逐字）、状态映射表、异常处理表；并读取 `02` 第 2.3 节的前端路由（如 `/config/billingConfig`）与菜单路径（如 `配置中心 / 商业化计费配置`），用于 03 第 2.1 环境信息（前端路由 / 前端入口）与权限用例（直接路由访问校验）。
3. 读取 `02b`（如有）抽取错误码与 retInfo 原文；缺失时按 §4.1 失败分支表降级处理。
4. 将用户路径类场景拆成 `FT-*`，每个 FT 标记对应 REQ；**操作步骤与预期结果编号严格 1:1 对应**（见 §10 约束）。
5. 将接口规则、边界、权限、状态流场景拆成 `IT-*`。

**🔴 CHECKPOINT 1 · 场景清单确认（步骤 5 完成、步骤 6 校验展开前）**

将 `FT-*` / `IT-*` / `ET-*` 用例清单（编号 + 一句话场景 + 关联 REQ）展示给用户确认覆盖范围，用户确认前不展开正文编写。若为增量版本，须同时列出**拟删除/调整的失效概念用例清单**（依据 §5.3 失效概念识别），删除或改写用户基线内容前必须经用户确认。

6. 对每个 FT/IT 执行 §5 上游映射校验。
7. 对每个 FT/IT 的预期文案执行 §6 文案规范化。
8. 对每个 FT/IT 的状态/枚举值执行 §7 术语转换。
9. 对全文执行 §8 多角色可读性评审。
10. 输出可直接落入 `03-测试用例文档.md` 的结构化内容 + 一致性检查清单；**功能/接口/权限三类用例表均填「适用版本」列**（当前版本号）。

### 4.1 执行失败分支表

步骤执行中遇到以下情况，按「一线修复 → 仍失败兜底」处理，禁止跳过或静默编造：

| 触发条件                            | 一线修复                                                                                                          | 仍失败兜底                                          |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| `02b` 整体缺失（推荐输入未提供）    | IT 仅按 02 接口清单生成；ET 改按 01 业务规则描述期望表现，不编造 retInfo；03 文档开头标注「未参考 02b（未提供）」 | 映射校验报告标 ⚠️ 并提示用户补 02b                  |
| 01 缺 REQ 编号或字段表结构异常      | 按标题层级推断功能点并自行编号（标注「推断编号」）                                                                | 🛑 停止，列出无法解析的章节请用户澄清               |
| 02 缺某 REQ 的接口定义（IT 无来源） | 该 REQ 仅生成 FT；IT 标注「02 未定义接口，暂缓」                                                                  | 映射校验报告标 ⚠️ 并提示用户补 02                   |
| 02/02b 缺某异常的错误码或 retInfo   | ET 用例改按 01 业务规则描述期望表现，不编造 retInfo                                                               | 01 亦无规则可依则删除该 ET 并在报告记录             |
| 校验提示等文案 01 未定义            | 从 02 异常处理表逐字提取并在文案对照表标注来源（§6.1）                                                            | 02 亦未定义则该步骤不断言具体文案，标「文案未定义」 |
| 当前版本号未知（适用版本列）        | 从 Prds 版本目录名（如 `V1.6.3`）或 01 文档头推断                                                                 | 推断不出 → 询问用户，禁止猜测填入                   |

## 5. 上游文档与测试用例内容映射校验规则

### 5.1 功能范围校验

每个测试用例必须能追溯到上游文档的具体功能点：

| 校验项        | 规则                                                              | 不通过时处理          |
| ------------- | ----------------------------------------------------------------- | --------------------- |
| REQ 归属      | 每个 FT/IT 必须关联一个 01 中存在的 REQ 编号                      | 删除该用例或补 01     |
| 功能点边界    | FT 测试的操作/预期必须落在 01 或 02 定义的功能范围内              | 删除超范围部分        |
| 按钮置灰/隐藏 | 仅当 02 明确描述了置灰/隐藏条件时才可测试；禁止凭"应该置灰"的推断 | 标注"02 未定义"并删除 |
| 接口覆盖      | IT 测试的接口必须在 02 第 5 章接口清单中                          | 删除或补 02           |
| 异常分支      | ET 测试的异常必须在 02 异常处理表或 02b 错误码中                  | 删除或补 02/02b       |

### 5.2 校验输出

生成测试用例后，输出一份《映射校验报告》附在 03 文档附录，格式：

```markdown
## 附录 C. 上游映射校验报告

| 用例编号 | 关联 REQ | 功能点来源(01行号) | 文案来源(02行号) | 接口来源(02b行号) | 校验结果                           |
| -------- | -------- | ------------------ | ---------------- | ----------------- | ---------------------------------- |
| FT-...   | REQ-...  | 01:L102            | 02:L411          | -                 | ✅ 通过                            |
| FT-...   | REQ-...  | 01:L237            | -                | -                 | ⚠️ 02 未定义文案，已按 01 口径编写 |
```

### 5.3 常见越界模式（禁止）

- **推断式置灰**：02 未描述某按钮置灰条件，但测试用例写"XX 按钮应置灰"。
- **臆测式校验**：02 未定义某字段校验规则，但测试用例编造校验提示文案。
- **超范围接口**：01/02 未纳入某接口，但 IT 用例测试了该接口。
- **不存在状态**：02 状态映射表中无某状态值，但测试用例使用了该状态。
- **枚举术语/标点偏离 01**：01 已明确给出枚举值或文案（如授权状态"启用/禁用"、Toast"保存成功"），但测试用例使用了 02/代码的变形术语（"启用中"/"已禁用"）或添加了 01 没有的标点（"保存成功！"）；必须以 **01 原文（含标点）** 为准，02 偏差不继承。
- **技术标识符裸用**：功能/异常用例中使用了前端封装的 API 函数名（如 `getOrgOptionsApi`）或后端技术字段名（如 `snapshotBefore/After`），而非自然语言描述（如"机构选项加载接口"/"历史变更快照"）；技术接口路径、函数名、字段名仅在 IT 用例中使用。
- **后端提示误置**：场景实际触发前端表单必填校验（必填项为空），但预期结果使用了后端 retInfo 校验提示（如"纯存储合同必须开通增值存储"）；后端校验提示仅在数据合法提交后触发的场景中使用。
- **后端实现细节泄漏**：测试用例中描述了后端字段恒为 null、前端展示"—"等实现限制（如"本期'增值存储已使用'因后端 `storageUsedTb` 恒为 null，展示'—'"），而非按需求描述预期行为；测试用例应基于需求定义的功能点编写，预期结果描述用户可见行为，不引入后端实现细节。
- **盲目继承失效概念/场景**：增量版本生成时，旧基线 02/03 中引用了新版 01 已删除/变更的概念或场景（如"配额行/添加一行/第 X 行"被删除，或 01 明确"有机构即有合同，不存在为 0 的情况"但仍生成"无合同的租户"用例），但新版 02/03 仍盲目继承相关校验文案/用例/异常处理，未做删除或调整。

### 5.4 环境信息与路由一致性校验

03 第 2.1 环境信息的路由/菜单必须与 `02` 第 2.3 节逐字一致，否则 UI 自动化按错误路由访问会导致整页失败（如停留在登录页），与脚本元素定位无关：

| 校验项       | 规则                                                           | 不通过时处理     |
| ------------ | -------------------------------------------------------------- | ---------------- |
| 前端路由来源 | 03「前端路由」必须等于 `02` 第 2.3 节的路由值                  | 修正 03 路由     |
| 菜单路径来源 | 03「前端入口」菜单路径须等于 `02` 第 2.3 节的菜单路径          | 修正菜单路径     |
| 路由引用统一 | 权限用例"直接路由访问"所用路由须等于 03 环境信息的「前端路由」 | 统一引用环境信息 |

### 5.5 以 01 为基准的场景识别规则（核心原则）

**功能测试用例（FT）必须以 01 为基准生成**，02 仅补充实现细节与文案，不扩展 01 未定义的场景：

| 校验项       | 规则                                                            | 不通过时处理                       |
| ------------ | --------------------------------------------------------------- | ---------------------------------- |
| 场景来源     | 每个 FT 场景必须能追溯到 01 的具体功能点/字段/业务规则          | 删除该场景或补 01                  |
| 字段完整性   | FT 预期结果中涉及的表/区块字段必须与 01 的字段表一致            | 补充 01 中定义的字段               |
| 后端实现隔离 | FT 预期结果禁止描述后端实现细节（字段恒为 null、展示"—"等）     | 删除后端实现描述，改按 01 需求描述 |
| 正常场景优先 | FT 以正常业务场景为主，异常/边界场景仅覆盖 01/02 明确定义的规则 | 删除 01/02 未定义的异常场景        |
| 增量版本识别 | 增量版本生成时，对比新旧 01 识别删除/变更的概念，不盲目继承     | 删除或调整失效概念相关用例         |

**场景识别流程**：

1. 从 01 的 REQ 字段表抽取每个表/区块的完整字段列表
2. 从 01 的业务规则抽取校验规则、显隐规则、联动规则
3. 基于 01 的字段和规则生成正常测试场景（填写成功、必填校验、格式校验、显隐切换、联动逻辑）
4. 异常/边界场景仅从 01/02 明确定义的规则中派生，不臆测
5. 每个 FT 的预期结果中，字段列表必须与 01 的字段表逐字一致

## 6. 文案提取与规范化输出

### 6.1 文案真源链

测试用例中的所有预期文案（校验提示、Toast、错误消息）必须从 02 逐字提取，**禁止改写**：

1. **表单校验文案** ← 02 的"异常处理与已知约束"表第 4 列（提示文案）
2. **Toast 成功文案** ← 02 的操作步骤中"提示 XX 成功"的原文
3. **接口错误 retInfo** ← 02b 的错误码定义表 retInfo 原文
4. **状态标签文案** ← 02 的状态映射表第 1 列（业务名称）
5. **01 优先于 02（文案与标点）** ← 当 01 已明确给出某文案（如「新增成功」「保存成功」），03 逐字使用 **01 原文（含标点）**；02 若在此基础上变形（多出「！」/「。」标点、术语改为"启用中"/"已禁用"等），**以 01 为准，02 偏差不继承**。01 未给的文案（如部分校验提示）才退化为从 02 逐字提取，并在文案对照表标注来源。

### 6.2 文案对照表

生成测试用例时，同步输出一份《文案对照表》确保逐字一致：

```markdown
## 附录 D. 文案对照表

| 文案用途         | 02 原文                              | 03 用例编号              | 03 中的文案                     | 一致性                          |
| ---------------- | ------------------------------------ | ------------------------ | ------------------------------- | ------------------------------- |
| 合同编号格式校验 | 合同编号仅支持字母、数字、-或\_      | FT-FORM-003, ET-FORM-004 | 合同编号仅支持字母、数字、-或\_ | ✅                              |
| 配额行项目必填   | 第 `<行号>` 行检测项目及产品套餐必填 | FT-FORM-009              | 第 X 行检测项目及产品套餐必填   | ✅（`<行号>`→`X` 为占位符替换） |
```

### 6.3 占位符替换规则

02 中的 `<行号>` 等占位符在 03 中可替换为具体示例值（如 `X`、`1`、`2`），但文案其余部分必须逐字一致。替换时在文案对照表中标注。

## 7. 专业术语与通用表述转换对照表

### 7.1 转换原则

- **FT（功能用例）**：面向产品/测试/项目开发管理人，**必须使用通用业务术语**，技术枚举值在括号中注明。
- **IT（接口用例）**：面向开发/联调，**保留技术枚举值**作为请求参数，可在备注中注明业务含义。
- **ET（异常用例）**：混合 — 触发方式用技术值（精确），期望表现用业务术语（可读）。
- **PT（权限用例）**：用业务角色描述，技术权限标识在括号中注明。

### 7.2 状态枚举转换对照表

测试用例中使用的状态值转换规则（以商业化计费配置模块为例，其他模块按 02 状态映射表类推）。**业务名称与枚举项必须以当前版本 01 为准**（如 V1.6.3 授权状态为「启用/禁用」、合同状态 4 态无「已停用」）；02 状态映射表若与 01 不一致（术语变形如"启用中"vs"启用"、多出已删枚举如"已停用"），**以 01 为准，02 偏差不继承到 03**：

| 01 业务名称 | 01 技术枚举值   | FT 用例中的表述             | IT 用例中的表述               | 备注                                               |
| ----------- | --------------- | --------------------------- | ----------------------------- | -------------------------------------------------- |

## 8. 多角色可读性评审机制

### 8.1 评审角色与视角

生成测试用例后，从四个角色视角逐一评审：

| 角色               | 评审重点                                                   | 不通过示例                                                   |
| ------------------ | ---------------------------------------------------------- | ------------------------------------------------------------ |
| **产品**           | 能否看懂用例在测什么业务场景？状态/操作是否用了业务语言？  | "已准备 `NORMAL`、`EXPIRING_SOON` 合同" — 产品不懂这些枚举值 |
| **开发**           | 技术细节是否准确？接口参数、错误码、字段名是否与代码一致？ | "提示 XX 错误" — 未写明 retCode 与 retInfo 原文              |
| **测试**           | 步骤是否可执行？预期是否可验证？是否有歧义？               | "验证状态正确" — 未写明具体期望值                            |
| **项目开发管理人** | 范围是否对齐需求？是否有越界测试或遗漏？优先级是否合理？   | "测试 XX 按钮置灰" — 但 01/02 未定义此行为                   |

### 8.2 评审检查清单

生成完成后逐项核对：

- [ ] 每个 FT 前置条件中的状态值使用业务名称 + 括号技术值
- [ ] 每个 FT 预期结果中的文案与 02 逐字一致
- [ ] 每个 IT 请求参数使用技术字段名与枚举值
- [ ] 每个 ET 期望表现中的 retInfo 与 02b 逐字一致
- [ ] 无推断式置灰/隐藏/禁用（02 未定义的交互行为）
- [ ] 无臆测式校验文案（02 未定义的校验规则）
- [ ] 无技术标识符裸用（FT/ET 用例中禁止 `getXxxApi` 函数名或 `snapshotBefore/After` 等后端字段名，改用自然语言描述）
- [ ] 无后端提示误置（前端必填校验场景的预期结果使用前端校验提示，而非后端 retInfo）
- [ ] 无后端实现细节泄漏（FT/ET 用例中禁止描述后端字段恒为 null、前端展示"—"等实现限制，按需求描述预期行为）
- [ ] 无盲目继承失效概念/场景（增量版本生成时，已删除旧版 01 中不存在的概念和 01 明确排除的场景，如"配额行/第 X 行/添加一行"、"无合同的租户"）
- [ ] 无枚举术语/标点偏离 01（FT 前置条件/预期结果中的状态值用 01 原文术语如"启用/禁用"，不变形为"启用中/已禁用"；Toast/提示文案标点与 01 一致，不擅自添加"！"等；01 已删枚举如"已停用"不出现）

- [ ] 功能/接口/权限三类用例表均含「适用版本」列，且迭代后仅更新被改用例的版本号，未改用例保持原值

## 10. 约束

- `FT/IT` 必须沿用对应 `REQ` 的路径编码。
- 不单独维护额外映射文件，直接保持 `REQ -> FT/IT` 主线。
- 要显式区分哪些场景适合 UI 自动化、哪些适合 API 自动化。
- 若 P0 / P1 需求点没有对应测试点，要明确指出。
- **文案禁止改写** — FT 预期结果中的提示文案必须与 02 逐字一致，仅允许占位符（如 `<行号>`）替换为示例值。**例外：当 01 已明确给出该文案时（如「新增成功」「保存成功」），以 01 原文（含标点）为准**；02 若变形（多出「！」、术语改为"启用中"等）不继承。
- **状态值禁止裸用** — FT 中禁止直接使用技术枚举值描述业务状态，必须用"业务名（`技术值`）"格式。
- **功能禁止越界** — 禁止测试 01/02 未定义的交互行为（如推断式置灰、臆测式校验）。
- **评审必须执行** — 生成完成后必须跑 §8 评审检查清单，结果写入附录 E。
- **路由须对齐详设** — 03 第 2.1 的「前端路由」「前端入口」必须与 `02` 第 2.3 节的路由、菜单路径逐字一致；权限用例"直接路由访问"须引用同一路由值，禁止各自硬编码。
- **适用版本列必填** — 功能/接口/权限三类用例表均必须含「适用版本」列，填当前版本号；迭代修改某用例时仅更新该用例的版本号，未改用例保持原值，禁止全量刷新。
- **步骤-预期编号 1:1 对应** — 功能用例的「操作步骤」与「预期结果」两列各自用 `1. 2. 3.` 编号且严格 1:1 对应；禁止步骤有编号而预期笼统一段文字不拆分；每步必有预期，全局性预期并入最相关步骤。
- **越界五禁（详细定义见 §5.3 与 §5.5，逐项自检见 §8.2）** — ①技术标识符禁止裸用（前端 API 函数名/后端字段名仅 IT 可用）；②后端提示禁止误置（前端必填校验场景用前端提示，后端 retInfo 仅在数据合法提交后使用）；③后端实现细节禁止泄漏（字段恒为 null、展示"—"等限制不继承到 03）；④增量版本失效概念/场景禁止盲目继承（对比新旧 01，删除/调整后须在映射校验报告记录）；⑤功能用例必须以 01 为唯一基准（FT 预期结果字段列表与 01 字段表逐字一致，02 不扩展 01 未定义场景）。
