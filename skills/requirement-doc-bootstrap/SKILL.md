# requirement-doc-bootstrap

## 1. 目标

把原始需求文档、会议纪要、聊天记录、补充说明等输入，整理成可进入正式治理链路的 `01-需求文档.md` 初稿。

这个 skill 的重点不是“直接生成一份看起来完整的文档”，而是：

1. 先判断需求是否已经足够清晰。
2. 若不清晰，先把分歧、缺口、边界问题暴露出来，先讨论清楚。
3. 再基于确认后的信息生成 `01-需求文档.md` 初稿。
4. 在功能点编号上优先复用已有模块路径与编号主线，不擅自替用户做最终确认。

## 2. 适用输入

- 原始需求文档
- 原始需求文档中的截图、原型图、流程图、批注图片
- 会议纪要
- 聊天记录
- 增量需求说明
- 现有 `Prds/` 模块目录结构
- 相关模块的既有 `01-需求文档.md`
- 相关 `TRACE.yaml`（如有）

## 3. 使用原则

### 3.1 先澄清，再写 01

如果存在以下情况，不应直接写 `01-需求文档.md`：

- 需求目标不明确
- 业务边界有多种理解
- 验收口径不清楚
- 关键角色、权限、状态流不明确
- 关键页面、弹窗、字段、按钮、提示语、状态切换等交互逻辑未确认清楚
- 操作类提示语、成功提示、空态/空结果文案未确认清楚
- 原始需求中的字段展示示例、颜色/红字/高亮、只读/禁用、显隐/互斥等交互要求未确认清楚
- 展示类或统计类字段的数据来源、计算公式、汇总关系未确认清楚
- 原始文档只有想法，没有形成稳定结论
- 图片中承载了关键业务信息、页面结构、字段说明、交互说明，但尚未被读取和理解

此时必须先组织澄清和头脑风暴，并与用户把交互逻辑确认清楚。

此时应先输出：

- 当前理解摘要
- 模糊点清单
- 待确认问题清单
- 建议讨论路径
- 需要重点确认的交互逻辑清单

在这些问题讨论清楚前，不直接进入 `01` 正文写作。

**需求成熟度评估表**（用于正向判定"是否可进入 01"，不能仅凭主观感觉）：

| 评估维度       | 清晰                                                    | 部分清晰                 | 缺失                       |
| -------------- | ------------------------------------------------------- | ------------------------ | -------------------------- |
| 业务目标       | 目标、价值、本期范围与不做事项均已明确                  | 范围含糊，不做事项未界定 | 仅一句话想法，无可衡量目标 |
| 业务边界       | 与相邻模块/产品的边界已界定                             | 边界方向有但细节未定     | 多种理解并存、未讨论       |
| 角色与权限     | 角色清单、权限矩阵、数据权限规则明确                    | 角色有但权限未细         | 角色未识别                 |
| 状态流         | 主流程、状态切换、异常分支完整                          | 主流程有、异常分支缺     | 状态未识别                 |
| 字段与交互逻辑 | 关键页面/弹窗/字段/按钮/提示/校验/展示示例/颜色约束明确 | 页面有但字段或校验未定   | 页面未识别                 |
| 验收口径       | 每个 REQ 都有可验收条件                                 | 部分 REQ 缺验收口径      | 验收口径整体未定           |
| 图片理解       | 所有引用图片已读取并归属到功能点                        | 部分图片未读或归属不明   | 图片未读取                 |

进入 `01` 正文写作的阈值：

1. 所有维度达到"清晰"——可直接进入。
2. 个别维度为"部分清晰"——仅当用户在澄清中**显式确认接受**该缺口，并标注为"待确认"后，方可进入。
3. 任一维度为"缺失"——必须先回到澄清与头脑风暴，不得进入正文。

评估结果需随澄清进展动态更新，并在最终输出中附上当前评估快照。

### 3.2 图片必须读取并理解，不能跳过

当原始需求材料中包含截图、原型图、流程图、表格图片、批注图片时：

1. 必须逐张读取并理解图片内容，不能因为图片不是正文文本就跳过。
2. 需要把图片视为正式需求输入的一部分，和正文、表格、聊天记录同等对待。
3. 要明确图片分别承载的是：
   - 哪个页面/弹窗/流程
   - 哪些字段/按钮/状态/提示信息
   - 哪些业务规则或交互约束
4. 如果图片与正文存在冲突，必须显式指出并向用户确认，不能自行择一。
5. 如果无法判断图片对应哪个功能点，必须直接询问用户，不能自己猜测归属。

### 3.3 图片素材需要复制到当前版本目录

若本次要把原始需求整理到某个版本目录（如 `Prds/Vx.y.z/`）下：

1. 原始需求中引用的图片不要继续沿用旧路径。
2. 需要把本次需求实际使用的图片统一复制到当前版本目录下的 `assets/`。
3. 文档内图片引用应改为当前版本目录下的相对路径，例如：`./assets/xxx.png`。
4. 复制后要保证文档脱离原始来源目录也能独立阅读。
5. 如果同一张图片同时被版本 `01` 与模块 `01` 使用，优先以当前正在产出的目标文档所在目录为准，避免继续依赖原始材料路径。

### 3.4 图片复制执行规范

为了让图片落位方式一致，默认按下面规则执行：

1. **版本目录优先落位**
   - 如果当前正在产出版本目录文档，默认把图片放到：`Prds/Vx.y.z/assets/`
   - 版本目录下的 `01-需求文档.md` 统一使用该目录中的图片副本
2. **默认目录结构**

```text
Prds/
└─ Vx.y.z/
   ├─ 01-需求文档.md
   └─ assets/
      ├─ overview-01.png
      ├─ tenant-list-01.png
      └─ tenant-edit-dialog-01.png
```

1. **命名建议**
   - 文件名优先体现图片用途，而不是沿用原始无语义文件名
   - 建议格式：`{模块或场景}-{序号}.{后缀}`
   - 例如：
     - `paycfg-overview-01.png`
     - `paycfg-tenant-list-01.png`
     - `paycfg-tenant-edit-dialog-01.png`
   - 若同一图片有标注版与原图，可区分为：
     - `paycfg-tenant-list-annotated-01.png`
     - `paycfg-tenant-list-raw-01.png`
2. **引用方式建议**
   - 版本目录 `01` 中统一使用相对路径：`./assets/文件名`
   - 不再引用：
     - 原始需求目录下的相对路径
     - `MySpace/` 下的原始路径
     - 其他历史版本目录下的图片路径
3. **同图被版本** **`01`** **与模块** **`01`** **同时使用时**
   - 优先保证当前正在产出的文档自洽可读
   - 如果当前目标是版本 `01`，则先复制到版本目录 `assets/`
   - 如果后续模块 `01` 也需要该图，可以：
     - 再复制一份到模块目录自己的 `assets/`，保持模块文档独立可读；或
     - 在用户明确接受的前提下，统一约定由版本目录图片作为共享来源
   - 如果用户没有明确要求共享来源，默认采用**各自产出目录各自保留副本**，优先保证文档独立性，而不是做跨目录依赖
4. **无法确定是否需要复制时的判断口径**
   - 只要图片被正式需求文档引用、解释或用于支撑功能点说明，就视为“需要复制”
   - 仅作为临时讨论背景、且最终没有进入正式文档的图片，可以不复制

### 3.5 功能点编号先查现有路径

在生成 `REQ-*` 前，先检查 `Prds/` 下是否已存在对应模块路径：

1. 若模块路径已存在：
   - 优先复用现有模块路径编码
   - 在该路径编码下续用功能点编号主线
2. 若模块路径不存在：
   - 可以基于原始需求给出一个**建议模块路径**
   - 但这个路径编码与模块命名必须由用户最终确认
3. 用户未确认前：
   - 不把建议路径写死进正式 `01-需求文档.md`
   - 可以先用“建议路径 / 待确认路径”标注

### 3.6 最终编号由用户确认

- skill 可以提出模块路径和 `REQ` 编号建议
- 但最终以用户确认结果为准
- 用户确认后，再写正式 `01-需求文档.md` 初稿

### 3.7 逐字段核对（写入纪律）

无论是 0-1 初稿还是增量 01，写 REQ 内容时必须逐字段对照原始材料，禁止摘要式改写或凭印象补全。

**字段清单提取**：

1. 原始材料中每个表格、每个字段列表，必须完整提取到 01 文档中，不得遗漏字段。
2. 字段顺序按原始材料顺序，不得自行调整。
3. 字段名、字段说明、约束条件必须与原始材料一致，不得改写含义。

**表单组件属性（按控件类型逐项检查）**：

每个表单字段必须写明控件类型和该控件类型的完整属性，不能只写"输入框""下拉框""日期控件"就结束。按控件类型检查以下属性：

| 控件类型        | 必须明确的属性                                                                                                                                                          | 示例                                                                  |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| **输入框**      | ① 字符类型（字母/数字/中文/特殊字符）② 最大长度 ③ 最小长度 ④ 格式校验（正则/邮箱/手机号等）⑤ 默认值 ⑥ 是否可编辑 ⑦ 单位（如有）                                         | "仅支持字母、数字、-、\_，最大长度 50 个字符，默认值 90"              |
| **日期控件**    | ① 精确度（日期/时分/时分秒）② 显示格式（YYYY-MM-DD HH:mm:ss）③ 日期范围限制（最早/最晚可选日期）④ 是否可手动输入还是只能选择 ⑤ 默认值 ⑥ 联动规则（如结束时间≥开始时间） | "日期插件，精确到时分秒，格式 YYYY-MM-DD HH:mm:ss，结束时间≥开始时间" |
| **下拉框**      | ① 单选/多选 ② 是否可搜索 ③ 是否可清空 ④ 数据来源（接口/字典/静态枚举）⑤ 级联关系（如选了 A 后 B 的选项变化）⑥ 默认值                                                    | "下拉多选，支持搜索，数据来源为产品配置中心"                          |
| **开关**        | ① 默认状态（开/关）② 开启后的联动行为 ③ 关闭后的联动行为                                                                                                                | "默认关闭，开启后存储到期自动续费"                                    |
| **数字输入框**  | ① 最小值 ② 最大值 ③ 是否支持小数 ④ 步长 ⑤ 默认值 ⑥ 单位                                                                                                                 | "仅支持正整数，最小值 1，默认值 2，单位 GB"                           |
| **文本域**      | ① 最大字符数 ② 是否支持换行 ③ 是否支持富文本 ④ 占位符提示                                                                                                               | "最大 200 字符，支持换行"                                             |
| **单选/复选组** | ① 枚举值完整列出 ② 默认选中 ③ 联动规则                                                                                                                                  | "枚举：启用、禁用，默认启用"                                          |

**禁止的写法**：

- ❌ "日期插件"（缺精确度、格式、范围限制）
- ❌ "下拉选择器"（缺单选/多选、数据来源）
- ❌ "输入框"（缺字符类型、长度限制）
- ❌ "输入框，必填"（缺格式校验和长度）

**正确的写法**：

- ✅ "日期插件，必填，精确到时分秒，格式 YYYY-MM-DD HH:mm:ss，结束时间≥开始时间"
- ✅ "下拉多选，必填，支持搜索，数据来源为产品配置中心，根据勾选动态展示下方表单字段"
- ✅ "输入框，必填，仅支持字母、数字、-、\_，最大长度 50 个字符，全局唯一"

**HOVER / 弹窗 / 交互细节**：

1. 原始材料中明确描述的 HOVER、弹窗、动态展示等交互行为，必须逐字对照写入，不得张冠李戴（如把 A 字段的 HOVER 写成 B 字段的 HOVER）。
2. 原始材料中明确说"HOVER 展示 X、Y、Z"，01 文档中必须写清楚 HOVER 的触发字段、展示内容、排序规则。

**表格属性（每个表格必须逐项检查）**：

文档中出现的每个表格（主表格、子表格、明细表、用量表、变更记录表等），必须明确以下属性，不能只写字段清单就结束：

| 属性类别       | 必须明确的内容                                                       | 示例                                                       |
| -------------- | -------------------------------------------------------------------- | ---------------------------------------------------------- |
| **排序**       | 默认排序字段、排序方向、哪些列支持点击排序                           | "默认按合同到期时间倒序排列"                               |
| **分页**       | 是否分页、默认每页条数、可选每页条数、是否展示总条数                 | "支持分页，默认每页 10 条，可切换 10/20/50"                |
| **单元格展示** | 长文本截断+tooltip、数字对齐、金额格式化、状态颜色标签、时间格式统一 | "长文本截断展示，鼠标悬浮显示完整内容；状态列使用颜色标签" |
| **固定列**     | 哪些列固定（左/右）、是否固定表头                                    | "操作列右侧固定，表头固定"                                 |

**禁止的写法**：

- ❌ 只写字段清单，不说明排序、分页等表格属性
- ❌ "支持分页"但不说明默认条数和可选条数

**正确的写法**：

- ✅ "展开明细区支持分页，默认每页 10 条，可切换 10/20/50"
- ✅ "默认按合同到期时间倒序排列；长文本截断展示，鼠标悬浮显示完整内容"

**结构与分区**：

1. 弹窗的分区方式（如"基础信息 + 资源配置 + 服务权益"）必须与原始材料一致。
2. 每个分区内的字段必须完整列出，不得遗漏。
3. 分区名称不得自行改写。

**原始材料矛盾时**：

1. 如果原始材料的标题与原型图文件名矛盾（如标题写"明细页"但原型图叫"抽屉弹窗"），不得自行选择一个，必须标记为"待确认"并交用户决定。
2. 如果原始材料中同一字段的描述在不同位置不一致，必须标记冲突并交用户确认。

**基线细节保留（增量场景）**：

1. 增量 01 中保留的基线字段约束（如"仅支持字母、数字、-、\_"，"最大长度 50 个字符"，"仅支持整数"，"默认值 90"等）必须完整迁移，不得丢失或简化。
2. 基线中的校验提示语（如"同一合同内产品套餐不可重复配置：projectCode=xxx，productNo=xxx"）必须迁移到对应位置，不得只写"弹提示"。
3. 即使字段名称或归属分区变化，字段的约束条件（字符类型、长度限制、默认值、数值类型）应保留基线规则，除非原始材料明确修改了该约束。
4. **基线规则只在增量文档中对应字段仍存在时才迁移**——如果增量文档中某字段已被移除，对应的汇总规则、校验规则、业务规则也不应出现在增量文档中。
5. 写入后必须逐字段对比基线，确认没有遗漏约束细节，也没有引入已移除字段的规则。

**自检清单（写入前）**：

- [ ] 原始材料中的每个表格字段是否都已写入 01？
- [ ] 每个字段的控件类型、必填、约束是否与原始材料一致？
- [ ] 每个表单组件是否按控件类型写明了完整属性（输入框：字符类型+长度+格式；日期：精确度+格式+范围；下拉：单选/多选+数据来源+级联）？
- [ ] 每个表格是否说明了排序、分页、单元格展示、固定列等属性？
- [ ] HOVER / 弹窗 / 动态展示的触发字段和展示内容是否正确？
- [ ] 弹窗分区名称和字段归属是否与原始材料一致？
- [ ] 是否存在凭印象补全或摘要式改写的内容？
- [ ] 原始材料中是否有矛盾未标记？
- [ ] 基线字段的约束细节（字符类型、长度、默认值、数值类型）是否完整迁移？
- [ ] 基线中的校验提示语是否迁移到对应位置？

**交互闭环**：

每个操作（按钮、开关、链接等）的交互逻辑必须形成闭环——从用户触发到最终结果，每一步都要写清楚，不能只写"提交成功"就结束。

1. **操作触发**：点击/触发动作后，系统做什么（打开弹窗、执行校验、发起请求等）。
2. **校验/确认**：是否需要二次确认、校验失败时如何处理（保持弹窗、提示错误）。
3. **提交成功后的结果**：不能只写"提示成功"，必须补全三步：
   - 关闭弹窗/抽屉/页面
   - 提示文案（如"新增成功""保存成功"）
   - **列表/页面刷新**（用户能看到操作结果反映在界面上，如新增的数据出现在列表中）
4. **操作失败的处理**：校验失败时终止提交、保持当前状态、提示错误信息。
5. **状态变化**：操作后界面状态的联动变化（如按钮切换、状态列更新、字段置灰）。
6. **校验失败提示文案**：每个校验规则必须写明具体的提示文案，不能只写"弹提示""拦截提交"。

**禁止的写法**：

- ❌ "提交成功后关闭弹窗并提示'新增成功'"（缺列表刷新）
- ❌ "点击禁用后按钮切换为启用"（缺确认成功 + 列表刷新）
- ❌ "校验通过后提交"（缺提交结果说明）
- ❌ "存在则弹提示"（缺具体提示文案）
- ❌ "空值拦截提交"（缺具体提示文案）

**正确的写法**：

- ✅ "提交成功后关闭弹窗并提示'新增成功'，主列表刷新展示最新数据"
- ✅ "点击禁用后确认成功，按钮切换为启用，授权状态变更为禁用，主列表刷新展示最新授权状态"

**自检清单（交互闭环）**：

- [ ] 每个操作是否写清楚了"触发→校验/确认→成功结果→失败处理"完整链路？
- [ ] 提交/保存成功后是否补充了"列表/页面刷新"说明？
- [ ] 状态切换操作是否写清楚了操作后按钮和状态列的联动变化？
- [ ] 是否存在只写"提示成功"而缺列表刷新的情况？
- [ ] 每个校验规则是否写明了具体提示文案（不能只写"弹提示""拦截提交"）？

### 3.8 每个功能点必须清晰、自洽、无歧义

拆分功能点时，不能只做表面切分，必须保证每个功能点本身能单独成立并且逻辑闭环。

至少要检查：

1. 功能边界是否清楚：这个功能点到底覆盖什么、不覆盖什么。
2. 触发对象是否清楚：由谁发起、在哪个页面或流程触发。
3. 输入输出是否清楚：涉及哪些字段、动作、结果。
4. 业务规则是否清楚：成功条件、限制条件、异常口径是否明确。
5. 与相邻功能点的关系是否清楚：是否重复、是否交叉、是否漏了一段关键流程。
6. 操作文案是否清楚：启用、禁用、删除、提交、保存等操作类提示语与结果文案是否已经明确。
7. 展示口径是否清楚：关键字段是否保留了展示示例，以及颜色/红字/高亮、只读/禁用、显隐/互斥等交互约束是否明确。
8. 数据口径是否清楚：展示数据来源、计算公式、汇总关系、历史记录生成来源是否已经明确。

如果某个功能点拆出来后仍然存在歧义、前后矛盾或无法独立验收，就不能直接写进正式 `01`，而应先回到澄清阶段。

### 3.9 不清晰时先调动头脑风暴，而不是硬写

如果原始材料不足以支撑“功能点清晰、自洽、无歧义”，应先进入澄清与头脑风暴阶段，而不是强行生成貌似完整的正文。

建议做法：

1. 先整理当前理解、冲突点、缺失点。
2. 必须先与用户组织澄清和头脑风暴，把交互逻辑、页面行为、字段规则、操作类提示语、成功提示、空态文案、字段展示示例、颜色/高亮/禁用等交互约束、数据来源与计算口径、异常提示、状态切换等内容讨论清楚。
3. 必要时调用相应的头脑风暴 / 方案讨论能力，先把整个功能讨论清楚。
4. 把讨论后形成的稳定结论沉淀为：
   - 业务目标
   - 功能边界
   - 页面/弹窗/流程归属
   - 字段与交互规则
   - 关键交互逻辑
   - 验收口径
5. 只有在这些结论稳定后，才进入 `01-需求文档.md` 初稿生成。

### 3.10 增量更新场景（已有 01 文档时）

本 skill 默认"生成初稿"，但当目标模块下已存在 `01-需求文档.md` 时，必须先识别是初稿还是增量，再选择处理模式，不能一律全量重写。

**模式判定**：

1. 先读取既有 `01-需求文档.md` 与 `TRACE.yaml`（如有），判断本次需求与既有内容的关系。
2. 若既有文档已发布/已进入下游（02/03 已引用），按**增量更新模式**处理。
3. 若既有文档仍是未确认初稿，可按用户意愿选择全量重写或增量更新。

#### 3.10.1 变动点分析

进入增量更新模式后，先执行变动点分析，再写增量 01。

**输入**：

- 基线 01：模块基线目录的 `01-需求文档.md`
- 原始需求材料：新版本的需求文档（如 `MySpace/V1.6.3需求.md`）

**分析方式**：

逐个 REQ 对比基线与原始材料，按功能区域（列表页、新增弹窗、编辑弹窗、明细页等）匹配基线 REQ 与原始材料中的对应功能。REQ 匹配方式为按功能区域 + 功能名称语义匹配，不是按 REQ 编号字符串匹配（原始材料中通常没有 REQ 编号）。

**变动检测维度**：

对比基线 REQ 与原始材料中对应功能时，从以下维度检测变化：

| 维度                | 检测内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 功能说明            | 功能定位、覆盖范围是否变化                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| 页面展示说明        | 字段增减、字段含义变化、展示方式变化、**枚举值变化**（如下拉选项枚举增减/替换，如合同状态从"正常/即将到期/已到期/已停用"变为"正常/即将到期/已到期/即将生效"）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 业务规则            | 校验规则、状态判定逻辑、计算口径变化                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| 交互逻辑            | 操作流程、按钮行为、提示语变化                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| 异常场景            | 边界条件、异常处理变化                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 弹窗结构            | 分区方式、字段分组变化（如从"基础信息+付费信息"改为"基础信息+资源配置+服务权益"）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 标题/功能范围一致性 | 基线 REQ 标题是否仍能准确描述原始材料中该功能的范围。以下任一命中即标记"标题偏移"：① 作用对象/主体发生迁移（如启停对象从合同级改为机构级）；② 新增与原标题主题不相关的新主题——\*\*判定口径：新主题必须独立于原配置动作/原交互流程，需要在其他页面、其他入口或其他弹窗完成。同一配置动作/同一弹窗内的扩展（如"新增合同配置"弹窗内新增存储服务配置模块、新增校验规则）不视为不相关新主题，归入"功能说明"维度的常规"修改"。\*\*示例：原"合同状态展示与启停"中塞入"存量合同存储扩容/续费规则""新签合同增值服务录入"等独立于状态展示动作的新主题——这些规则在新增合同弹窗/独立合同上完成，视为不相关新主题；③ 作用范围、页面位置迁移导致原标题无法覆盖（如合同状态展示从主表操作列移至子表格）。**不触发**：枚举增减、颜色规则调整、状态判定逻辑变化等纯规则层面调整（归入"业务规则"维度的常规"修改"）。 |

任一维度有变化即标记为"修改"；"标题/功能范围一致性"命中时除标记"修改"外，还需走 3.10.1 末尾的"标题偏移处理流程"。

**变动类型判定**：

| 变动类型 | 判定条件                               | 增量 01 中的处理                         |
| -------- | -------------------------------------- | ---------------------------------------- |
| 新增     | 原始材料中有但基线无对应功能           | 完整写入 REQ 详情，需求类型=新增         |
| 修改     | 基线有对应 REQ，原始材料中该功能有变化 | 完整写入 REQ 最新版内容，需求类型=修改   |
| 删除     | 基线有但原始材料中已移除该功能         | 标记 REQ 为删除，需求类型=删除，保留编号 |
| 未变动   | 基线有且原始材料中无变化               | 不出现在增量 01 中                       |

**标题偏移处理流程**：

当"标题/功能范围一致性"维度命中时，除按"修改"处理外，必须额外走以下流程。skill 会按规则自动给出推荐路径及完整推荐改法详情，用户可直接采纳或修改，省去大量确认过程。

**推荐路径判定规则**（按优先级从高到低，命中第一条即推荐）：

| 推荐路径   | 触发条件                                                                              | 推荐改法详情                                                                                                          |
| ---------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 废弃后重建 | 原标题主题已完全不存在，功能已被完全重新定义                                          | 给出新 REQ 承接主题、新 REQ 编号建议（按"拆分新 REQ 编号规则"扫描）、原 REQ 废弃原因                                  |
| 拆分并新建 | 新增≥2 个独立子模块（满足三条件：独立验收+独立测试+独立维护），且原主题仍部分保留     | 给出拆分方案：拆分为 N 个 REQ、每个新 REQ 承接的主题、新 REQ 编号建议（按"拆分新 REQ 编号规则"扫描）、原 REQ 废弃原因 |
| 改标题     | 仅作用对象/主体迁移或作用范围/页面位置迁移，原主题仍部分保留，且未新增≥2 个独立子模块 | 给出新标题候选（1-2 个），格式为"{原主题}+{新作用对象/新范围}"，如"合同状态展示与机构级启停控制"                      |

**"独立子模块"判定口径**（三条件必须全部满足）：

1. **独立验收**：该模块有独立的验收点（如"存储用量模块能独立验收展示与分页"），不依赖其他模块即可完成验收
2. **独立测试**：该模块可单独写测试用例（如 FT-BILLCFG-DETAIL-STORAGE-001），测试失败时不阻塞其他模块的测试
3. **独立维护**：后续版本对该模块的修改（如字段扩展、规则调整）不影响其他模块的实现与维护

**不视为独立子模块的情况**：

- 同一分区内新增字段（如明细抽屉"分析用量表"新增"合同编号"字段）——归入"修改"
- 同一配置动作内的规则扩展（如【新增合同配置弹窗】内新增存储服务配置模块）——归入"修改"
- 单个新增独立规则主题——只有≥2 个才推荐拆分

**处理流程**：

1. 在变动清单中标注"标题偏移=是"，列出三种候选处理路径，并按"推荐路径判定规则"自动给出推荐路径（标"⭐推荐"）及完整推荐改法详情（新标题候选/拆分方案/重建方案）。
2. 用户可直接采纳推荐路径，或选择其他路径，或修改推荐改法详情；用户确认后才进入 01 写作。
3. 用户确认路径后的处理：
   - **改标题路径**：增量 01 中该 REQ 标"修改"；功能清单表的"功能名称"列更新为新标题；"最近变更版本"列更新为本次版本；变动说明表中记录"标题从『X』改为『Y』，原因：..."。
   - **拆分路径**：增量 01 中原 REQ 写简略条目（格式见下文"原 REQ 简略条目格式"），状态标"已废弃"，废弃原因写"拆分至 {新 REQ 编号列表}"；新增的 REQ 标"新增"，各自写完整需求正文；变动说明表中按"拆分映射记录格式"列出单层拆分映射。
   - **重建路径**：增量 01 中原 REQ 写简略条目，状态标"已废弃"，废弃原因写"重建至 {新 REQ 编号}，原因：..."；新 REQ 标"新增"，写完整需求正文；变动说明表中列出重建映射。
4. 废弃路径下，原 REQ 编号不得被回收复用，避免追溯断裂。
5. 历史 03-测试用例文档、05-变更记录.md 中对原 REQ 编号的引用由后续 02/03/05 链路处理，本 skill 只在 01 层面记录映射关系，不替下游链路决策。

**拆分新 REQ 编号规则**（避免嵌套）：

1. 新 REQ 用扁平编号，续用模块既有编号主线，扫描模块基线目录和当前版本目录的 `01-需求文档.md`，找出该 L1/L2 路径下所有已存在的 REQ 编号，取最大序号 +1、+2、+3…生成新编号建议。
2. 编号建议需用户确认（与 3.6 节"最终编号由用户确认"规则对齐）。
3. **禁止用字母后缀（`-A`、`-B`、`-C`）或版本后缀（`-V163-A`）生成嵌套编号**——这些写法在下次迭代中会演变为 `-A-A`、`-V163-A-V164-A`，导致编号链不可读。
4. **变动说明表记录单层映射**：每个新 REQ 只记录"本次拆分来源 REQ"，不记录原始祖先 REQ。多层拆分追溯通过传递关系查找（如 `DETAIL-007` 源自 `DETAIL-002`，`DETAIL-002` 源自 `DETAIL-001`，查两次变动说明表可得 `DETAIL-007` 追溯到 `DETAIL-001`）。
5. 原 REQ 编号标记"已废弃"后不得被回收复用（沿用 3.10.2 节规则）。

**原 REQ 简略条目格式**（拆分/重建路径下，原 REQ 在增量 01 中的呈现）：

```markdown
#### REQ-CONFIG-BILLCFG-DETAIL-001 明细抽屉查看（已废弃）

| 字段         | 内容                                                                        |
| ------------ | --------------------------------------------------------------------------- |
| 功能点编号   | `REQ-CONFIG-BILLCFG-DETAIL-001`                                             |
| 需求类型     | 删除                                                                        |
| 引入版本     | `V1.6.1`                                                                    |
| 最近变更版本 | `V1.6.3`                                                                    |
| 当前状态     | 已废弃                                                                      |
| 废弃原因     | 拆分至 `DETAIL-002`、`DETAIL-003`、`DETAIL-004`、`DETAIL-005`、`DETAIL-006` |
| 关联验收编号 | `[A06]`（原验收编号保留，新 REQ 各自的验收编号在功能清单中单独列出）        |

> 原 REQ 详情见 V1.6.1 基线；功能已拆分至上述新 REQ，详见各新 REQ 条目。
```

**废弃原因的语义区分**（状态统一为"已废弃"，拆分/重建/不再需要通过废弃原因区分）：

| 废弃原因格式                      | 语义                                            |
| --------------------------------- | ----------------------------------------------- |
| `拆分至 {新 REQ 编号列表}`        | 拆分场景：原功能仍然存在，只是被重组到新 REQ 中 |
| `重建至 {新 REQ 编号}，原因：...` | 重建场景：原功能已完全重新定义                  |
| `功能不再需要，{具体原因}`        | 功能不再需要场景：原功能已被移除                |

简略条目中**不写**"功能说明/业务规则/页面展示说明/交互逻辑/异常场景"等详细需求正文，避免与拆分后的新 REQ 重复，同时保留编号追溯能力。

**拆分映射记录格式**（变动说明表中新增"拆分映射"列）：

```markdown
| 功能点编号                      | 变动类型 | 变动说明                                       | 拆分映射                                                     |
| ------------------------------- | -------- | ---------------------------------------------- | ------------------------------------------------------------ |
| `REQ-CONFIG-BILLCFG-DETAIL-001` | 删除     | 已废弃，拆分至 5 个新 REQ                      | → DETAIL-002、DETAIL-003、DETAIL-004、DETAIL-005、DETAIL-006 |
| `REQ-CONFIG-BILLCFG-DETAIL-002` | 新增     | 租户汇总区（承接原 DETAIL-001 中的汇总区部分） | ← DETAIL-001                                                 |
| `REQ-CONFIG-BILLCFG-DETAIL-003` | 新增     | 分析用量（承接原 DETAIL-001 中的分析用量部分） | ← DETAIL-001                                                 |
```

**多层拆分追溯示例**：

- V1.6.3：DETAIL-001 → DETAIL-002\~006（变动说明表记录单层映射）
- V1.6.4：DETAIL-002 → DETAIL-007\~008（变动说明表记录单层映射）
- 追溯 DETAIL-007 到原始祖先：查 V1.6.4 变动说明表得 DETAIL-007 ← DETAIL-002，再查 V1.6.3 变动说明表得 DETAIL-002 ← DETAIL-001，即 DETAIL-007 的原始祖先为 DETAIL-001
- 编号永远扁平（最多三位：DETAIL-007），不会出现 -A-A 嵌套

**功能清单表"当前状态"列枚举值**：

| 当前状态枚举 | 含义                     |
| ------------ | ------------------------ |
| 已确认       | 已确认，正常使用         |
| 已废弃       | 功能已废弃，编号不再使用 |

> 拆分、重建、功能不再需要三种场景的状态统一标"已废弃"，通过"废弃原因"字段区分具体场景（如"拆分至 LIST-004/005/006"、"重建至 LIST-004，原因：..."、"功能不再需要，原因：..."）。

**检查结果输出格式**：

偏移检查结果只列出命中标题偏移的 REQ，未命中项不出现在结果中。每个命中项必须包含：

| 字段          | 说明                                                                                                                                                          |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 基线 REQ 编号 | -                                                                                                                                                             |
| 基线标题      | -                                                                                                                                                             |
| 命中触发条件  | 列出命中的①②③具体条件及证据                                                                                                                                   |
| 推荐路径      | 按"推荐路径判定规则"自动给出，标"⭐推荐"                                                                                                                      |
| 推荐改法详情  | 新标题候选 / 拆分方案（含新 REQ 编号建议）/ 重建方案（含新 REQ 编号建议）                                                                                     |
| 推荐理由      | 一句话说明推荐路径的判定依据，必须包含：命中触发条件 + 推荐路径判定规则的关键依据。格式示例："命中①②③；新增 N 个独立子模块（列出名称），满足三条件，推荐拆分" |

**输出表格示例**：

| 基线 REQ   | 基线标题               | 命中条件 | 推荐路径     | 推荐改法详情                                                                                                                                                                 | 推荐理由                                                                                                     |
| ---------- | ---------------------- | -------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| LIST-003   | 合同状态展示与启停控制 | ①②③      | ⭐拆分并新建 | 拆分为 3 个 REQ：LIST-004 合同状态展示（子表格）、LIST-005 机构级启停控制、LIST-006 存储扩容与增值服务录入（编号建议，需用户确认）；原 LIST-003 标"已废弃"                   | 命中①②③；新增 2 个独立子模块（存储扩容规则、增值服务录入规则），均满足三条件（独立验收/测试/维护），推荐拆分 |
| DETAIL-001 | 明细抽屉查看           | ①②③      | ⭐拆分并新建 | 拆分为 5 个 REQ：DETAIL-002 租户汇总区、DETAIL-003 分析用量、DETAIL-004 存储用量、DETAIL-005 下载记录、DETAIL-006 历史变更（编号建议，需用户确认）；原 DETAIL-001 标"已废弃" | 命中①②③；新增 2 个独立子模块（存储用量表、下载记录表），均满足三条件（独立验收/测试/维护），推荐拆分         |

**注意事项**：

- 基线 01 中已有但原始材料完全未提及的功能默认视为"未变动"而非"删除"，除非用户在确认时明确标记为删除。
- **REQ 内部的子区域（如查询区、主表格、子表格、操作列等）同样遵循"未提及即未变动"原则**：原始材料只描述了主表格字段，不代表查询区字段也变动了。每个子区域必须独立判断——只有原始材料明确描述了该子区域的变化，才标记为变动。禁止从 A 子区域的变化推断 B 子区域也变化。
- **禁止从字段清单推断未提及的区域**：原始材料列出了主表格的新字段，不代表查询区、操作列、交互逻辑也跟着变了。必须严格以原始材料中明确描述的内容为准。
- 变动点分析基于语义匹配，不做代码级 diff。
- 在 REQ 级别整体判断变动类型，不拆分 REQ 内部细粒度变动点。

#### 3.10.2 变动清单确认

分析完成后，输出变动清单交用户确认，再写增量 01。变动清单格式：

```markdown
## 变动清单

| 功能区域          | 基线 REQ 编号               | 变动类型 | 标题偏移 | 推荐路径 + 推荐改法详情                                              | 变动说明                                                                                          |
| ----------------- | --------------------------- | -------- | -------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 列表页-主表格     | REQ-CONFIG-BILLCFG-LIST-002 | 修改     | 是       | ⭐改标题：新标题候选"租户聚合列表与合同子表格展开"                   | 主表格从"一行一合同"改为"一行一租户，多合同聚合"；展开区重构为合同子表格                          |
| 操作列/状态列     | REQ-CONFIG-BILLCFG-LIST-003 | 修改     | 是       | ⭐拆分并新建：拆分为 LIST-004/005/006 三个新 REQ（编号建议，需确认） | 启停对象从合同级改为机构级；新增存储扩容/续费、增值服务录入等不相关主题；状态展示从主表移至子表格 |
| 存储服务购买/扩容 | （无）                      | 新增     | -        | -                                                                    | 新增增值存储服务的购买、扩容、续费规则                                                            |
```

**列说明**：

- `标题偏移`：命中 3.10.1 "标题/功能范围一致性"维度时填"是"，否则填"否"；新增项填"-"。
- `推荐路径 + 推荐改法详情`：仅当"标题偏移=是"时按 3.10.1 "推荐路径判定规则"自动给出推荐路径（标"⭐推荐"）及完整推荐改法详情（新标题候选/拆分方案/重建方案）；其余填"-"。

**确认流程**：

1. 输出变动清单
2. 用户确认变动类型是否正确、变动说明是否准确
3. 用户可以修正变动类型（如把"修改"改为"新增"或"删除"）
4. 用户可以补充变动说明
5. 用户确认后，基于确认后的变动清单写增量 01
6. **标题偏移项由用户采纳推荐路径或显式选择其他路径/修改推荐改法详情后才进入 01 写作；用户未确认前该 REQ 暂停在变动清单阶段，不进入 01 正文。**

**增量更新模式规则**：

1. **只包含变动 REQ**：增量 01 只包含变动的 REQ（新增的完整写、修改的完整写最新版、删除的标记）。未变动的 REQ 不出现在增量文档中。
2. **变更追溯**：
   - 功能清单表的"需求类型"列填写新增/修改/删除。
   - 功能清单表的"最近变更版本"列必须更新为本次版本号。
   - 增量 01 末尾附"变动说明"表，汇总所有变动 REQ 的变动摘要。
3. **新增 REQ**：续用既有编号主线，不重新起编。
4. **废弃 REQ**：废弃 ≠ 删除。保留编号与历史描述，状态标记为"已废弃"，注明废弃版本与原因，避免编号被回收复用导致追溯断裂。
5. **图片处理**：
   - 本次新增/变更的图片按 3.3/3.4 规则复制到当前版本目录 `assets/`。
   - 未变更的图片保持原引用路径，不强行迁移，避免无谓 diff。
6. **待确认项**：增量场景同样适用第 3.1 节成熟度评估，缺口标"待确认"，不得自行补全。

**全量重写模式规则**（仅在用户明确要求或既有文档作废时）：

1. 重新走完整澄清与编号确认流程。
2. 旧文档不直接删除，归档或标记"已废弃-由 Vx.y.z 替代"。

### 3.11 四维审查（交付前质量关卡）

01 文档生成后、正式交付前，执行四维审查，识别逻辑不完整、功能不完善的问题，输出问题清单 md。

**适用场景**：

- 0-1 初稿：审查全量 REQ
- 增量 01：审查变动 REQ（新增的完整审查，修改的审查最新版内容，删除的确认废弃理由是否充分）

**审查方式**：逐模块、逐 REQ 进行以下四个维度的审查。

#### 维度一：需求清晰度

- 功能描述是否有歧义，开发能否直接实现
- 业务规则是否明确（如：字段必填/选填、长度限制、格式要求）
- 边界条件是否定义（如：最大数量、超时时间、并发处理）
- 状态定义是否完整（如：枚举值是否列全、状态流转图是否有）
- 术语是否一致（同一概念是否用了不同名称）

#### 维度二：交互场景完整性

- 页面跳转逻辑是否完整（从哪来、到哪去）
- 按钮操作后的反馈是否说明（成功/失败提示）
- 操作按钮操作前是否有防呆措施（如：删除前确认弹窗提醒）
- 表单提交的校验规则是否明确
- 列表的排序、筛选、分页规则是否说明
- 弹窗/抽屉的触发条件和关闭行为是否定义
- 批量操作的场景是否覆盖（部分成功/部分失败如何处理）
- 权限不足时的交互是否定义
- 大数据量场景的交互是否考虑（导入/导出进度、列表性能）

#### 维度三：逻辑一致性

- 同一字段在不同 REQ 中的定义是否一致
- 状态流转是否有矛盾（如：REQ-A 说可以从 X 到 Y，REQ-B 说不行）
- 业务规则在不同场景下是否冲突
- 数据流向是否闭环（创建的数据是否有对应的查看/编辑/删除）
- 跨 REQ 引用的数据是否对齐
- 增量场景：变动 REQ 与基线未变动 REQ 之间是否有逻辑冲突（如：修改的 REQ 引用了已删除 REQ 的字段）

#### 维度四：异常处理覆盖

- 网络异常、接口超时的处理是否说明
- 并发操作冲突的处理（如：两人同时编辑）
- 数据不存在或已被删除时的处理
- 权限变更后的处理（操作中途权限被收回、角色被禁用）
- 必要的确认操作是否有（如：删除前确认）
- 数据回滚/撤销机制是否需要
- 会话过期时未保存数据的保护
- 外部系统对接的异常处理（如需）

#### 问题清单格式

审查完成后，输出问题清单 md 文件（建议命名：`01-需求文档.问题清单.md`，放在同目录下）：

```markdown
# 需求文档问题清单

> 审查对象：{01-需求文档.md 路径}
> 审查日期：{YYYY-MM-DD}
> 审查范围：全量 REQ / 变动 REQ（增量场景）

## 问题汇总

| 序号 | 所属 REQ                    | 维度           | 严重度 | 问题描述                                                                     | 出处           | 修改建议                                              |
| ---- | --------------------------- | -------------- | ------ | ---------------------------------------------------------------------------- | -------------- | ----------------------------------------------------- |
| 1    | REQ-CONFIG-BILLCFG-LIST-001 | 交互场景完整性 | 高     | 主表格"合同数量"字段的 HOVER 展示未定义关闭时机                              | 一、1.主表格   | 补充：鼠标移出合同数量区域时自动收起                  |
| 2    | REQ-CONFIG-BILLCFG-FORM-001 | 逻辑一致性     | 中     | 新增弹窗中"分析产品套餐编码"多选，但未定义同一合同内是否允许重复选择同一套餐 | 二、2.资源配置 | 补充：与基线的 projectCode+productNo 唯一校验规则对齐 |
```

**严重度定义**：

| 级别 | 含义                 | 示例                                     |
| ---- | -------------------- | ---------------------------------------- |
| 高   | 会导致开发阻塞或返工 | 核心流程缺失、逻辑矛盾、关键字段未定义   |
| 中   | 开发可推进但需确认   | 边界条件不明确、交互细节缺失、术语不一致 |
| 低   | 建议优化             | 描述可更清晰、建议补充说明               |

**审查原则**：

- 站在开发者角度：每个问题都要问"如果我来实现，这里够不够清楚？"
- 不做产品决策：只指出问题和缺失，不替产品做选择
- 给出具体位置：每个问题都要标注出处（章节/REQ 编号），方便定位
- 建议要可操作：建议应该具体，而不是"请补充说明"
- 避免吹毛求疵：聚焦真正影响开发的问题，不纠结文档格式
- 标注待确认项：对原始需求中标注"待确认"的内容不提问题，但在问题清单备注中记录

**审查后的处理**：

1. 输出问题清单后，向用户展示问题汇总
2. 高严重度问题建议在交付前修复
3. 中/低严重度问题可由用户决定是否修复
4. 用户确认后，可选择：修复问题后重新输出 01，或带着问题清单交付（在 01 中标注"待确认"项）

## 4. 期望输出

根据需求成熟度分两种输出：

### 4.1 需求未清晰时

输出澄清材料，而不是直接输出 `01`

至少包含：

1. 当前理解的业务目标
2. 模糊点清单
3. 待确认问题清单
4. 建议模块路径（如需要）
5. 图片理解结果与未确认图片清单
6. 进入 `01` 写作前还缺什么

### 4.2 需求已清晰且路径已确认时

输出 `01-需求文档.md` 初稿所需内容：

1. 模块路径
2. 模块中文名与英文编码
3. `REQ-*` 清单
4. 每个 `REQ` 的功能描述
5. 验收条件
6. 影响范围
7. 与后续 `02/03` 的最小衔接信息

### 4.3 增量更新时

输出增量 `01-需求文档.md` 所需内容：

1. **变动清单**（先输出，交用户确认）：功能区域、基线 REQ 编号、变动类型、变动说明
2. **增量 01 文档**（用户确认变动清单后输出）：
   - 功能清单表（仅变动 REQ，需求类型=新增/修改/删除）
   - 模块详细需求（变动 REQ 的完整最新版内容）
   - 变动说明表（汇总变动摘要）
   - 非功能要求（仅变动部分，如有）

### 4.4 四维审查问题清单

01 文档生成后输出问题清单 md：

1. **问题汇总表**：序号、所属 REQ、维度、严重度、问题描述、出处、修改建议
2. **严重度分级**：高（阻塞开发）、中（需确认）、低（建议优化）
3. **审查范围标注**：全量 REQ 或变动 REQ（增量场景）
4. 图片资产落位方案（目标 `assets/` 路径 + 对应引用关系）
5. 关键操作类提示语、成功文案、空态/空结果文案的明确口径（如需求已确认）
6. 原始需求中的字段展示示例、颜色/高亮/只读等交互约束保留方式
7. 展示类或统计类字段的数据来源、计算公式、汇总关系（如需求涉及）

## 5. 使用步骤

1. 先阅读原始需求材料正文，并识别其中引用的图片、附件和截图。
2. 逐张读取图片内容，整理每张图片对应的页面、流程、字段、交互和业务约束。
3. 如果图片与正文冲突，或无法判断图片归属到哪个功能点，先向用户澄清，不自行猜测。
4. 再搜索 `Prds/` 下是否已存在对应模块路径、相似模块或已有编号主线。
5. 判断需求是否足够清晰，以及每个拆分功能点是否已经自洽、无歧义。
6. 若不清晰：必须先输出澄清清单，并与用户组织澄清和头脑风暴，把交互逻辑确认清楚。
7. 必要时调用头脑风暴/方案讨论能力完善需求理解，而不是直接写 `01`。
8. 若清晰但模块路径未确认：给出建议路径与建议 `REQ`，等待用户确认。
9. 若本次需要产出版本目录文档：同步规划并复制图片到当前版本目录的 `assets/`。
10. 只有在“需求清晰 + 图片理解完成 + 交互逻辑确认完成 + 模块路径确认 + 编号确认”后，才生成 `01-需求文档.md` 初稿。
11. 生成正文后、交付前，必须执行**输出前自检清单**，任一项不通过即回到对应步骤修正，不得带病交付：

    - [ ] 每个 REQ 在"功能清单"与"模块详细需求"中一一对应，无孤儿编号
    - [ ] 每个 REQ 都有可验收条件，且验收口径无歧义
    - [ ] 每个 REQ 的边界 / 触发对象 / 输入输出 / 业务规则 / 异常场景 均已覆盖
    - [ ] 所有引用图片已读取并归属到具体功能点，无"未确认图片"
    - [ ] 文档内图片引用已改为当前版本目录 `assets/` 相对路径，无残留旧路径（`MySpace/`、历史版本目录、原始需求目录）
    - [ ] `assets/` 下图片文件名符合命名规范，无冲突

    - [ ] 颜色/红字/高亮、只读/禁用、显隐/互斥等交互要求已写入对应 REQ，而不是只停留在图片里

    - [ ] 同一 REQ 的业务规则较多时（如超过 5 条），已优先按分类或表格组织
    - [ ] 增量场景下：废弃 REQ 已标记"已废弃"+ 废弃版本 + 原因，未被删除或回收复用
    - [ ] 增量场景下：受影响 REQ 的"最近变更版本"列已更新
