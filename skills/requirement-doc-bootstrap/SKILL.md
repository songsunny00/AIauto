# requirement-doc-bootstrap

## 1. 目标

把原始需求文档、会议纪要、聊天记录、补充说明等输入，整理成可进入正式治理链路的 `01-需求文档.md` 初稿。

这个 skill 的重点不是“直接生成一份看起来完整的文档”，而是：

1. 先判断需求是否已经足够清晰。
2. 若不清晰，先把分歧、缺口、边界问题暴露出来，先讨论清楚。
3. 再基于确认后的信息生成 `01-需求文档.md` 初稿。
4. 在功能点编号上优先复用已有模块路径与编号主线，不擅自替用户做最终确认。

## 2. 适用输入

- 原始需求文档
- 原始需求文档中的截图、原型图、流程图、批注图片
- 会议纪要
- 聊天记录
- 增量需求说明
- 现有 `Prds/` 模块目录结构
- 相关模块的既有 `01-需求文档.md`
- 相关 `TRACE.yaml`（如有）

## 3. 使用原则

### 3.1 先澄清，再写 01

如果存在以下情况，不应直接写 `01-需求文档.md`：

- 需求目标不明确
- 业务边界有多种理解
- 验收口径不清楚
- 关键角色、权限、状态流不明确
- 关键页面、弹窗、字段、按钮、提示语、状态切换等交互逻辑未确认清楚
- 操作类提示语、成功提示、空态/空结果文案未确认清楚
- 原始需求中的字段展示示例、颜色/红字/高亮、只读/禁用、显隐/互斥等交互要求未确认清楚
- 展示类或统计类字段的数据来源、计算公式、汇总关系未确认清楚
- 原始文档只有想法，没有形成稳定结论
- 图片中承载了关键业务信息、页面结构、字段说明、交互说明，但尚未被读取和理解

此时必须先组织澄清和头脑风暴，并与用户把交互逻辑确认清楚。

此时应先输出：

- 当前理解摘要
- 模糊点清单
- 待确认问题清单
- 建议讨论路径
- 需要重点确认的交互逻辑清单

在这些问题讨论清楚前，不直接进入 `01` 正文写作。

**需求成熟度评估表**（用于正向判定"是否可进入 01"，不能仅凭主观感觉）：

| 评估维度       | 清晰                                      | 部分清晰                 | 缺失                       |
| -------------- | ----------------------------------------- | ------------------------ | -------------------------- |
| 业务目标       | 目标、价值、本期范围与不做事项均已明确    | 范围含糊，不做事项未界定 | 仅一句话想法，无可衡量目标 |
| 业务边界       | 与相邻模块/产品的边界已界定               | 边界方向有但细节未定     | 多种理解并存、未讨论       |
| 角色与权限     | 角色清单、权限矩阵、数据权限规则明确      | 角色有但权限未细         | 角色未识别                 |
| 状态流         | 主流程、状态切换、异常分支完整            | 主流程有、异常分支缺     | 状态未识别                 |
| 字段与交互逻辑 | 关键页面/弹窗/字段/按钮/提示/校验/展示示例/颜色约束明确 | 页面有但字段或校验未定 | 页面未识别                 |
| 验收口径       | 每个 REQ 都有可验收条件                   | 部分 REQ 缺验收口径      | 验收口径整体未定           |
| 图片理解       | 所有引用图片已读取并归属到功能点          | 部分图片未读或归属不明   | 图片未读取                 |

进入 `01` 正文写作的阈值：

1. 所有维度达到"清晰"——可直接进入。
2. 个别维度为"部分清晰"——仅当用户在澄清中**显式确认接受**该缺口，并标注为"待确认"后，方可进入。
3. 任一维度为"缺失"——必须先回到澄清与头脑风暴，不得进入正文。

评估结果需随澄清进展动态更新，并在最终输出中附上当前评估快照。

### 3.2 图片必须读取并理解，不能跳过

当原始需求材料中包含截图、原型图、流程图、表格图片、批注图片时：

1. 必须逐张读取并理解图片内容，不能因为图片不是正文文本就跳过。
2. 需要把图片视为正式需求输入的一部分，和正文、表格、聊天记录同等对待。
3. 要明确图片分别承载的是：
   - 哪个页面/弹窗/流程
   - 哪些字段/按钮/状态/提示信息
   - 哪些业务规则或交互约束
4. 如果图片与正文存在冲突，必须显式指出并向用户确认，不能自行择一。
5. 如果无法判断图片对应哪个功能点，必须直接询问用户，不能自己猜测归属。

### 3.3 图片素材需要复制到当前版本目录

若本次要把原始需求整理到某个版本目录（如 `Prds/Vx.y.z/`）下：

1. 原始需求中引用的图片不要继续沿用旧路径。
2. 需要把本次需求实际使用的图片统一复制到当前版本目录下的 `assets/`。
3. 文档内图片引用应改为当前版本目录下的相对路径，例如：`./assets/xxx.png`。
4. 复制后要保证文档脱离原始来源目录也能独立阅读。
5. 如果同一张图片同时被版本 `01` 与模块 `01` 使用，优先以当前正在产出的目标文档所在目录为准，避免继续依赖原始材料路径。

### 3.4 图片复制执行规范

为了让图片落位方式一致，默认按下面规则执行：

1. **版本目录优先落位**
   - 如果当前正在产出版本目录文档，默认把图片放到：`Prds/Vx.y.z/assets/`
   - 版本目录下的 `01-需求文档.md` 统一使用该目录中的图片副本

2. **默认目录结构**

```text
Prds/
└─ Vx.y.z/
   ├─ 01-需求文档.md
   └─ assets/
      ├─ overview-01.png
      ├─ tenant-list-01.png
      └─ tenant-edit-dialog-01.png
```

3. **命名建议**
   - 文件名优先体现图片用途，而不是沿用原始无语义文件名
   - 建议格式：`{模块或场景}-{序号}.{后缀}`
   - 例如：
     - `paycfg-overview-01.png`
     - `paycfg-tenant-list-01.png`
     - `paycfg-tenant-edit-dialog-01.png`
   - 若同一图片有标注版与原图，可区分为：
     - `paycfg-tenant-list-annotated-01.png`
     - `paycfg-tenant-list-raw-01.png`

4. **引用方式建议**
   - 版本目录 `01` 中统一使用相对路径：`./assets/文件名`
   - 不再引用：
     - 原始需求目录下的相对路径
     - `MySpace/` 下的原始路径
     - 其他历史版本目录下的图片路径

5. **同图被版本 `01` 与模块 `01` 同时使用时**
   - 优先保证当前正在产出的文档自洽可读
   - 如果当前目标是版本 `01`，则先复制到版本目录 `assets/`
   - 如果后续模块 `01` 也需要该图，可以：
     - 再复制一份到模块目录自己的 `assets/`，保持模块文档独立可读；或
     - 在用户明确接受的前提下，统一约定由版本目录图片作为共享来源
   - 如果用户没有明确要求共享来源，默认采用**各自产出目录各自保留副本**，优先保证文档独立性，而不是做跨目录依赖

6. **无法确定是否需要复制时的判断口径**
   - 只要图片被正式需求文档引用、解释或用于支撑功能点说明，就视为“需要复制”
   - 仅作为临时讨论背景、且最终没有进入正式文档的图片，可以不复制

### 3.5 功能点编号先查现有路径

在生成 `REQ-*` 前，先检查 `Prds/` 下是否已存在对应模块路径：

1. 若模块路径已存在：
   - 优先复用现有模块路径编码
   - 在该路径编码下续用功能点编号主线
2. 若模块路径不存在：
   - 可以基于原始需求给出一个**建议模块路径**
   - 但这个路径编码与模块命名必须由用户最终确认
3. 用户未确认前：
   - 不把建议路径写死进正式 `01-需求文档.md`
   - 可以先用“建议路径 / 待确认路径”标注

### 3.6 最终编号由用户确认

- skill 可以提出模块路径和 `REQ` 编号建议
- 但最终以用户确认结果为准
- 用户确认后，再写正式 `01-需求文档.md` 初稿

### 3.7 每个功能点必须清晰、自洽、无歧义

拆分功能点时，不能只做表面切分，必须保证每个功能点本身能单独成立并且逻辑闭环。

至少要检查：

1. 功能边界是否清楚：这个功能点到底覆盖什么、不覆盖什么。
2. 触发对象是否清楚：由谁发起、在哪个页面或流程触发。
3. 输入输出是否清楚：涉及哪些字段、动作、结果。
4. 业务规则是否清楚：成功条件、限制条件、异常口径是否明确。
5. 与相邻功能点的关系是否清楚：是否重复、是否交叉、是否漏了一段关键流程。
6. 操作文案是否清楚：启用、禁用、删除、提交、保存等操作类提示语与结果文案是否已经明确。
7. 展示口径是否清楚：关键字段是否保留了展示示例，以及颜色/红字/高亮、只读/禁用、显隐/互斥等交互约束是否明确。
8. 数据口径是否清楚：展示数据来源、计算公式、汇总关系、历史记录生成来源是否已经明确。

如果某个功能点拆出来后仍然存在歧义、前后矛盾或无法独立验收，就不能直接写进正式 `01`，而应先回到澄清阶段。

### 3.8 不清晰时先调动头脑风暴，而不是硬写

如果原始材料不足以支撑“功能点清晰、自洽、无歧义”，应先进入澄清与头脑风暴阶段，而不是强行生成貌似完整的正文。

建议做法：

1. 先整理当前理解、冲突点、缺失点。
2. 必须先与用户组织澄清和头脑风暴，把交互逻辑、页面行为、字段规则、操作类提示语、成功提示、空态文案、字段展示示例、颜色/高亮/禁用等交互约束、数据来源与计算口径、异常提示、状态切换等内容讨论清楚。
3. 必要时调用相应的头脑风暴 / 方案讨论能力，先把整个功能讨论清楚。
4. 把讨论后形成的稳定结论沉淀为：
   - 业务目标
   - 功能边界
   - 页面/弹窗/流程归属
   - 字段与交互规则
   - 关键交互逻辑
   - 验收口径
5. 只有在这些结论稳定后，才进入 `01-需求文档.md` 初稿生成。

### 3.9 增量更新场景（已有 01 文档时）

本 skill 默认"生成初稿"，但当目标模块下已存在 `01-需求文档.md` 时，必须先识别是初稿还是增量，再选择处理模式，不能一律全量重写。

**模式判定**：

1. 先读取既有 `01-需求文档.md` 与 `TRACE.yaml`（如有），判断本次需求与既有内容的关系。
2. 若既有文档已发布/已进入下游（02/03 已引用），按**增量更新模式**处理。
3. 若既有文档仍是未确认初稿，可按用户意愿选择全量重写或增量更新。

**增量更新模式规则**：

1. **不全量重写**：保留既有正文结构与既有 REQ 编号，仅对本次变更涉及的部分修改。
2. **变更追溯**：
   - 功能清单表的"最近变更版本"列必须更新为本次版本号。
   - 受影响的 REQ 在"模块详细需求"中追加变更说明（变更点、变更原因、影响范围）。
   - 建议在文档末尾或独立变更日志中记录：新增 / 修改 / 废弃 的 REQ 清单。
3. **新增 REQ**：续用既有编号主线，不重新起编。
4. **废弃 REQ**：废弃 ≠ 删除。保留编号与历史描述，状态标记为"已废弃"，注明废弃版本与原因，避免编号被回收复用导致追溯断裂。
5. **图片处理**：
   - 本次新增/变更的图片按 3.3/3.4 规则复制到当前版本目录 `assets/`。
   - 未变更的图片保持原引用路径，不强行迁移，避免无谓 diff。
6. **待确认项**：增量场景同样适用第 3.1 节成熟度评估，缺口标"待确认"，不得自行补全。

**全量重写模式规则**（仅在用户明确要求或既有文档作废时）：

1. 重新走完整澄清与编号确认流程。
2. 旧文档不直接删除，归档或标记"已废弃-由 Vx.y.z 替代"。

## 4. 期望输出

根据需求成熟度分两种输出：

### 4.1 需求未清晰时

输出澄清材料，而不是直接输出 `01`

至少包含：

1. 当前理解的业务目标
2. 模糊点清单
3. 待确认问题清单
4. 建议模块路径（如需要）
5. 图片理解结果与未确认图片清单
6. 进入 `01` 写作前还缺什么

### 4.2 需求已清晰且路径已确认时

输出 `01-需求文档.md` 初稿所需内容：

1. 模块路径
2. 模块中文名与英文编码
3. `REQ-*` 清单
4. 每个 `REQ` 的功能描述
5. 验收条件
6. 影响范围
7. 与后续 `02/03` 的最小衔接信息
8. 图片资产落位方案（目标 `assets/` 路径 + 对应引用关系）
9. 关键操作类提示语、成功文案、空态/空结果文案的明确口径（如需求已确认）
10. 原始需求中的字段展示示例、颜色/高亮/只读等交互约束保留方式
11. 展示类或统计类字段的数据来源、计算公式、汇总关系（如需求涉及）

## 5. 使用步骤

1. 先阅读原始需求材料正文，并识别其中引用的图片、附件和截图。
2. 逐张读取图片内容，整理每张图片对应的页面、流程、字段、交互和业务约束。
3. 如果图片与正文冲突，或无法判断图片归属到哪个功能点，先向用户澄清，不自行猜测。
4. 再搜索 `Prds/` 下是否已存在对应模块路径、相似模块或已有编号主线。
5. 判断需求是否足够清晰，以及每个拆分功能点是否已经自洽、无歧义。
6. 若不清晰：必须先输出澄清清单，并与用户组织澄清和头脑风暴，把交互逻辑确认清楚。
7. 必要时调用头脑风暴/方案讨论能力完善需求理解，而不是直接写 `01`。
8. 若清晰但模块路径未确认：给出建议路径与建议 `REQ`，等待用户确认。
9. 若本次需要产出版本目录文档：同步规划并复制图片到当前版本目录的 `assets/`。
10. 只有在“需求清晰 + 图片理解完成 + 交互逻辑确认完成 + 模块路径确认 + 编号确认”后，才生成 `01-需求文档.md` 初稿。
11. 生成正文后、交付前，必须执行**输出前自检清单**，任一项不通过即回到对应步骤修正，不得带病交付：

    **输出前自检清单**：
    - [ ] 模块路径与 REQ 编号已经用户显式确认（非 AI 建议）
    - [ ] 每个 REQ 在"功能清单"与"模块详细需求"中一一对应，无孤儿编号
    - [ ] 每个 REQ 都有可验收条件，且验收口径无歧义
    - [ ] 每个 REQ 的边界 / 触发对象 / 输入输出 / 业务规则 / 异常场景 均已覆盖
    - [ ] 所有引用图片已读取并归属到具体功能点，无"未确认图片"
    - [ ] 文档内图片引用已改为当前版本目录 `assets/` 相对路径，无残留旧路径（`MySpace/`、历史版本目录、原始需求目录）
    - [ ] `assets/` 下图片文件名符合命名规范，无冲突
    - [ ] 成熟度评估表所有维度≥"清晰"，或"部分清晰"项已标注"待确认"并经用户接受
    - [ ] 原始需求中的关键字段展示示例已作为“字段展示示例”保留，未在整理时丢失
    - [ ] 颜色/红字/高亮、只读/禁用、显隐/互斥等交互要求已写入对应 REQ，而不是只停留在图片里
    - [ ] 操作类提示语、成功文案、空态/空结果文案已明确；查看态未被强行补提示语
    - [ ] 展示类或统计类字段的数据来源、计算公式、汇总关系已明确
    - [ ] 同一 REQ 的业务规则较多时（如超过 5 条），已优先按分类或表格组织
    - [ ] 增量场景下：废弃 REQ 已标记"已废弃"+ 废弃版本 + 原因，未被删除或回收复用
    - [ ] 增量场景下：受影响 REQ 的"最近变更版本"列已更新
    - [ ] 待确认项已显式标出，未用想象补齐
    - [ ] 文风符合正式需求基线，无聊天式表达

## 6. 输出格式建议

### 情况 A：先澄清

```markdown
## 当前理解

-

## 图片理解结果

- 图片 1：{页面/流程/字段/交互理解}
- 图片 2：{页面/流程/字段/交互理解}

## 未确认图片清单

- 图片：
  - 不确定原因：
  - 需要用户确认什么：

## 模糊点

-

## 待确认问题

-

## 建议模块路径

- 英文编码：
- 中文名称：
- 原因：

## 进入 01 之前还缺什么

-
```

## 7. Prompt 模板建议

### 7.1 用于“先澄清”的 prompt 模板

```text
请先不要直接写 `01-需求文档.md`。

我会给你一份原始需求材料，请先做这几件事：
1. 先完整阅读正文，并识别其中所有图片/截图/原型图/流程图；
2. 必须逐张读取并理解图片内容，不能跳过图片；
3. 输出每张图片承载的页面、流程、字段、按钮、交互、业务规则理解；
4. 如果图片与正文冲突，或无法判断图片属于哪个功能点，必须先提问，不要自行猜测；
5. 判断需求是否已经足够清晰；
6. 如果不清晰，先输出“当前理解 / 图片理解结果 / 未确认图片清单 / 模糊点 / 待确认问题 / 建议模块路径 / 进入 01 之前还缺什么”；
7. 先检查 `Prds/` 下是否已经存在可复用的模块路径与编号主线；
8. 如果已有路径，优先建议复用；如果没有，请给出建议路径，但不要直接定稿；
9. 功能点编号只给建议，最终要等用户确认后，才能进入正式 `01-需求文档.md` 写作；
10. 如果功能点拆分还不够清晰、存在歧义或逻辑不自洽，必须先与用户组织澄清和头脑风暴，把交互逻辑、操作类提示语、成功文案、空态文案、字段展示示例、颜色/高亮等交互口径确认清楚，不要硬写正文。
11. 展示类或统计类字段若涉及数据来源、计算公式、汇总关系，必须先确认清楚再写。
12. 只要需求不清晰、不完整，或者关键交互逻辑 / 文案口径 / 数据口径没有确认完，就禁止直接输出 `01` 正文。

输出要面向后续写 `01`，不要写成泛泛摘要。
```

### 7.2 用于“生成 01 初稿”的 prompt 模板

```text
请基于已经确认的需求材料，生成 `01-需求文档.md` 初稿。

要求：
1. 先沿用已确认的模块路径、模块编码和功能点编号；
2. 如果 `Prds/` 中已有相同模块路径，必须复用现有主线；
3. 原始材料中的图片必须已经读取并理解，不允许跳过；
4. 如果图片无法对应到具体功能点，必须先停下来询问，不要假设；
5. 每个拆分功能点都必须边界清晰、逻辑自洽、没有歧义；
6. 若仍存在未确认项，必须单独标出，不要假设；
7. 输出内容至少包括：背景、目标、功能点、功能点编号、验收条件、影响范围；
8. 原始需求中已给出的字段展示示例、颜色/红字/高亮、只读/禁用等交互要求必须保留到对应 REQ；
9. 操作类提示语、成功文案、空态/空结果文案若未确认清楚，必须先停下来询问；查看态不要强行补提示语；
10. 展示类或统计类字段要写清数据来源、计算公式、汇总关系；业务规则较多时优先按分类或表格组织；
11. 如果本次产出的是版本目录文档，图片应统一复制到当前版本目录的 `assets/`，文档中使用新相对路径引用；
12. 文风要适合作为正式需求基线，不写聊天式表达。

输出结果应可直接进入 `01-需求文档.md` 进一步整理。
```

- 不因为想加快速度而跳过需求澄清。

- 输出应服务于写 `01-需求文档.md`，不要写成泛泛会议总结。
- 不允许跳过图片理解；图片中的页面、字段、交互、流程信息必须纳入需求分析。
- 不允许继续沿用原始材料中的图片路径作为正式版本文档引用路径。
- 不允许在图片归属不明、功能点边界不清或业务规则冲突时自行猜测补全。
- 若需求存在明显缺口、矛盾或歧义，必须先与用户组织澄清和头脑风暴，把交互逻辑确认清楚，而不是输出貌似完整但不可靠的正文。
