# 失败归因五类详解

> 本文件从 `playwright-test-implementation` SKILL §10 / §13.3 拆出，供失败修复与 AI 报告归因时按需加载。
> **铁律：每个失败用例的根因只归为 `ENV / DATA / SCRIPT / DEFECT / CHANGE` 五类之一，且必须先读工件再下结论。**

## 0. 排查固定顺序（先做这一步）

不论归因哪一类，排查按以下顺序读工件，避免凭印象归因：

1. **`junit.xml`**：确认失败用例、耗时、是否批量失效（批量失效多指向 `ENV` 或 `CHANGE`）。
2. **screenshot / `error-context.md`**：失败瞬间的 DOM 与提示信息（按钮是否可见、有无 toast、有无错误码）。
3. **`trace.zip`**（`npx playwright show-trace`）：是否真点到了按钮、是否打开了弹窗、是否发出了请求、请求返回什么。
4. 再判定根因类别（见下表）。

## 1. 五类对照表

| 类别 | 含义 | 典型迹象 | 修复方向 |
| ---- | ---- | -------- | -------- |
| `ENV` | 环境 / 配置问题 | baseURL 不通、登录态失效、502/504、`Executable doesn't exist`、依赖未装、`TEST_DOMAIN_PATH` 未注入 | 修环境/重捕登录态/装浏览器二进制，不改脚本 |
| `DATA` | 测试数据 / 前置条件不满足 | 列表无目标数据、目标合同已消耗、权限缺失、应 skip 未 skip | 补数据或改动态 skip，不改业务断言 |
| `SCRIPT` | 脚本 / 定位 / 断言问题 | 选择器失效、等待不足、文案断言过宽/过严、未触发真实变更、`force:true` 掩盖 disabled | 改脚本（选择器/等待/断言/交互） |
| `DEFECT` | 真实功能缺陷 | 接口 `retCode != 0`、前端报错、DOM 缺失本应存在元素、交互与需求不符 | 提 `BUG-*`，脚本暂 skip 或标记 expected fail |
| `CHANGE` | 需求或页面变更致脚本失效 | 文案改版、字段移除、路由变更、组件库升级 | 同步脚本（选择器/文案/数据）与需求口径 |

## 2. 关键区分点

### 2.1 「请求发没发出」四态（避免误归 SCRIPT）

排查请求类失败时，先分清四态，再归因：

| 状态 | 表现 | 常见归因 |
| ---- | ---- | -------- |
| 脚本没点到按钮 | trace 里无 click，或 click timeout | `SCRIPT`（定位/等待） |
| 按钮点到了，请求没发出 | 有 click，但网络面板无对应请求 | `SCRIPT`（前置字段未填/弹窗拦截）或 `DEFECT`（按钮无 handler） |
| 请求发出了，后端返回业务错误码 | 有请求，`retCode != 0` | `DEFECT`（**禁止**继续归「定位器没找到」） |
| 请求成功了，前端提示/页面反馈未按预期 | `retCode === 0`，但 toast/页面未变 | `DEFECT`（前端反馈）或 `SCRIPT`（断言时机/口径） |

> **核心纪律**：工件已表明 `retCode != 0` 时，**禁止**把问题默认归因为「定位器没找到」或「按钮没点击」。先看 `retCode` 与响应体。

### 2.2 `SCRIPT` vs `DEFECT` 边界

- 脚本能点到、请求能发出、后端 `retCode === 0`，但页面表现与需求不符 → `DEFECT`。
- 脚本定位/等待/断言口径本身有问题 → `SCRIPT`。
- 介于两者之间、需研发核对 → 暂归 `DEFECT?` 并提 `ISSUE-*`，不强行下定论。

### 2.3 `DATA` 的动态 skip 纪律

- 前置数据不满足应**动态检查后 `test.skip(reason)`**，不要直接让用例失败，也不要凭静态假设 skip。
- 例：`if (!(await billingPage.hasConsumedContract())) test.skip(true, "缺少 hasConsumed=true 合同数据");`
- `DATA` 类失败如能用动态 skip 规避，修复方向就是改脚本加 skip，**不提 BUG**。

### 2.4 `CHANGE` 的同步纪律

- 需求/页面变更致脚本失效，归 `CHANGE`：先同步脚本（选择器/文案/数据）与需求口径，再回归。
- `CHANGE` 不提 BUG（变更本身可能是预期），除非变更引入了新缺陷。

## 3. 报告中的归因写法

每个失败用例备注结构固定（详见 `templates/report-generation-prompt.md` 第 3 步）：

```
预期：<用例期望，引用需求/用例口径>
实际：<执行中真实发生，引用截图/trace/retCode>
DOM 状态：<失败瞬间关键元素可见/可点击情况>
归因：<五类之一> + <一句话理由>
修复建议：<对应类别的可执行动作>
证据：<截图/trace 相对路径>
```

## 4. 反模式（禁止）

- ❌ 不读工件直接归「定位器没找到」。
- ❌ `retCode != 0` 仍归 `SCRIPT`。
- ❌ 一律归 `ENV` 蒙混（除非确实批量失效 + 环境异常迹象）。
- ❌ 归因写「未知」「待查」而不给类别。
- ❌ 用 `force: true` 掩盖 disabled/hidden 后把失败归 `DEFECT`（实为 `SCRIPT`）。
