# AI + 接口自动化测试落地方案

## 1. 文档定位

本文档用于明确接口自动化在当前项目中的落地方式、选型理由、目录结构、执行规则和演进路径。

目标不是只选一个工具，而是建立一套能与需求、开发、测试治理主线对齐的接口自动化方案。

---

## 2. 目标与约束

### 2.1 本期目标

1. 把需求编号与接口自动化脚本建立稳定映射
2. 建立一期可落地的最小接口自动化骨架
3. 明确环境、鉴权、数据、断言、报告的统一规则
4. 与 UI 自动化共享一套测试治理主线

### 2.2 约束

- 当前优先目标是**先跑通闭环**，不是一开始就追求接口自动化最深专业化。
- 需要与 `Prds/`、`Tests/`、后续 `TRACE.yaml` 保持同一条追踪主线。
- 需要支持 skill / AI 辅助生成与失败分析。
- 需要兼顾本地执行与后续 CI 执行。

---

## 3. 三种接口自动化方案对比

### 3.1 方案一：Playwright API

| 维度 | 说明 |
|---|---|
| 技术栈 | TypeScript + Playwright APIRequestContext |
| 优点 | 与 UI 自动化同栈；统一配置、统一报告、统一运行入口；上手快 |
| 缺点 | 深度数据编排、复杂 fixture 分层不如 Python 生态灵活 |
| 适用阶段 | 一期优先 |
| 适用场景 | 中小规模接口回归、登录态串联、UI/API 协同验证 |

### 3.2 方案二：Pytest + requests/httpx

| 维度 | 说明 |
|---|---|
| 技术栈 | Python + Pytest + requests/httpx |
| 优点 | fixture、参数化、数据驱动、复杂断言和生态成熟；适合大规模接口集 |
| 缺点 | 与前端/UI 栈分离；团队需要再维护一套 Python 运行时与规范 |
| 适用阶段 | 二期扩展 |
| 适用场景 | 大规模接口覆盖、复杂数据构造、契约校验、批量回归 |

### 3.3 方案三：Postman / Newman / Apifox / OpenAPI 驱动

| 维度 | 说明 |
|---|---|
| 技术栈 | 集合工具 + CLI 执行 |
| 优点 | 上手快；便于接口定义与调试；适合早期协作 |
| 缺点 | 与需求编号、代码目录、自动化工程化治理结合较弱；复用和分层能力一般 |
| 适用阶段 | 补充工具，不建议作为主方案 |
| 适用场景 | 接口调试、联调、临时验证、OpenAPI 导入初稿 |

---

## 4. 选型结论

### 4.1 一期推荐

> **Playwright(UI) + Playwright(API) + skill + AI**

选择原因：

1. UI 与 API 同栈，便于统一 `Tests/` 目录、命名、执行入口、报告方式。
2. 团队可以先用一套 TypeScript 能力跑通需求 → 开发 → 测试闭环。
3. 便于把 `REQ -> FT/IT -> ATS` 的追踪链一次串起来。
4. skill / AI 生成脚本骨架时，上下文更一致。

### 4.2 二期演进方向

当出现以下信号时，再演进到 `Playwright(UI) + Pytest(API) + skill + AI`：

- 接口自动化数量明显增加
- 复杂数据编排场景增多
- 批量参数化与 fixture 复用需求显著增强
- 需要更强的契约校验、Mock、性能插件生态

## 5. 接口自动化资产映射规则

### 5.1 主映射关系

接口自动化也必须以需求编号为主线：

`REQ -> IT -> ATS`

| 资产类型 | 编号规则 | 说明 |
|---|---|---|
| 需求功能点 | `REQ-{L1}-{L2}-{L3}-{NNN}` | 来源于需求目录 |
| 接口测试点 | `IT-{L1}-{L2}-{L3}-{NNN}` | 来源于 `03-测试用例文档.md` |
| 自动化脚本 | `ATS-{L1}-{L2}-{L3}-{NNN}.api.spec.ts` | 接口自动化脚本 |

示例：

- `REQ-CONFIG-REPORTCFG-TYPECFG-001`
- `IT-CONFIG-REPORTCFG-TYPECFG-001`
- `ATS-CONFIG-REPORTCFG-TYPECFG-001.api.spec.ts`

### 5.2 映射约束

1. 一个需求点可拆多个接口测试点。
2. 一个接口测试点原则上对应一组主断言。
3. 接口脚本必须保留原始需求编号，不允许脱离 `REQ` 自造本地编号。
4. 报告标题、执行记录、失败分析必须带 `REQ` / `IT` 编号。

## 6. `Tests/` 下接口自动化推荐目录结构

### 6.1 一期（Playwright API）

```text
Tests/
└─ api/
   └─ CONFIG-配置中心/
      └─ REPORTCFG-报告配置/
         └─ TYPECFG-报告类别配置/
            ├─ specs/
            │  ├─ ATS-CONFIG-REPORTCFG-TYPECFG-001.api.spec.ts
            │  └─ ATS-CONFIG-REPORTCFG-TYPECFG-002.api.spec.ts
            ├─ clients/
            │  └─ typecfg.client.ts
            ├─ fixtures/
            │  └─ auth.fixture.ts
            ├─ data/
            │  └─ typecfg.data.ts
            ├─ schemas/
            │  └─ typecfg.schema.ts
            └─ README.md
```

### 6.2 各目录职责

| 目录 | 职责 |
|---|---|
| `specs/` | 测试场景脚本 |
| `clients/` | 接口访问封装 |
| `fixtures/` | 鉴权、前后置数据准备 |
| `data/` | 请求参数、断言数据 |
| `schemas/` | 响应结构校验 |
| `README.md` | 账号、环境、数据依赖说明 |

### 6.3 二期（Pytest）演进后建议

```text
Tests/
└─ api-py/
   ├─ conftest.py
   ├─ clients/
   ├─ fixtures/
   ├─ data/
   ├─ schemas/
   └─ test_*.py
```

## 7. 鉴权、环境、测试数据、断言分层

### 7.1 鉴权分层

建议统一三层：

1. **账号层**：测试账号、角色账号、权限账号清单
2. **登录层**：登录接口封装、token 获取与刷新
3. **调用层**：业务接口自动附带鉴权头

要求：

- 不在每个脚本里重复写登录逻辑
- Token 获取与刷新统一走 fixture / helper
- 权限测试要显式区分账号，不混用

### 7.2 环境分层

建议最少区分：

- `local`
- `test`
- `staging`

配置项建议抽离：

- baseURL
- 登录地址
- 用户名密码来源
- 代理/证书配置
- 数据清理开关

### 7.3 测试数据分层

建议分三类：

| 数据类型 | 说明 | 处理方式 |
|---|---|---|
| 固定基线数据 | 长期复用的稳定数据 | 固化编号，统一维护 |
| 临时造数 | 每次执行前动态创建 | fixture 负责创建与清理 |
| 受限共享数据 | 多人共用但有并发风险 | 明确锁定规则或隔离规则 |

原则：

- 优先使用可回收、可重复的数据
- 尽量避免依赖人工提前造好的脏数据
- 关键断言不要依赖随机不稳定字段

### 7.4 断言分层

接口断言建议至少分 4 层：

1. **状态码断言**：HTTP status
2. **业务码断言**：`code` / `message`
3. **结构断言**：字段是否存在、类型是否正确
4. **业务断言**：值、状态流、权限结果是否符合需求

不建议只断言：

- `status = 200`
- `code = 0`

必须补业务层断言，否则价值不足。

## 8. 标准编写与执行流程

1. 读取 `01-需求文档.md`、`02-详细设计文档.md`、`03-测试用例文档.md`
2. 识别目标 `REQ` 与 `IT` 编号
3. 确认依赖接口、权限、环境、前置数据
4. 生成接口脚本骨架
5. 人工补齐断言、造数、清理逻辑
6. 本地执行
7. 产出报告
8. 回填执行记录与失败归因

---

## 9. skill / AI 协同方式

### 9.1 推荐分工

| 角色 | 职责 |
|---|---|
| skill | 固定生成流程、命名校验、目录脚手架 |
| agent | 从需求/详设/用例中抽测试点、接口、断言口径 |
| AI | 生成脚本初稿、补齐 schema、分析失败 |
| 人 | 评审断言、确认环境与数据策略 |

### 9.2 推荐链路

```text
需求 / 详设 / 测试用例
    ↓
skill：识别目标需求编号与接口测试点
    ↓
agent：整理接口清单、参数、断言点
    ↓
AI：生成 API 脚本骨架
    ↓
人工补齐与审核
    ↓
执行与报告输出
    ↓
AI 辅助失败分析
    ↓
回填执行记录与追踪状态
```

## 10. 失败归因与结果回填

### 10.1 失败归因分类

建议统一分 6 类：

| 分类 | 说明 |
|---|---|
| `ENV` | 环境不可用、网络异常、网关错误 |
| `AUTH` | token、权限、登录态问题 |
| `DATA` | 数据前置不成立、脏数据、并发占用 |
| `SCRIPT` | 脚本错误、断言错误、造数逻辑错误 |
| `DEFECT` | 后端真实缺陷 |
| `CHANGE` | 需求或接口变更后脚本未同步 |

### 10.2 回填位置

每次执行后至少回填：

1. `versions/04-测试执行记录.md`
   - 执行批次
   - `REQ` / `IT` / 脚本编号
   - 通过/失败
   - 失败分类
   - 报告地址
2. `versions/05-变更记录.md`
   - 若接口契约变更导致脚本调整，记录变更原因
3. `03-测试用例文档.md`
   - 若接口测试点口径变化，更新测试用例
4. 后续 `TRACE.yaml`
   - 更新 `REQ -> IT -> ATS -> result` 的链路状态

### 10.3 报告字段建议

| 字段 | 示例 |
|---|---|
| 需求编号 | `REQ-CONFIG-REPORTCFG-TYPECFG-001` |
| 接口测试点 | `IT-CONFIG-REPORTCFG-TYPECFG-001` |
| 脚本编号 | `ATS-CONFIG-REPORTCFG-TYPECFG-001.api.spec.ts` |
| 结果 | PASS / FAIL |
| 失败分类 | `AUTH` |
| 失败摘要 | token 过期，刷新失败 |
| 报告地址 | `playwright-report/index.html` |
| 责任归属 | 后端 / 测试 / 环境 / 权限配置 |

## 11. 一期最小落地清单

一期建议至少具备：

1. `Tests/api/` 目录骨架
2. 环境配置与 baseURL 规范
3. 鉴权 fixture
4. 首批 10 个以内 P0/P1 接口场景
5. 请求 / 响应 schema 校验能力
6. 失败分类规则
7. 执行报告规范
8. 与需求编号的映射规则

---

## 12. 结论

当前阶段接口自动化推荐顺序为：

1. **一期：Playwright API**
2. **二期：Pytest + requests/httpx**
3. **工具型补充：Postman / Newman / Apifox**

结论不是因为 Playwright API 在所有维度都最强，而是因为它最符合当前阶段目标：

- 先统一栈
- 先统一治理
- 先统一执行入口
- 先统一需求追踪链

在这条主线跑稳后，再把 API 自动化向更专业的 Python 生态扩展。
