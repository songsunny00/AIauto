# 需求开发测试一体化协同方案（落地蓝图版）

## 1. 目标与适用范围

本蓝图用于指导项目内建立一套围绕需求资产治理、开发实现、UI 自动化测试、接口自动化测试的协同体系。

当前目标：

- 统一目录与编号体系
- 建立需求 → 设计 → 开发 → 测试闭环
- 沉淀可复用的模板、skill、agent 和测试资产结构
- 在正式试点项目确定后，快速复用本蓝图落地

说明：

- 当前仅有既有小范围验证案例，正式试点项目待汇报会讨论确定。
- 本文件是详细执行骨架；若与总设计 spec 的最小骨架存在粒度差异，以本文件的子目录和执行规则为准。

## 2. 顶层目录职责

```text
AIauto/
├─ .agents/
├─ Agents/
├─ Codes/
├─ Prds/
├─ Templates/
├─ Tests/
└─ skills/
```

### 2.1 `Prds/`

需求资产中心，放置需求文档、增量需求、原型、详细设计、测试用例源头文件。

### 2.2 `Codes/`

前后端代码与需求映射层。代码目录保持工程组织，不强行镜像需求目录。

补充说明：本文档继续保留 `Codes/` 写法，主要是为了统一表达“需求 -> 代码”的协作视图；物理落地时可以映射到外部代码仓，例如：

- `repos/frontend-repo`
- `repos/backend-repo`

### 2.3 `Tests/`

测试资产中心，放置功能测试用例、UI 自动化、接口自动化、共享测试数据、测试报告。

补充说明：本文档继续保留 `Tests/` 写法，主要是为了完整说明测试资产目录结构；物理落地时可以对应独立测试仓，例如：

- `repos/test-repo`

### 2.4 `Templates/`

分三层：

- `deliverables/`：正式交付物模板
- `governance/`：追踪与映射模板
- `prototypes/`：原型脚手架资源

### 2.5 `skills/`

放置流程能力，如需求解析、需求转任务、测试用例生成、UI/API 自动化骨架生成、失败分析、追踪审计。

第一批先补的本地自定义 skills：

- `skills/requirement-doc-bootstrap/`
- `skills/requirement-analysis/`
- `skills/testcase-generation/`
- `skills/ui-automation-bootstrap/`
- `skills/api-automation-bootstrap/`

补充落地的产品角色 skill：

- `skills/prd-git-commit/`：面向产品角色的 Git 文档提交一体化技能，通过自然语言指令完成暂存-提交-推送，涉及 `01-需求文档` 变更时自动更新 `05-变更记录.md` 并通过钉钉 Webhook 通知开发与测试同事。

补充说明：

- `skills/README.md` 作为本地 skill 目录入口，说明命名规则、目录结构和当前批次范围。
- 第一批优先补"生成与引导"能力，不在这一批内补齐失败分析与追踪审计类增强 skill。
- `prd-git-commit` 作为第一批之外的补充能力，服务于需求变更后的提交、留痕与通知一体化流程，降低产品角色使用 Git 的门槛。

### 2.6 `Agents/`

放置角色 agent，建议按 `product / architect / developer / tester / governance` 分层。

### 2.7 IDE 与 Git 协作载体

建议整个流程统一在 **TRAE / qOder / 其他支持 AI 的 IDE + Git 仓库** 中完成，而不是把需求、代码、测试拆散在多个脱节工具里流转。

推荐协作方式：

- 本文档中的 `Prds/`、`Codes/`、`Tests/` 优先理解为**逻辑协作视图**，方便统一理解需求、代码、测试三类资产的关系。
- 物理落地时，`Codes/`、`Tests/` 可以分别映射到外部仓，例如：`repos/frontend-repo`、`repos/backend-repo`、`repos/test-repo`。
- 需求、开发、测试都在 IDE 中打开系统治理仓，并按需要同时关联外部代码仓/测试仓工作。
- 公共信息默认放在系统治理仓内可检索路径，而不是散落在聊天记录或本地私有文件中。
- IDE 侧建议把 `Prds/`、`Codes/`、`Tests/`、`Templates/`、`docs/` 设为常驻收藏目录；其中 `Codes/`、`Tests/` 可以是指向外部仓的映射入口。

公共信息建议优先放在：

- `Prds/`：需求主文档、增量需求、设计与测试基线
- `docs/traceability-matrix.md`：项目级追踪总览
- `docs/delivery-status-board.md`：模块与版本状态看板
- `Prds/README.md` / 仓库根 `README.md`：入口索引、协作说明、目录导航

## 3. 文档体系与编号规则

### 3.1 正式交付物模板

必选：

- `01-需求文档.md`
- `02-详细设计文档.md`
- `03-测试用例文档.md`

可选：

- `01b-数据流转设计.md`
- `01c-原型文档.md`（可选原型说明文档：在已有专门 HTML 原型/设计稿时，说明原型路由、需求模块映射、前端交互要求与界面风格约束）

过程文档：

- `04-测试执行记录.md`
- `05-变更记录.md`

职责边界：

- `CHANGELOG.md`：系统级持续变更台账，记录版本、影响模块/功能点、主文档回写状态。
- `04-测试执行记录.md`：系统级版本目录下单次版本或单轮执行的测试结果、失败摘要、回归结论。
- `05-变更记录.md`：系统级版本目录下对外发布或里程碑版本的正式变更说明；若项目不需要单独对外记录，可先不启用。

原则：**正式交付物进入编号体系；生成工艺和实施说明不进入编号体系。**

### 3.2 目录命名规则

统一格式：`英文编码-中文名称`

示例：

- `CONFIG-配置中心`
- `REPORTCFG-报告配置`
- `TYPECFG-报告类别配置`

约束：

- 英文编码全大写
- 同层级英文编码唯一
- 功能点编号只引用英文编码

### 3.3 功能点编号

格式：`REQ-{L1}-{L2}-{L3}-{NNN}`

示例：`REQ-CONFIG-REPORTCFG-TYPECFG-001`

规则：

- 每个叶子模块自增编号
- 删除不回收
- 新增续号，修改复用原号

### 3.4 测试编号

- 功能测试用例：`FT-CONFIG-REPORTCFG-TYPECFG-001`
- 自动化脚本：`ATS-CONFIG-REPORTCFG-TYPECFG-001.spec.ts`

## 4. 系统级目录与模块级骨架

建议按“**Prds 代表单个系统项目根目录；一级目录为系统功能模块；稳定基线下沉到模块叶子目录，版本资产放在 Prds 根目录下的系统级版本目录**”组织：

```text
Prds/
├─ README.md
├─ CHANGELOG.md
├─ V1.5.4.1/
│  ├─ 01-需求文档.md             # 系统级版本正式需求
│  ├─ 04-测试执行记录.md
│  └─ 05-变更记录.md
├─ LOGIN-登录/
│  ├─ INDEX.md
│  ├─ 01-需求文档.md
│  ├─ 01b-数据流转设计.md      # 可选
│  ├─ 01c-原型文档.md          # 可选
│  ├─ 02-详细设计文档.md
│  └─ 03-测试用例文档.md
├─ CONFIG-配置中心/
│  └─ REPORTCFG-报告配置/
│     └─ TYPECFG-报告类别配置/
│        ├─ INDEX.md
│        ├─ 01-需求文档.md
│        ├─ 01b-数据流转设计.md  # 可选
│        ├─ 01c-原型文档.md      # 可选
│        ├─ 02-详细设计文档.md
│        └─ 03-测试用例文档.md
└─ SAMPLE-样本中心/
   └─ ...
```

对应测试目录：

```text
Tests/.../模块叶子目录/
├─ INDEX.md
├─ cases/
├─ ui-automation/
│  ├─ specs/
│  ├─ pages/
│  ├─ fixtures/
│  └─ reports/
├─ api-automation/
│  ├─ specs/
│  ├─ clients/
│  ├─ fixtures/
│  └─ reports/
├─ shared/
│  ├─ data/
│  ├─ auth/
│  └─ utils/
```

说明：

- `Prds/` 表示单个系统项目的需求资产根目录，一级目录就是系统功能模块。
- `01-需求文档.md`、`01b`、`01c`、`02`、`03` 等稳定基线文档建议放在功能模块叶子目录。
- `01-需求文档.md`、`04-测试执行记录.md`、`05-变更记录.md` 建议放在 `Prds/` 根目录下的系统级版本目录中，不挂在某个模块下面。
- `CHANGELOG.md` 作为系统级持续变更台账常驻 `Prds/` 根目录。

## 5. 元数据与映射文件

项目级建议新增：

- `docs/traceability-matrix.md`：汇总模块主需求、版本状态与回归状态的项目级总追踪视图。
- `docs/delivery-status-board.md`：汇总模块状态、版本状态与回归状态。

项目级更新责任建议：

- 模块责任人维护本模块的主需求文档、版本文档与测试执行记录。
- 治理角色按固定节奏汇总 `prd-to-code.yaml / 03-测试用例文档.md / 04-测试执行记录.md` 到项目级总矩阵。
- `traceability-matrix` 作为阶段评审和版本关闭时的总览输入之一。

### 5.1 `Codes/mappings/prd-to-code.yaml`

建议至少包含：

- `REQ -> repo`（前端仓 / 后端仓）
- `REQ -> page`
- `REQ -> component`
- `REQ -> api`
- `REQ -> service`
- `REQ -> PR / commit / tag`（按需）

### 5.2 测试关联原则

不再单独维护 `req-test-map.yaml`。

原因：

- `FT` / `IT` 测试点编号本身就是由 `REQ` 功能点编号派生而来。
- UI / API 自动化脚本编号也继续沿用同一功能点编号主线。
- 因此测试关联关系可以通过 `03-测试用例文档.md`、脚本命名和 `04-测试执行记录.md` 直接回溯，不需要额外再维护一份独立映射文件。

建议做法：

- 在 `03-测试用例文档.md` 中按功能点编号组织 `FT` / `IT`。
- UI / API 自动化脚本命名直接沿用功能点编号。
- 执行结果统一回填到 `04-测试执行记录.md`。

## 6. 流程闭环与阶段门禁

### 6.1 阶段 1：需求基线化

输入：原始需求、业务讨论结果

输出：

- `01-需求文档.md`
- 功能点编号

门禁：

- 无主需求文档，不得进入下阶段
- 无功能点编号，不得进入下阶段
- 无验收条件，不得进入下阶段

### 6.2 阶段 2：补充设计

按需触发：

- 版本目录 `01-需求文档.md`：本次存在版本范围内的需求更新
- `01b`：影响状态/权限/数据流转
- `01c`：已有独立原型页面，且需要说明原型路由、页面交互或界面风格约束

输出：

- 本次实际触发的版本 `01-需求文档.md`、`01b-数据流转设计.md`、`01c-原型文档.md`
- 受影响功能点清单
- `05-变更记录.md`（如本版本在需求交接后发生增量需求、范围调整、验收变化或回写动作）

回写规则：

- 版本关闭前，版本目录 `01-需求文档.md` 与模块主需求 `01-需求文档.md` 必须完成同步更新。
- `01b/01c` 若形成了新的稳定业务规则、字段口径、页面交互结论，也需同步回写 `01` 或 `02` 的对应章节，避免补充文档长期漂移。
- 需求交接开发后，若同版本内继续出现增量需求、范围调整、验收变化或正式回写动作，应在 `05-变更记录.md` 中追加留痕，说明变动原因、影响范围、受影响 `REQ` 与回写情况。

门禁：

- 增量需求若未指明影响功能点，不得进入详细设计

### 6.3 阶段 3：详细设计

输出：

- `02-详细设计文档.md`
- 需求到页面/API/字段/状态映射

门禁：

- 无详细设计，不进入大规模开发

### 6.4 阶段 4：开发实现

输出：

- 代码实现
- `prd-to-code.yaml` 更新

门禁：

- 代码若无法映射回功能点编号，不视为完成

### 6.5 阶段 5：测试设计与自动化生成

输出：

- `03-测试用例文档.md`
- `FT-*` / `IT-*` 测试点
- UI/API 自动化脚本骨架

补充原则：

- 测试脚本不建议等到“开发结束、正式转测前”才开始写。
- 更合理的方式是分阶段推进：需求/详设阶段先完成 `03-测试用例文档.md` 和 `FT-*` / `IT-*`；开发联调阶段优先落接口自动化脚本、UI 自动化骨架、测试数据准备；转测前再集中补齐 UI 断言、稳定等待、回归集和执行口径。
- 接口自动化通常可以更前置，只要接口定义、入参出参、鉴权方式基本稳定，就可以先写和先跑。
- UI 自动化建议在页面结构、关键交互、稳定定位点基本确定后再补齐主场景脚本，避免页面频繁变动时过早投入导致大量返工。

门禁：

- P0/P1 功能点无测试点，不得进入测试完成状态

### 6.6 阶段 6：执行回归与结果回填

输出：

- `04-测试执行记录.md`
- 自动化执行报告
- 失败分析摘要
- 功能点通过/失败状态回填

门禁：

- 不能只给出“脚本通过/失败”，必须能回到需求点层说明状态

### 6.7 阶段 7：版本关闭与主文档回写

输出：

- 主需求文档已同步
- `CHANGELOG.md`

门禁：

- 若版本 `01-需求文档.md` 尚未完成更新，不能关闭版本

### 6.8 流程跑通流程图

```text
[业务提出需求]
        ↓
[需求角色]
编写/更新 `01-需求文档.md`
生成 REQ 编号（统一功能点编号主键）
        ↓
{是否存在增量或复杂补充说明?}
   ├─ 是 → [更新版本 `01-需求文档.md`，并按需补 `01b-数据流转设计.md` / `01c-原型文档.md`，同时标记受影响 REQ，追加 `05-变更记录.md`]
   └─ 否 → [直接进入详细设计]
        ↓
[架构/开发角色]
编写 `02-详细设计文档.md`
按 REQ 拆开发任务
更新 prd-to-code 映射
        ↓
[开发角色]
在 Codes/ 实现并提交 PR / commit
PR、commit 持续关联同一 REQ
        ↓
[测试角色]
编写 `03-测试用例文档.md`
按 REQ 生成 FT / IT
生成 UI/API 自动化骨架
按 REQ 衍生关系组织测试点与脚本编号
        ↓
[测试执行]
手工回归 + UI 自动化 + API 自动化
执行结果回到同一 REQ
        ↓
{是否发现缺陷?}
   ├─ 是 → [提交缺陷并挂接 REQ → 开发修复并关联 REQ → 测试回归验证并更新同一 REQ 状态]
   └─ 否 → [进入结果回填]
        ↓
[结果回填]
更新 04
回填 `04-测试执行记录.md`
沉淀失败分析
        ↓
{是否满足发布门禁?}
   ├─ 否 → [回需求/开发/测试继续修正，再次回归]
   └─ 是 → [关闭版本，回写 01，更新 CHANGELOG，按需产出 05]
```

补充说明：

- 整个闭环建议直接在 IDE（如 TRAE / qOder）中围绕同一 Git 仓执行。
- 文档、代码、测试脚本、映射文件都走分支与 PR，不再依赖线下传文档或人工拷贝结果。
- **同一个 `REQ` 是贯穿需求、开发、测试、缺陷修复、回归验证的统一主键**；若缺陷、PR、测试结果无法挂回 `REQ`，就无法形成稳定闭环。
- 每一阶段至少要留下一个可追踪的仓库内证据：文档变更、映射文件、脚本、执行记录或版本说明。

## 7. Agent / skill 分工建议

### 7.1 product agent

- 校验需求文档完整性
- 识别增量影响
- 维护功能点追踪

### 7.2 architect agent

- 生成/校验详细设计草稿
- 校验状态机与数据流转一致性

### 7.3 developer agent

- 生成开发任务清单
- 更新需求到代码映射

### 7.4 tester agent

- 生成测试点与测试用例骨架
- 生成 UI/API 自动化脚本骨架
- 分析失败原因

### 7.5 governance agent

- 编号检查
- 文档完整性检查
- 增量回写一致性检查
- 功能点编号与测试覆盖完整性检查

### 7.6 推荐的 skill 能力分组

| Skill                        | 所属阶段            | 作用                                                                                                                                                 | 使用场景                                                                                                                  |
| ---------------------------- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `requirement-doc-bootstrap/` | 需求阶段            | 将原始需求材料整理为可进入正式治理链路的 `01-需求文档.md` 初稿；强制读取图片，先判断需求是否清晰，不清晰时先澄清再写正文。                           | 只有原始需求文档、会议纪要、聊天记录、截图或原型，还没有形成稳定的 `01-需求文档.md`，需要先做需求整理、澄清和初稿生成时。 |
| `requirement-analysis/`      | 需求阶段            | 解析 `01/01b/01c/02` 等需求与设计材料，抽取模块范围、`REQ` 清单、验收点、影响资产。                                                                  | 已经有较完整的需求或设计材料，需要快速识别本次影响哪些功能点、页面、接口和下游文档时。                                    |
| `requirement-to-task/`       | 需求交接 / 排期阶段 | 把已确认的需求功能点进一步拆成研发、测试、回写等可执行任务。                                                                                         | 需求已经明确，准备进入排期、开发分工、任务派发或执行清单整理时。                                                          |
| `prototype-to-testpoint/`    | 需求 / 测试设计阶段 | 把原型页面、交互路径、界面约束转换成测试点候选清单。                                                                                                 | 已有原型图、HTML 原型或设计稿，希望提前整理页面级测试点、交互校验点和主路径覆盖范围时。                                   |
| `testcase-generation/`       | 测试设计阶段        | 基于 `01 + 02` 生成 `03-测试用例文档.md` 的组织建议，输出 `FT/IT` 与手工/UI/API 覆盖建议。                                                           | 需求和设计已经相对稳定，需要系统化产出测试用例、测试点编号和覆盖策略时。                                                  |
| `ui-automation-bootstrap/`   | 自动化建设阶段      | 基于 `03` 和模块路径生成 UI 自动化目录结构、README 要点和脚本骨架建议。                                                                              | 页面结构、核心交互、定位点基本明确，准备启动 Playwright 等 UI 自动化建设时。                                              |
| `api-automation-bootstrap/`  | 自动化建设阶段      | 基于 `02/03` 和接口信息生成 API 自动化目录结构、client/spec/fixture/schema 骨架建议。                                                                | 接口定义、入参出参、鉴权方式和关键断言点已经较稳定，准备启动接口自动化时。                                                |
| `ui-failure-analysis/`       | 测试执行 / 回归阶段 | 分析 UI 自动化失败结果，辅助区分真实缺陷、环境问题、数据问题和脚本问题。                                                                             | 自动化执行后出现失败，需要快速归因、给出修复方向和是否需要提缺陷结论时。                                                  |
| `traceability-audit/`        | 评审 / 关闭阶段     | 检查需求、设计、测试、执行记录、变更记录之间的编号与回写一致性。                                                                                     | 阶段评审、版本关闭、交付复盘，或需要核对 `REQ -> 03 -> 04 -> 05` 是否闭环时。                                             |
| `prd-git-commit/`            | 需求变更提交阶段    | 通过自然语言指令完成 `Prds/` 下文档的 Git 暂存-提交-推送；涉及 `01-需求文档` 变更时自动追加 `05-变更记录.md` 并通过钉钉 Webhook 通知开发与测试同事。 | 产品角色完成需求文档编写或修改后，需要提交到 Git 并同步通知团队时。                                                       |

### 7.7 第一批已落地范围

本批次优先落地以下最小闭环 skills：

- `requirement-doc-bootstrap/`
- `requirement-analysis/`
- `testcase-generation/`
- `ui-automation-bootstrap/`
- `api-automation-bootstrap/`

暂不在本批次落地：

- `requirement-to-task/`
- `prototype-to-testpoint/`
- `ui-failure-analysis/`
- `traceability-audit/`

原则：先补原始需求整理、需求解析、测试点生成与 UI/API 自动化骨架这五类起步能力，保证方法能先跑通；失败分析、追踪审计和更细的任务拆解能力放到后续批次增强。

### 7.8 补充落地的产品角色 skill

在第一批最小闭环之外，补充落地以下面向产品角色的 skill：

- `prd-git-commit/`

能力说明：

- 通过自然语言指令（如"提交需求""更新PRD""更新文档"）触发 Git 文档提交一体化流程
- 自动执行暂存-提交-推送，按文件精确暂存（禁止 `git add .`）
- 提交信息遵循 Conventional Commits 规范（`docs(prd): <变更摘要>`）
- 涉及 `01-需求文档` 变更时，自动向 `05-变更记录.md` 三个表格追加变更记录行
- 通过钉钉 Webhook 向开发和测试同事发送变更通知，支持关键词校验和 @ 指定同事
- Webhook 配置从 `.env` 读取，凭证不硬编码、不提交

定位：

- 服务于需求变更后的提交、留痕与通知一体化流程，降低产品角色使用 Git 的门槛
- 与 `requirement-doc-bootstrap` 衔接：后者负责生成 `01-需求文档.md` 初稿，本 skill 负责将其提交到 Git 并通知团队
- 仅处理 `Prds/` 目录下的文档提交，不处理 `Codes/`、`Tests/` 目录的代码提交

## 8. 测试技术方案

### 8.1 UI 自动化三方案

| 方案                    | 实施成本 | 维护成本 | 稳定性 | 复杂场景能力 | AI 协同 | 适用边界                           |
| ----------------------- | -------- | -------- | ------ | ------------ | ------- | ---------------------------------- |
| Playwright + AI         | 中低     | 中低     | 高     | 高           | 高      | 企业后台、复杂交互、多浏览器回归   |
| Cypress + AI            | 低       | 中       | 中高   | 中           | 中高    | 前端主导、快速上手、交互相对单一   |
| Selenium/WebDriver + AI | 中高     | 高       | 中     | 中高         | 中      | 有历史资产、已有成熟 Selenium 体系 |

结论：UI 自动化首选 **Playwright**，Cypress 作为上手型备选，Selenium/WebDriver 仅在已有存量资产时优先考虑。

### 8.2 接口自动化三方案

| 方案                                  | 实施成本 | 维护成本 | 复杂断言能力 | 同栈复用 | AI 协同 | 适用边界                             |
| ------------------------------------- | -------- | -------- | ------------ | -------- | ------- | ------------------------------------ |
| Playwright API + AI                   | 低       | 中低     | 中           | 高       | 高      | 一期快速打通闭环、强调 UI/API 联动   |
| Pytest + requests/httpx + AI          | 中高     | 中       | 高           | 低       | 中高    | 接口规模大、断言复杂、数据编排要求高 |
| Postman/Newman 或 Apifox/OpenAPI + AI | 中       | 中       | 中           | 低       | 中      | 更强调接口契约展示与跨角色协作       |

结论：接口自动化分阶段选型。

- **一期试点**：Playwright API 优先，目标是低成本打通闭环。
- **长期深化**：当接口规模、断言复杂度、数据编排复杂度提升后，再演进到 Pytest 体系。

### 8.3 综合推荐

一期推荐：

> **Playwright(UI) + Playwright(API) + skill + AI**

原因：

- 单技术栈更利于目录、环境、fixture、报告、skill 和 agent 的统一治理。
- 一期目标是尽快跑通闭环，而不是一开始就追求接口自动化的最深专业化。
- 不直接选择 `Pytest(API)` 的核心原因，是为了避免首期进入双技术栈治理，降低落地阻力。

二期演进：

> **Playwright(UI) + Pytest(API) + skill + AI**

触发条件建议：

- 接口自动化数量明显增加
- 复杂断言与数据编排场景增多
- 需要更细的接口分层治理与更强的 Python 测试生态支持

### 11.6 Git 仓库组织建议

推荐口径：**一个系统治理仓 + 多个外部执行仓**。

建议结构：

```text
system-governance/
├─ Prds/
├─ Templates/
├─ skills/
├─ Agents/
└─ docs/

repos/frontend-repo
repos/backend-repo
repos/test-repo
```

这样设计的原因：

- 需求、模板、规则、版本信息集中放在系统治理仓，便于所有角色共享公共信息。
- `Codes/`、`Tests/` 在当前蓝图中继续作为逻辑协作入口，方便统一理解目录结构和映射关系。
- 前端、后端、测试资产分别在独立仓里演进，更符合实际工程管理方式。
- 在 TRAE / qOder 这类 IDE 中，仍可以把系统治理仓和外部仓一起纳入同一工作区协作。

分支与权限建议：

- 系统治理仓：`main` 受保护，需求与规则变更走 PR
- 前端仓：`feat/<module>-<topic>` / `release/<version>`
- 后端仓：`feat/<module>-<topic>` / `release/<version>`
- 测试仓：`test/<module>-<topic>` / `release/<version>`

目录责任建议：

- 需求角色主责：系统治理仓中的 `Prds/**`
- 开发角色主责：外部前端仓、后端仓，以及映射文件
- 测试角色主责：外部测试仓
- 治理/公共角色共管：系统治理仓中的 `Templates/**`、`docs/**`、`skills/**`、`Agents/**`

协作机制建议：

- 所有人默认可读系统治理仓中的 `Prds/`、`Templates/`、`docs/`，确保需求文档和公共规则透明。
- 通过映射文件把需求与外部仓实现建立结构化关联，而不是只靠口头同步。
- PR 模板中强制填写：关联版本、关联 `REQ`、关联外部仓 PR/commit、是否更新 `03/04/05`、是否更新映射文件。
- 版本关闭前必须检查：版本 `01-需求文档.md` 是否已完成更新、`04` 是否已形成。

对当前蓝图的理解方式保持不变：

- `Codes/`：仍作为“需求 -> 代码实现”的逻辑入口
- `Tests/`：仍作为“测试资产结构”的逻辑入口
- 物理仓库则分别映射到 `repos/frontend-repo`、`repos/backend-repo`、`repos/test-repo`

这样既方便统一理解 `Tests` 目录结构，也兼容前后端与测试独立仓管理的现实。
