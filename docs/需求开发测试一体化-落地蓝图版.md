# 需求开发测试一体化协同方案（落地蓝图版）

## 1. 目标与适用范围

本蓝图用于指导项目内建立一套围绕需求资产治理、开发实现、UI 自动化测试、接口自动化测试的协同体系。

当前目标：

- 统一目录与编号体系
- 建立需求 → 设计 → 开发 → 测试闭环
- 沉淀可复用的模板、skill、agent 和测试资产结构
- 在正式试点项目确定后，快速复用本蓝图落地

说明：

- 当前仅有既有小范围验证案例，正式试点项目待汇报会讨论确定。
- 本文件是详细执行骨架；若与总设计 spec 的最小骨架存在粒度差异，以本文件的子目录和执行规则为准。

## 2. 顶层目录职责

```text
AIauto/
├─ .agents/
├─ Agents/
├─ Codes/
├─ Prds/
├─ Templates/
├─ Tests/
└─ skills/
```

### 2.1 `Prds/`

需求资产中心，放置需求文档、增量需求、原型、详细设计、测试用例源头文件。

### 2.2 `Codes/`

代码与需求映射层。当前仓库主要维护 `Codes/mappings/prd-to-code.yaml`，前后端实际代码可以继续放在独立代码仓，不强行镜像 `Prds/` 目录。

物理落地时可以映射到外部代码仓，例如：

- `repos/frontend-repo`
- `repos/backend-repo`

### 2.3 `Tests/`

测试资产根目录，统一承载测试依赖、环境配置、共享认证态、UI 自动化脚本、接口自动化资产和执行报告。

当前已落地的 UI 套件位于 `Tests/ui-automation/`，依赖和 `.env` 统一放在 `Tests/` 级，UI 与后续接口套件共用 `Tests/shared/` 的认证与公共能力。

### 2.4 `Templates/`

分三层：

- `deliverables/`：正式交付物模板
- `governance/`：追踪与映射模板
- `prototypes/`：原型脚手架资源

### 2.5 `skills/`

放置流程能力，当前已落地的能力覆盖需求整理、需求分析、详细设计、测试用例生成、UI 自动化骨架、Playwright 脚本实现、API 自动化骨架、代码驱动的 UI/API 测试和产品需求提交。

当前技能目录包括：

- `requirement-doc-bootstrap/`
- `requirement-analysis/`
- `detail-design-bootstrap/`
- `testcase-generation/`
- `ui-automation-bootstrap/`
- `playwright-test-implementation/`
- `api-automation-bootstrap/`
- `code-driven-ui-api-testing/`
- `playwright-cli-testing/`
- `prd-git-commit/`
- `version-archive/`
- `version-release/`

- `ui-automation-bootstrap/` 负责 UI 自动化目录、README、命名和骨架建议。
- `playwright-test-implementation/` 负责真实 Playwright 脚本生成、维护、失败修复和回归执行约束。
- `api-automation-bootstrap/` 负责 API 自动化结构与骨架建议。
- `code-driven-ui-api-testing/` 负责从前端代码、接口文档和测试用例提取可执行测试信息。
- `playwright-cli-testing/` 负责基于 CLI 的浏览器执行、证据采集和报告整理。
- `prd-git-commit/` 负责 `Prds/` 文档变更的精确提交、变更留痕和通知。
- `version-archive/` 负责版本结束后将增量文档回写为模块基线全量文档，支持首次沉淀（全量覆盖）和增量合并（按 REQ 区块合并），维护模块 INDEX.md 和 CHANGELOG 回写状态。
- `version-release/` 负责版本封版与 Git 标记，校验归档完成后收敛 CHANGELOG、精确提交版本文件、创建 annotated Tag 并推送。归档是封版的前置门禁。

`skills/README.md` 作为技能目录入口，维护技能命名规则、能力边界和当前落地范围。

### 2.6 `Agents/`

当前采用角色文档平铺结构，已落地 `ProductorAgent.md`、`CoderAgent.md`、`TesterAgent.md` 和 `FixBugAgent.md`，统一入口为 `Agents/AGENTS.md`。后续角色数量明显增加时，再按角色域拆分子目录。

### 2.7 IDE 与 Git 协作载体

建议整个流程统一在 **TRAE / qOder / 其他支持 AI 的 IDE + Git 仓库** 中完成，而不是把需求、代码、测试拆散在多个脱节工具里流转。

推荐协作方式：

- 本文档中的 `Prds/`、`Codes/`、`Tests/` 优先理解为**逻辑协作视图**，方便统一理解需求、代码、测试三类资产的关系。
- 物理落地时，`Codes/`、`Tests/` 可以分别映射到外部仓，例如：`repos/frontend-repo`、`repos/backend-repo`、`repos/test-repo`。
- 需求、开发、测试都在 IDE 中打开系统治理仓，并按需要同时关联外部代码仓/测试仓工作。
- 公共信息默认放在系统治理仓内可检索路径，而不是散落在聊天记录或本地私有文件中。
- IDE 侧建议把 `Prds/`、`Codes/`、`Tests/`、`Templates/`、`skills/`、`Agents/` 设为常驻收藏目录；其中 `Codes/`、`Tests/` 可以是指向外部仓的映射入口。

公共信息建议优先放在：

- `Prds/`：需求主文档、增量需求、设计、测试基线与版本资产
- `Prds/CHANGELOG.md`：系统级版本变更总览
- `Prds/Vx.y.z/04b-测试执行记录.md`：版本或单轮执行结果
- `Prds/Vx.y.z/05-变更记录.md`：版本详细变更说明
- `Prds/README.md` / 仓库根 `README.md`：入口索引、协作说明、目录导航
- `Templates/README.md`、`skills/README.md`、`Agents/AGENTS.md`：模板、技能和角色入口

## 3. 文档体系与编号规则

### 3.1 正式交付物模板

必选：

- `01-需求文档.md`
- `02-详细设计文档.md`
- `03-测试用例文档.md`

可选：

- `01a-增量需求文档.md`（版本目录内按需启用，记录版本范围内的新增或调整需求）
- `01b-数据流转设计.md`（按需启用）
- `01c-原型文档.md`（按需启用；已有专门 HTML 原型/设计稿时，用于说明原型路由、需求模块映射、前端交互要求与界面风格约束）

过程文档：

- `04b-测试执行记录.md`
- `05-变更记录.md`

职责边界：

- `CHANGELOG.md`：系统级持续变更台账，记录版本、影响模块/功能点、主文档回写状态。
- `04b-测试执行记录.md`：版本或单轮执行的测试结果、失败摘要和回归结论；当前模板位于 `Templates/deliverables/04b-测试执行记录.md`。
- `05-变更记录.md`：版本目录下对外发布或里程碑版本的正式变更说明；需求交接后发生增量、范围调整、验收变化或正式回写时追加记录。

原则：**正式交付物进入编号体系；生成工艺和实施说明不进入编号体系。**

### 3.2 目录命名规则

统一格式：`英文编码-中文名称`

示例：

- `CONFIG-配置中心`
- `REPORTCFG-报告配置`
- `TYPECFG-报告类别配置`

约束：

- 英文编码全大写
- 同层级英文编码唯一
- 功能点编号只引用英文编码

### 3.3 功能点编号

格式：`REQ-{L1}-{L2}-{L3}-{NNN}`

示例：`REQ-CONFIG-REPORTCFG-TYPECFG-001`

规则：

- 每个叶子模块自增编号
- 删除不回收
- 新增续号，修改复用原号

### 3.4 测试编号

- 功能测试用例：`FT-{L1}-{L2}-{功能域}-{序号}`
- 接口测试用例：`IT-{L1}-{L2}-{功能域}-{序号}`
- 权限 / 异常用例：`PT-{L1}-{L2}-{功能域}-{序号}` / `ET-{L1}-{L2}-{功能域}-{序号}`
- UI 自动化脚本：`ATS-{L1}-{L2}-{功能域}-{起始用例号}.spec.ts`
- 示例：`ATS-CONFIG-BILLCFG-LIST-001.spec.ts`

## 4. 系统级目录与模块级骨架

建议按“**Prds 作为需求与版本资产根目录；版本目录保持浅层；稳定文档、版本需求和测试执行记录按版本统一管理；测试自动化在 Tests/ui-automation/ 独立运行**”组织：

```text
Prds/
├─ README.md
├─ CHANGELOG.md
├─ 00-全局公共说明.md
├─ 系统变更说明.md
├─ 业务术语表.md
├─ CONFIG-配置中心/
│  ├─ BILLCFG-商业化计费配置/
│  │  ├─ 01-需求文档.md              # 模块基线（由 version-archive 回写）
│  │  ├─ 02-详细设计文档.md
│  │  ├─ 03-测试用例文档.md
│  │  └─ INDEX.md
│  └─ ANALYSISCFG-分析策略/
│     └─ (同上结构，按需生成)
├─ LOGIN-登录/
│  ├─ README.md
│  └─ <二级模块>/
│     └─ (同上结构，按需生成)
└─ V1.6.1/
   ├─ assets/                         # 原型截图等版本附件
   ├─ 01-需求文档.md                  # 版本正式需求基线
   ├─ 02-详细设计文档.md
   ├─ 02b-后台文档.md                  # 按需启用
   ├─ 03-测试用例文档.md
   ├─ 04-测试报告文档.md
   ├─ 04b-测试执行记录.md              # 按需生成
   └─ 05-变更记录.md                   # 有变更时维护
```

对应测试目录：

```text
Tests/
├─ package.json / package-lock.json
├─ tsconfig.json
├─ .env                              # 本地环境与账号，不入库
├─ shared/
│  ├─ .auth/<一级模块>/domain-state.json
│  └─ auth/                          # 登录态捕获与路径解析
└─ ui-automation/
   ├─ playwright.config.ts           # 动态一级/二级模块作用域
   ├─ global-setup.ts
   ├─ run.mjs / run-report.mjs / gen-report.mjs
   ├─ fixtures/base.fixture.ts
   ├─ helpers/
   ├─ report-template.md
   ├─ <一级模块>/
   │  └─ <二级模块>/
   │     ├─ specs/ATS-*.spec.ts
   │     ├─ pages/
   │     ├─ fixtures/
   │     ├─ data/
   │     ├─ snapshots/
   │     └─ README.md
   └─ test-reports/<一级模块>/<二级模块|all-modules>/
```

说明：

- `Prds/` 是需求、设计、测试基线和版本资产的统一入口；版本目录不再继续嵌套到模块叶子目录。
- `00-全局公共说明.md` 记录跨模块公共约定（如编号规则、角色权限概览等）。
- 一级模块目录（如 `CONFIG-配置中心/`）下挂二级模块叶子目录（如 `BILLCFG-商业化计费配置/`），叶子目录存放模块基线全量文档（01/02/03 + INDEX.md），由 `version-archive` 在版本结束后回写。
- `01-需求文档.md` 是版本正式需求基线，首次沉淀时为全量，后续版本通过「需求类型」列区分新增/修改/删除。
- `01-需求文档.md`、`02`、`03`、`04b`、`05` 通过版本号和 `REQ` 编号关联，不再依赖额外追踪文件。
- `CHANGELOG.md` 作为系统级持续变更台账常驻 `Prds/` 根目录。
- `Tests/` 统一承载依赖、环境和认证态；当前 UI 自动化实际运行入口为 `Tests/ui-automation/`。

## 5. 元数据与映射文件

项目级汇总优先使用现有资产，不再新增独立总矩阵文件：

- `Prds/CHANGELOG.md`：系统级版本变更总览
- `Prds/Vx.y.z/04b-测试执行记录.md`：版本或单轮测试结果与回归结论
- `Prds/Vx.y.z/05-变更记录.md`：版本详细变更说明
- `Templates/governance/prd-to-code.yaml` 或 `Codes/mappings/prd-to-code.yaml`：需求到代码映射

项目级更新责任建议：

- 模块责任人维护对应版本目录下的需求、设计、测试和变更文档。
- 治理角色按固定节奏核对 `CHANGELOG.md`、版本 `03/04b/05` 和 `prd-to-code.yaml` 的关联状态。
- 阶段评审和版本关闭以 `REQ` 编号、测试用例、执行记录、变更记录和版本台账作为总览依据。

### 5.1 `Codes/mappings/prd-to-code.yaml`

建议至少包含：

- `REQ -> repo`（前端仓 / 后端仓）
- `REQ -> page`
- `REQ -> component`
- `REQ -> api`
- `REQ -> service`
- `REQ -> PR / commit / tag`（按需）

### 5.2 测试关联原则

不再单独维护 `req-test-map.yaml`。

原因：

- `FT` / `IT` 测试点编号本身就是由 `REQ` 功能点编号派生而来。
- UI / API 自动化脚本编号也继续沿用同一功能点编号主线。
- 因此测试关联关系可以通过 `03-测试用例文档.md`、脚本命名和 `04b-测试执行记录.md` 直接回溯，不需要额外再维护一份独立映射文件。

建议做法：

- 在 `03-测试用例文档.md` 中按功能点编号组织 `FT` / `IT` / `PT` / `ET`。
- UI 自动化脚本命名直接沿用功能点编号，例如 `ATS-CONFIG-BILLCFG-LIST-001.spec.ts`。
- API 自动化脚本沿用同一 `REQ` 主线，并与 UI 用例共享环境、账号和数据准备规则。
- 执行结果统一回填到 `04b-测试执行记录.md`。

## 6. 流程闭环与阶段门禁

### 6.1 阶段 1：需求基线化

输入：原始需求、业务讨论结果

输出：

- `01-需求文档.md`
- 功能点编号

门禁：

- 无主需求文档，不得进入下阶段
- 无功能点编号，不得进入下阶段
- 无验收条件，不得进入下阶段

### 6.2 阶段 2：补充设计

按需触发：

- 版本目录 `01-需求文档.md`：本次存在版本范围内的需求更新
- `01b`：影响状态/权限/数据流转
- `01c`：已有独立原型页面，且需要说明原型路由、页面交互或界面风格约束

输出：

- 本次实际触发的版本 `01-需求文档.md`、`01b-数据流转设计.md`、`01c-原型文档.md`
- 受影响功能点清单
- `05-变更记录.md`（如本版本在需求交接后发生增量需求、范围调整、验收变化或回写动作）

回写规则：

- 版本关闭前，版本目录 `01-需求文档.md` 与模块主需求 `01-需求文档.md` 必须完成同步更新。
- `01b/01c` 若形成了新的稳定业务规则、字段口径、页面交互结论，也需同步回写 `01` 或 `02` 的对应章节，避免补充文档长期漂移。
- 需求交接开发后，若同版本内继续出现增量需求、范围调整、验收变化或正式回写动作，应在 `05-变更记录.md` 中追加留痕，说明变动原因、影响范围、受影响 `REQ` 与回写情况。

门禁：

- 增量需求若未指明影响功能点，不得进入详细设计

### 6.3 阶段 3：详细设计

输出：

- `02-详细设计文档.md`
- 需求到页面/API/字段/状态映射

门禁：

- 无详细设计，不进入大规模开发

### 6.4 阶段 4：开发实现

输出：

- 代码实现
- `prd-to-code.yaml` 更新

门禁：

- 代码若无法映射回功能点编号，不视为完成

### 6.5 阶段 5：测试设计与自动化生成

输出：

- `03-测试用例文档.md`
- `FT-*` / `IT-*` / `PT-*` / `ET-*` 测试点
- UI/API 自动化脚本骨架或实现任务

补充原则：

- 测试脚本不建议等到“开发结束、正式转测前”才开始写。
- 更合理的方式是分阶段推进：需求/详设阶段先完成 `03-测试用例文档.md` 和 `FT-*` / `IT-*` / `PT-*` / `ET-*`；开发联调阶段优先落接口自动化脚本、UI 自动化骨架、测试数据准备；转测前再集中补齐 UI 断言、稳定等待、回归集和执行口径。
- 接口自动化通常可以更前置，只要接口定义、入参出参、鉴权方式基本稳定，就可以先写和先跑。
- UI 自动化建议在页面结构、关键交互、稳定定位点基本确定后再补齐主场景脚本，避免页面频繁变动时过早投入导致大量返工。

门禁：

- P0/P1 功能点无测试点，不得进入测试完成状态

### 6.6 阶段 6：执行回归与结果回填

输出：

- `04b-测试执行记录.md`
- 自动化执行报告
- 失败分析摘要
- 功能点通过/失败状态回填

门禁：

- 不能只给出“脚本通过/失败”，必须能回到需求点层说明状态

### 6.7 阶段 7：版本关闭与主文档回写

输出：

- 版本 `01-需求文档.md` 已同步
- `05-变更记录.md`（有版本变更时）
- `CHANGELOG.md` 已更新

门禁：

- 若版本 `01-需求文档.md` 尚未完成更新，不能关闭版本

### 6.8 流程跑通流程图

#### 6.8.1 首次版本流程（以 V1.6.1 为例）

```text
[业务提出需求]
        ↓
[需求角色]
编写 `01-需求文档.md`（全量）
生成 REQ 编号（统一功能点编号主键）
        ↓
{是否存在数据流转或原型补充?}
   ├─ 是 → [按需新增 `01b-数据流转设计.md` / `01c-原型文档.md`]
   └─ 否 → [直接进入详细设计]
        ↓
[架构/开发角色]
编写 `02-详细设计文档.md`
按需产出 `02b-后台文档.md`
按 REQ 拆开发任务
更新 prd-to-code 映射
        ↓
[开发角色]
在 Codes/ 实现并提交 PR / commit
PR、commit 持续关联同一 REQ
        ↓
[测试角色]
编写 `03-测试用例文档.md`
按 REQ 生成 FT / IT / PT / ET
生成 UI/API 自动化骨架或实现任务
按 REQ 衍生关系组织测试点与脚本编号
        ↓
[测试执行]
```

补充说明：

- 整个闭环建议直接在 IDE（如 TRAE / qOder）中围绕同一 Git 仓执行。
- 文档、代码、测试脚本、映射文件都走分支与 PR，不再依赖线下传文档或人工拷贝结果。
- **同一个 `REQ` 是贯穿需求、开发、测试、缺陷修复、回归验证的统一主键**；若缺陷、PR、测试结果无法挂回 `REQ`，就无法形成稳定闭环。
- 每一阶段至少要留下一个可追踪的仓库内证据：文档变更、映射文件、脚本、执行记录或版本说明。
- **首次版本与后续迭代版本的核心差异**：首次版本的 01/02/03 是全量文档，归档时直接全量覆盖到模块基线；后续迭代版本的 01/02/03 是增量文档，归档时按 REQ 操作类型（新增/修改/删除）合并到模块基线。
- **版本归档与版本封版是两个独立环节**：归档（`version-archive`）负责把增量回写为模块基线全量；封版（`version-release`）负责 Git 提交、打 Tag、推送。归档是封版的前置门禁。

## 8. 测试技术方案

### 8.1 UI 自动化三方案

| 方案                    | 实施成本 | 维护成本 | 稳定性 | 复杂场景能力 | AI 协同 | 适用边界                           |
| ----------------------- | -------- | -------- | ------ | ------------ | ------- | ---------------------------------- |
| Playwright + AI         | 中低     | 中低     | 高     | 高           | 高      | 企业后台、复杂交互、多浏览器回归   |
| Cypress + AI            | 低       | 中       | 中高   | 中           | 中高    | 前端主导、快速上手、交互相对单一   |
| Selenium/WebDriver + AI | 中高     | 高       | 中     | 中高         | 中      | 有历史资产、已有成熟 Selenium 体系 |

结论：UI 自动化首选 **Playwright**，Cypress 作为上手型备选，Selenium/WebDriver 仅在已有存量资产时优先考虑。

### 8.2 接口自动化三方案

| 方案                                  | 实施成本 | 维护成本 | 复杂断言能力 | 同栈复用 | AI 协同 | 适用边界                             |
| ------------------------------------- | -------- | -------- | ------------ | -------- | ------- | ------------------------------------ |
| Playwright API + AI                   | 低       | 中低     | 中           | 高       | 高      | 一期快速打通闭环、强调 UI/API 联动   |
| Pytest + requests/httpx + AI          | 中高     | 中       | 高           | 低       | 中高    | 接口规模大、断言复杂、数据编排要求高 |
| Postman/Newman 或 Apifox/OpenAPI + AI | 中       | 中       | 中           | 低       | 中      | 更强调接口契约展示与跨角色协作       |

结论：接口自动化分阶段选型。

- **一期试点**：Playwright API 优先，目标是低成本打通闭环。
- **长期深化**：当接口规模、断言复杂度、数据编排复杂度提升后，再演进到 Pytest 体系。

### 8.3 综合推荐

一期推荐：

> **Playwright(UI) + Playwright(API) + skill + AI**

原因：

- 单技术栈更利于目录、环境、fixture、报告、skill 和 agent 的统一治理。
- 一期目标是尽快跑通闭环，而不是一开始就追求接口自动化的最深专业化。
- 不直接选择 `Pytest(API)` 的核心原因，是为了避免首期进入双技术栈治理，降低落地阻力。

二期演进：

> **Playwright(UI) + Pytest(API) + skill + AI**

触发条件建议：

- 接口自动化数量明显增加
- 复杂断言与数据编排场景增多
- 需要更细的接口分层治理与更强的 Python 测试生态支持

### 11.6 Git 仓库组织建议

推荐口径：**一个系统治理仓 + 多个外部执行仓**。

建议结构：

```text
system-governance/
├─ Prds/
├─ Templates/
├─ skills/
├─ Agents/
└─ docs/

repos/frontend-repo
repos/backend-repo
repos/test-repo
```

这样设计的原因：

- 需求、模板、规则、版本信息集中放在系统治理仓，便于所有角色共享公共信息。
- `Codes/`、`Tests/` 在当前蓝图中继续作为逻辑协作入口，方便统一理解目录结构和映射关系。
- 前端、后端、测试资产分别在独立仓里演进，更符合实际工程管理方式。
- 在 TRAE / qOder 这类 IDE 中，仍可以把系统治理仓和外部仓一起纳入同一工作区协作。

分支与权限建议：

- 系统治理仓：`main` 受保护，需求与规则变更走 PR
- 前端仓：`feat/<module>-<topic>` / `release/<version>`
- 后端仓：`feat/<module>-<topic>` / `release/<version>`
- 测试仓：`test/<module>-<topic>` / `release/<version>`

目录责任建议：

- 需求角色主责：系统治理仓中的 `Prds/**`
- 开发角色主责：外部前端仓、后端仓，以及映射文件
- 测试角色主责：外部测试仓
- 治理/公共角色共管：系统治理仓中的 `Templates/**`、`docs/**`、`skills/**`、`Agents/**`

协作机制建议：

- 所有人默认可读系统治理仓中的 `Prds/`、`Templates/`、`docs/`，确保需求文档和公共规则透明。
- 通过映射文件把需求与外部仓实现建立结构化关联，而不是只靠口头同步。
- PR 模板中强制填写：关联版本、关联 `REQ`、关联外部仓 PR/commit、是否更新 `03/04/05`、是否更新映射文件。
- 版本关闭前必须检查：版本 `01-需求文档.md` 是否已完成更新、`04` 是否已形成。

对当前蓝图的理解方式保持不变：

- `Codes/`：仍作为“需求 -> 代码实现”的逻辑入口
- `Tests/`：仍作为“测试资产结构”的逻辑入口
- 物理仓库则分别映射到 `repos/frontend-repo`、`repos/backend-repo`、`repos/test-repo`

这样既方便统一理解 `Tests` 目录结构，也兼容前后端与测试独立仓管理的现实。
