# 版本归档与基线回写设计

## 1. 背景与目标

当前需求—开发—测试流程在版本测试结束后，版本目录（如 `Prds/V1.6.1/`）下已沉淀了完整的增量文档（`01/02/02b/03/04/05`），但模块基线目录（如 `Prds/CONFIG-配置中心/BILLCFG-商业化计费配置/`）仍为空，稳定基线文档没有沉淀。

`Prds/README.md` 已定义目录模型：版本目录存增量，模块目录存基线全量。但没有任何 skill 负责版本结束后的"基线回写"动作，导致基线目录长期为空，无法作为模块的稳定参考入口。

本设计新增独立的 `version-archive` Skill，由版本负责人 / PM 角色在版本测试结束后触发，把版本目录下的正式交付物回写为模块基线全量文档，并完成索引维护和一致性校验。

## 2. 已确认的决策

### 2.1 责任人：版本负责人 / PM 角色统一归档

归档是版本收尾动作，由版本负责人 / PM 角色统一触发和执行，不拆分到各阶段角色各自归档。这样保证全量一致性有明确兜底人，且符合"版本闭环"的职责定位。

### 2.2 回写范围：仅正式交付物 01/02/03，区分首次沉淀与增量合并

- ✅ 回写 `01-需求文档.md`、`02-详细设计文档.md`、`03-测试用例文档.md` 到模块基线目录
- ✅ **首次沉淀**（模块基线目录无 01/02/03 文件）：全量覆盖
- ✅ **增量合并**（模块基线目录已有 01/02/03 文件）：按 REQ 编号区块合并
- ✅ 支持 `--full` 参数强制全量覆盖（用于基线文档被改乱后重置）
- ✅ 维护模块目录 `INDEX.md`（文档清单 + 最后回写版本 + 回写时间）
- ✅ 更新 `Prds/CHANGELOG.md` 的"主文档回写状态"列
- ✅ REQ 编号 + 测试编号一致性校验（阻断式）
- ❌ 不处理 `04/04b/05`（过程文档留在版本目录）
- ❌ 不回写 `01b/01c/02b`（版本级补充文档留在版本目录作为版本快照，不纳入模块基线；`02b` 中的稳定接口契约应由 `detail-design-bootstrap` 在下一版本回流到 `02` 正文）
- ❌ 不备份旧基线（Git 已提供历史追溯）
- ❌ 不自动创建模块目录（目录不存在时停止并提示）

### 2.3 校验严格度：严格阻断

一致性校验发现任何问题时，skill 停止归档并输出问题清单，等人工修复后重新触发。保证基线质量，不会把带病的文档沉淀下去。

### 2.4 与 version-release 分离

`version-archive` 与 `version-release`（封版）保持独立，通过门禁串联：

- `version-archive` 完成后提示"可执行封版"
- `version-release` 阶段一检查增加门禁：模块基线 `INDEX.md` 存在且最后回写版本等于目标版本

两个 skill 各自独立、各自可单独触发，但通过门禁形成自然先后顺序。

## 3. 触发条件

当用户指令包含以下意图时激活本 skill：

- **归档 V1.6.1 / 版本归档 / 回写基线 / 版本收尾归档**
- **archive V1.6.1**
- **归档 V1.6.1 --full**（强制全量覆盖模式）

缺少版本号时不推断"当前版本"，要求用户明确指定。

## 4. 输入与输出

| 项 | 内容 |
|---|---|
| **输入** | 版本号（如 `V1.6.1`）、`Prds/V1.6.1/` 目录、`Prds/CHANGELOG.md`、模块目录结构 |
| **输出** | 模块基线目录下的 `01/02/03`（带版本标记头）、`INDEX.md`、更新后的 `CHANGELOG.md`、归档报告 |

## 5. 核心流程

```text
1. 解析版本号 → 定位 Prds/V1.6.1/ 目录
2. 识别本次版本涉及的模块（从 01-需求文档的模块编码或 05-变更记录提取）
3. 判断归档模式：
   ├─ 用户指定 --full → 强制全量覆盖模式
   ├─ 模块基线目录无 01/02/03 文件 → 首次沉淀模式（全量覆盖）
   └─ 模块基线目录已有 01/02/03 文件 → 增量合并模式（按 REQ 区块合并）
4. 一致性校验（阻断关卡）：
   ├─ 校验 01 中的 REQ 编号是否在 02/03 中都有对应
   ├─ 校验 03 中的测试编号是否覆盖 01 的所有 REQ
   ├─ 校验 REQ 编号格式（REQ-{L1}-{L2}-{L3}-{NNN}）
   └─ 任一硬错误 → 停止，输出问题清单
5. 按归档模式回写文档（01 → 模块/01，02 → 模块/02，03 → 模块/03）
   ├─ 首次沉淀/--full：全量覆盖版本目录文档到基线目录
   └─ 增量合并：按 REQ 编号区块合并到基线文档（见 5.3.2）
6. 文档头部更新版本标记：<!-- 最后回写版本: V1.6.1 | 回写日期: 2026-08-13 -->
7. 生成/更新模块 INDEX.md（文档清单 + 最后回写版本 + 回写时间）
8. 更新 Prds/CHANGELOG.md 对应版本的「主文档回写状态」列 → 已回写
9. 输出归档报告（回写模式、回写了哪些文件/REQ 区块、校验结果、索引状态）
10. 提示用户："归档已完成，可执行「封版 V1.6.1」进入版本封版流程"
```

### 5.1 模块识别与路径映射

从以下来源交叉确认本次版本涉及的模块：

1. `01-需求文档.md` 中的模块编码主线（如 `CONFIG / BILLCFG`）
2. `05-变更记录.md` 中的模块列
3. 版本目录路径本身

**REQ 编号到物理路径的映射规则**：

REQ 编号格式为 `REQ-{L1}-{L2}-{L3}-{NNN}`（如 `REQ-CONFIG-BILLCFG-FORM-001`）。从中提取 `{L1}` 和 `{L2}`，在 `Prds/` 下按 `英文编码-中文名称` 命名规则定位物理路径：

```text
REQ-CONFIG-BILLCFG-xxx → Prds/CONFIG-配置中心/BILLCFG-商业化计费配置/
```

一级模块（L1，如 `CONFIG`）对应 `Prds/` 下的第一级目录，叶子模块（L2，如 `BILLCFG`）对应一级模块下的第二级目录。L3（如 `FORM`、`LIST`）是功能域，不对应目录层级。

**多模块版本的处理策略**：

当前阶段约束：**一个版本只涉及一个叶子模块**。版本目录下的 `01/02/03` 是该叶子模块的全量文档，整文件回写到对应的模块基线目录。

如果 `05-变更记录.md` 或 `01-需求文档.md` 中出现了多个 L2 编码（如同时涉及 `BILLCFG` 和 `ANALYSISCFG`），skill 停止并提示"当前版本归档仅支持单模块，检测到多个模块：{模块列表}，请拆分版本或手动处理"。多模块版本的拆分回写能力作为后续演进项。

**模块目录不存在时的处理**：

若目标模块目录不存在，skill 停止归档并提示用户按 `英文编码-中文名称` 命名规则手动创建目录后重新触发。skill 不自动创建模块目录。

### 5.2 一致性校验规则

校验在回写前执行，任一失败即停止：

| 校验项 | 规则 | 失败处理 |
|---|---|---|
| REQ 编号格式 | 匹配 `REQ-{L1}-{L2}-{L3}-{NNN}` | 阻断，输出不合规编号清单 |
| REQ 在 02 有对应 | 01 中每个 REQ 在 02 详设中能找到引用 | 阻断，输出缺失清单 |
| REQ 在 03 有对应 | 01 中每个 REQ 在 03 用例中能找到覆盖 | 阻断，输出未覆盖清单 |
| 测试编号格式 | 匹配 `FT/IT/PT/ET-{L1}-{L2}-{功能域}-{NNN}` | 阻断，输出不合规编号清单 |

校验方式：文本检索（grep 风格），不要求语义理解。只要编号字符串在目标文档中出现即视为"有对应"。

### 5.3 文档回写规则

根据归档模式（见步骤 3）执行不同的回写策略。

#### 5.3.1 首次沉淀模式（全量覆盖）

**触发条件**：模块基线目录下不存在 01/02/03 文件，或用户指定 `--full` 参数。

**执行逻辑**：将版本目录下的 01/02/03 整文件复制到模块基线目录，覆盖已有文件（如有）。

**适用场景**：
- 模块首次落地（如 V1.6.1 的 BILLCFG 模块）
- 基线文档被改乱后需要用版本目录全量文档重置（`--full`）

#### 5.3.2 增量合并模式（按 REQ 编号区块合并）

**触发条件**：模块基线目录下已存在 01/02/03 文件，且用户未指定 `--full`。

**核心思路**：版本目录下的增量文档只包含本次版本新增/修改的 REQ 区块。skill 按 REQ 编号识别增量文档中的区块，将其合并到基线文档的对应位置。

**REQ 区块的识别规则**：

不同文档的 REQ 区块锚点不同：

| 文档 | 区块锚点 | 示例 |
|---|---|---|
| `01-需求文档.md` | `#### REQ-{L1}-{L2}-{L3}-{NNN}` 四级标题 | `#### REQ-CONFIG-BILLCFG-LIST-001 列表查询与默认加载` |
| `02-详细设计文档.md` | `##### REQ-{L1}-{L2}-{L3}-{NNN}` 五级标题 | `##### 4.1.4.1 REQ-CONFIG-BILLCFG-LIST-001 列表查询与默认加载` |
| `03-测试用例文档.md` | 用例表中 `REQ-xxx` 列的关联行 | `FT-BILLCFG-LIST-001` 行关联 `REQ-CONFIG-BILLCFG-LIST-001` |

**合并操作分类**：

对增量文档中出现的每个 REQ，按以下规则处理：

| REQ 在基线中的状态 | 合并操作 | 说明 |
|---|---|---|
| 不存在 | **新增区块** | 将增量文档中该 REQ 的完整区块插入基线文档对应位置 |
| 已存在 | **替换区块** | 用增量文档中该 REQ 的区块替换基线文档中的同名区块 |

**各文档的具体合并方式**：

**01-需求文档.md 合并**：
1. **REQ 清单表**：基线表 + 增量表合并，按 REQ 编号去重（增量覆盖同编号行）
2. **REQ 详情区块**：按 `#### REQ-xxx` 标题定位，新增的插入到末尾，已存在的替换区块内容
3. **验收点表**：基线表 + 增量表合并，按验收点编号（如 A01）去重（增量覆盖同编号行）
4. **非 REQ 区块内容**（如项目概述、角色权限等）：**保留基线版本，不合并**。这些是模块级公共内容，增量文档中若出现是版本上下文，不应覆盖基线

**02-详细设计文档.md 合并**：
1. **REQ 映射表**：基线表 + 增量表合并，按 REQ 编号去重
2. **REQ 详情区块**：按 `##### REQ-xxx` 标题定位，新增的插入到末尾，已存在的替换区块内容
3. **接口清单表**：基线表 + 增量表合并，按接口路径去重
4. **非 REQ 区块内容**（如技术架构概述、页面路由等）：保留基线版本

**03-测试用例文档.md 合并**：
1. **用例表**：基线表 + 增量表合并，按测试编号（如 `FT-BILLCFG-LIST-001`）去重（增量覆盖同编号行）
2. **非用例区块内容**（如测试概述、环境说明等）：保留基线版本

**合并后的区块排序**：
- REQ 详情区块按 REQ 编号自然序排列（LIST-001, LIST-002, LIST-003, FORM-001, FORM-002, DETAIL-001）
- 测试用例按测试编号自然序排列

**合并冲突处理**：

| 场景 | 处理 |
|---|---|
| 增量文档中某 REQ 区块无法在文档中定位到完整边界（标题缺失或格式异常） | 阻断，输出"REQ-xxx 区块边界无法识别，请检查文档格式" |
| 基线文档中某 REQ 区块格式异常（标题缺失或格式异常） | 阻断，输出"基线文档中 REQ-xxx 区块格式异常，建议使用 --full 全量覆盖重置基线" |
| 增量文档中某 REQ 在 01 中有但 02/03 中缺失 | 由 5.2 一致性校验拦截，不进入合并阶段 |

#### 5.3.3 不确定项交用户确认

增量合并涉及文档结构理解，skill 可能遇到无法自动判断的情况。遵循"不确定时交用户确认"原则：skill 输出自己的判断和理由，由用户确认后再执行。

**需要用户确认的场景**：

| 场景 | skill 的判断逻辑 | 用户确认方式 |
|---|---|---|
| 非 REQ 区块内容（项目概述、技术架构、页面路由等）在增量文档中有变化 | skill 默认判断"保留基线版本，不合并"，但输出增量文档中的变化摘要 | skill 输出"检测到非 REQ 区块有变化，默认保留基线版本，变化摘要：{摘要}。是否需要合并？[Y/N]"，用户确认 |
| REQ 区块内除了 REQ 编号相关内容外还有其他变动（如全局约束调整） | skill 默认判断"按 REQ 区块整体替换"，但提示用户注意 | skill 输出"REQ-xxx 区块将整体替换，请注意该区块内还有以下非 REQ 内容变动：{变动清单}"，用户确认后继续 |
| 增量文档中出现基线中不存在的新的表格/章节（非 REQ 区块） | skill 无法判断是新增模块级内容还是版本临时内容 | skill 输出"增量文档中出现新章节：{章节标题}，skill 无法判断是否应纳入基线。是否合并？[Y/N]"，逐项确认 |

**确认流程**：
1. skill 完成所有自动判断后，汇总需要确认的项
2. 一次性输出确认清单（不逐项打断用户）
3. 用户逐项回复 Y/N，或统一回复"全部保留基线"/"全部按增量"
4. 用户确认后，skill 按确认结果执行合并

**合并结果预览**：

合并写入前，skill 输出合并预览摘要：
- 每份文档的新增 REQ 区块数、替换 REQ 区块数
- 非 REQ 区块的保留/合并决策
- 用户确认项的处理结果

用户确认预览后，skill 才写入基线文件。

#### 5.3.4 版本标记头

无论哪种模式，回写后在文档原始标题行之前更新 HTML 注释标记，不影响 Markdown 渲染：

```text
<!-- 最后回写版本: V1.6.1 | 回写日期: 2026-08-13 | 来源: Prds/V1.6.1/01-需求文档.md | 模式: 首次沉淀/增量合并 -->
# 原始标题...
```

**标记头覆盖规则**：若文档头部已存在 `<!-- 最后回写版本:` 标记，替换为最新版本标记，不累积多条。

#### 5.3.5 旧基线不备份

Git 已提供历史追溯，不额外产生 `.bak` 文件。如需对比合并前后的差异，使用 `git diff` 查看。

### 5.4 INDEX.md 格式

模块基线目录下的 `INDEX.md` 记录该模块的文档清单和回写状态：

```markdown
# {模块名称} 基线索引

## 文档清单

| 文档 | 文件名 | 最后回写版本 | 回写日期 | 来源 |
|---|---|---|---|---|
| 需求文档 | 01-需求文档.md | V1.6.1 | 2026-08-13 | Prds/V1.6.1/01-需求文档.md |
| 详细设计文档 | 02-详细设计文档.md | V1.6.1 | 2026-08-13 | Prds/V1.6.1/02-详细设计文档.md |
| 测试用例文档 | 03-测试用例文档.md | V1.6.1 | 2026-08-13 | Prds/V1.6.1/03-测试用例文档.md |

## 回写历史

| 版本 | 回写日期 | 回写人 | 说明 |
|---|---|---|---|
| V1.6.1 | 2026-08-13 | {git user.name} | 首次基线沉淀 |
```

### 5.5 CHANGELOG 更新规则

更新 `Prds/CHANGELOG.md` 中目标版本记录的"主文档回写状态"列：

- 从 `待回写` 改为 `已回写`
- 不删除行、不修改其他列、不新增行
- 若目标版本有多行记录，全部更新为 `已回写`

**边界场景处理**：

| 场景 | 处理 |
|---|---|
| CHANGELOG 中不存在目标版本行 | 停止归档，提示"CHANGELOG 中未找到版本 V1.6.1 的记录，请先在版本流程中创建" |
| 目标版本行的"主文档回写状态"已经是 `已回写` | 作为幂等成功处理，提示"该版本已归档，无需重复操作"，跳过 CHANGELOG 更新但继续执行其余步骤（若基线文档有变动仍回写） |
| 目标版本行的"主文档回写状态"为非 `待回写` 且非 `已回写` 的值 | 停止归档，提示"CHANGELOG 中 V1.6.1 的主文档回写状态为 {当前值}，预期为 待回写 或 已回写，请人工确认" |

## 6. 首次沉淀 vs 增量合并

skill 根据模块基线目录的文件状态自动判断归档模式，用户也可通过 `--full` 强制指定。

### 6.1 判断逻辑

```text
用户指定 --full？
├─ 是 → 全量覆盖模式
└─ 否 → 检查模块基线目录是否有 01/02/03 文件
   ├─ 没有（目录不存在或为空） → 首次沉淀模式（全量覆盖）
   └─ 有 → 增量合并模式（按 REQ 区块合并）
```

### 6.2 两种模式的差异

| 维度 | 首次沉淀模式 | 增量合并模式 |
|---|---|---|
| 触发条件 | 模块基线目录无 01/02/03 文件 | 模块基线目录已有 01/02/03 文件 |
| 回写方式 | 整文件复制覆盖 | 按 REQ 编号区块合并 |
| 用户确认 | 不需要（无歧义） | 需要（不确定项交用户确认，见 5.3.3） |
| 版本标记头模式 | `首次沉淀` | `增量合并` |
| INDEX.md 回写历史说明 | "首次基线沉淀" | "增量合并：新增 {N} 个 REQ，替换 {M} 个 REQ" |

### 6.3 V1.6.1 本次归档

## 7. 与现有 skills 的关系

| 现有 skill | 与 version-archive 的关系 |
|---|---|
| `version-release` | 归档完成后可触发封版；封版阶段一检查归档是否完成 |
| `prd-git-commit` | 归档完成后可选择调用它提交，复用其精确暂存 + 钉钉通知能力 |
| `requirement-doc-bootstrap` 等 | 不冲突，它们负责"生成"，version-archive 负责"回写归档" |
| 无归档能力 | 填补空白，现有 skills 没有任何职责覆盖版本收尾归档 |

### 7.1 与 version-release 的门禁串联

`version-archive` 完成后：
- 输出提示："归档已完成，可执行「封版 V1.6.1」进入版本封版流程"
- 不自动调用 `version-release`

`version-release` 阶段一检查新增门禁：
- 检查模块基线目录的 `INDEX.md` 是否存在
- 检查 `INDEX.md` 中的"最后回写版本"是否等于目标版本号
- 不满足时停止并提示"请先执行版本归档：归档 V1.6.1"

## 8. 边界与非目标

- 不处理 `04/04b/05`（过程文档留在版本目录）
- 不回写 `01b/01c/02b`（版本级补充文档留在版本目录作为版本快照）
- 不备份旧基线（Git 已提供历史追溯）
- 不创建 Git commit 或 Tag（由 `prd-git-commit` 或 `version-release` 负责）
- 不自动推断当前版本
- 不自动创建模块目录（目录不存在时停止并提示）
- 不跨仓库操作（只操作当前治理仓库的 `Prds/` 目录）
- 不做语义级校验（只做编号文本级匹配）
- 不支持多模块版本的拆分回写（当前仅支持单模块，多模块时停止并提示）
- 不对 `02b` 做一致性校验（`02b` 的一致性由 `version-release` 阶段一检查覆盖）
- 不自动决定非 REQ 区块的合并（不确定项交用户确认，见 5.3.3）

## 10. 验证策略

执行完成后至少验证：

- 模块基线目录下 `01/02/03` 文件存在
- **首次沉淀模式**：基线文件内容与版本目录对应文件一致（除版本标记头外）
- **增量合并模式**：
  - 基线文件中包含合并前已有的所有 REQ 区块（未被误删）
  - 基线文件中包含增量文档中所有新增 REQ 区块
  - 基线文件中被替换的 REQ 区块内容与增量文档一致
  - 非 REQ 区块内容按用户确认结果处理
- `INDEX.md` 存在且"最后回写版本"等于目标版本号
- `Prds/CHANGELOG.md` 中目标版本的"主文档回写状态"为 `已回写`
- 归档报告中无阻断项
- 文档头部的版本标记格式正确，模式标注与实际执行模式一致
