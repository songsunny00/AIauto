# 需求-开发-测试一体化协同方案设计

## 1. 背景

当前项目希望把“需求 → 开发 → 测试（UI 自动化 / 接口自动化）”打通，但现状仍存在几个关键断点：

1. 需求、设计、代码、测试资产缺少统一主线，跨阶段追踪主要依赖人工理解。
2. 增量需求容易独立漂移，主需求文档与实际落地口径不容易长期保持一致。
3. `Codes`、`Prds`、`Tests` 三类目录各自成形，但尚未沉淀统一的命名、编号、映射与状态规则。
4. UI 自动化与接口自动化尚未进入同一治理框架，难以支撑后续平台化复用。
5. AI 已可用于局部生成内容，但若没有统一模板、路径和编号体系，只会形成一次性辅助，难以形成稳定方法论。

本设计的目标，不是单独选择某个测试工具，而是建立一套围绕需求资产治理、交付过程编排、测试资产沉淀的协同体系。

## 2. 目标

### 2.1 设计目标

- 以“目录路径 + 功能点编号”建立统一追踪主线。
- 让 `Prds / Codes / Tests / Agents / skills / Templates` 形成清晰分工与稳定接口。
- 建立可落地的需求 → 设计 → 开发 → 测试 → 回填闭环。
- 将 UI 自动化与接口自动化纳入统一测试治理体系。
- 在保持测试框架治理中立的前提下，给出一期可快速落地的推荐技术组合。
- 沉淀出可复用于后续业务域的模板、skill、agent、映射文件和推进规则。

### 2.2 非目标

- 不在当前阶段追求“需求一确认即可全自动产出代码与测试”的高度自动化平台。
- 不强行要求 `Codes` 目录镜像 `Prds` 目录。
- 不一次性治理全部历史项目与存量测试资产。
- 不在当前方案中确定正式试点项目；当前仅有既有小范围验证案例，正式试点项目待汇报会讨论确定。

## 3. 方案结论

采用“**治理主线 + 平台试点型**”方案。

### 3.1 核心结论

1. 用 **目录路径主线** 管模块归属，例如 `CONFIG / REPORTCFG / TYPECFG`。
2. 用 **功能点编号主线** 管具体需求追踪，例如 `REQ-CONFIG-REPORTCFG-TYPECFG-001`。
3. 文档采用“**主文档收敛 + 可选补充文档前置挂载**”结构：
   - 必选：`01-需求文档.md`、`02-详细设计文档.md`、`03-测试用例文档.md`
   - 可选：`01a-增量需求文档.md`、`01b-数据流转设计.md`、`01c-原型文档.md`
4. `03-原型-HTML说明` 之类工艺说明不进入正式交付编号体系，应降级为模板级 guide。
5. `Codes` 保持工程组织，但必须用映射文件建立需求到页面/API/服务的关联。
6. `Tests` 尽量与 `Prds` 目录对齐，便于需求点回查测试资产。
7. AI 的定位是：校验、生成骨架、分析失败、回填结果；不替代业务决策与最终审核。

### 3.2 为什么不直接采用其他方案

#### 方案 B：只做规范治理，不做试点技术落地

优点是投入低，但短期内难体现 AI 与自动化测试的实际价值，领导层面不容易看到可落地成果。

#### 方案 C：直接做高度自动化平台

想象空间大，但对规范成熟度、环境稳定性、测试数据治理和团队配合要求过高，首期实施风险大，不适合作为当前方案。

因此采用“先统一治理主线，再用试点验证平台能力”的路径更稳妥。

## 4. 目录与资产结构设计

### 4.1 顶层目录职责

```text
AIauto/
├─ .agents/                # 外部安装的 agent 资源
├─ Agents/                 # 自定义角色 agent
├─ Codes/                  # 前后端代码与映射
├─ Prds/                   # 需求、增量、原型、设计源头资产
├─ Templates/              # 交付物模板、guide、原型脚手架
├─ Tests/                  # 用例、UI 自动化、接口自动化、报告
├─ skills/                 # 过程技能
├─ docs/                   # 方案、专项说明、全局台账
└─ framework/              # 后续沉淀完整方法框架
```

### 4.2 叶子模块目录建议

以 `TYPECFG-报告类别配置` 为例：

```text
Prds/.../TYPECFG-报告类别配置/
├─ INDEX.md
├─ TRACE.yaml
├─ 01-需求文档.md
├─ 01a-增量需求文档.md      # 可选
├─ 01b-数据流转设计.md      # 可选
├─ 01c-原型文档.md          # 可选
├─ 02-详细设计文档.md
├─ 03-测试用例文档.md
├─ CHANGELOG.md
└─ versions/
```

对应测试目录：

```text
Tests/.../TYPECFG-报告类别配置/
├─ INDEX.md
├─ TRACE.yaml
├─ cases/
├─ ui-automation/
├─ api-automation/
├─ shared/
└─ mappings/
```

### 4.3 建议新增的治理型文件

- `INDEX.md`：说明目录职责、路径编码、下级模块、关联代码与测试。
- `TRACE.yaml`：记录路径、文档、功能点、状态、代码映射、测试映射。
- `Codes/mappings/prd-to-code.yaml`：记录 `REQ -> 页面/API/服务`。
- `Tests/.../mappings/req-test-map.yaml`：记录 `REQ -> FT -> UI/API 脚本`。
- `CHANGELOG.md`：记录模块持续变更、影响功能点和主文档回写状态。
- `04-测试执行记录.md`：记录单次版本或单轮执行的测试结果、失败摘要与回归结论。
- `05-变更记录.md`：记录里程碑版本或对外发布所需的正式变更说明；如暂时没有该类要求，可先不启用。
- `docs/traceability-matrix.md`：项目级总追踪矩阵。

## 5. 命名与编号规则

### 5.1 目录命名规则

统一格式：`英文编码-中文名称`

例如：

- `CONFIG-配置中心`
- `REPORTCFG-报告配置`
- `TYPECFG-报告类别配置`

约束：

- 英文编码全大写。
- 同层级英文编码唯一。
- 功能点编号只引用英文编码，不引用中文名称。

### 5.2 文档编号规则

必选文档：

- `01-需求文档.md`
- `02-详细设计文档.md`
- `03-测试用例文档.md`

可选补充文档：

- `01a-增量需求文档.md`
- `01b-数据流转设计.md`
- `01c-原型文档.md`

可选过程文档：

- `04-测试执行记录.md`
- `05-变更记录.md`

### 5.3 功能点编号规则

格式：`REQ-{L1}-{L2}-{L3}-{NNN}`

示例：`REQ-CONFIG-REPORTCFG-TYPECFG-001`

规则：

- 同一叶子模块内从 `001` 开始顺序递增。
- 删除后不回收编号。
- 新增功能续号；修改已有功能沿用原编号。

### 5.4 测试编号规则

- 测试用例：`FT-CONFIG-REPORTCFG-TYPECFG-001`
- 自动化脚本：`ATS-CONFIG-REPORTCFG-TYPECFG-001.spec.ts`

### 5.5 增量需求回写规则

采用“**独立存档 + 同步回主文档 + 保留变更记录**”机制：

1. 增量需求先独立存在于 `01a` 或 `versions/`。
2. 明确影响的路径与功能点编号。
3. 落地确认后同步回 `01-需求文档.md`。
4. 在 `CHANGELOG.md` 或 `TRACE.yaml` 中保留回写留痕。

## 6. 流程闭环设计

将需求 → 开发 → 测试设计为 7 个阶段：

1. 需求基线化
2. 补充设计（按需触发 `01a/01b/01c`）
3. 详细设计
4. 开发实现
5. 测试设计与自动化生成
6. 执行回归与结果回填
7. 版本关闭与主文档回写

### 6.1 阶段职责摘要

- **产品/业务**：主需求、功能点、验收标准、增量确认
- **开发/架构**：详细设计、代码实现、代码映射
- **测试**：测试点、自动化范围、执行审核、缺陷闭环
- **AI 协同层**：文档校验、影响分析、任务拆解、脚本骨架、失败分析、结果回填

### 6.2 必须自动回填的 4 类信息

1. `REQ -> 页面/组件/API/服务`
2. `REQ -> FT -> ATS`
3. `版本 -> 受影响功能点 -> 受影响代码/测试`
4. `功能点 -> 测试状态 -> 失败原因 -> 关闭状态`

## 7. 测试技术选型

### 7.1 UI 自动化三方案

1. **Playwright + skill + AI**：首期最推荐，稳定性、诊断能力、AI 协同能力强。
2. **Cypress + skill + AI**：上手快，但复杂企业后台、多场景治理略弱。
3. **Selenium/WebDriver + skill + AI**：兼容历史资产，但维护成本高。

UI 推荐顺序：`Playwright > Cypress > Selenium/WebDriver`

### 7.2 接口自动化三方案

1. **Playwright API + skill + AI**：首期最推荐，投入低、与 UI 一体化强。
2. **Pytest + requests/httpx + skill + AI**：长期专业性最强，适合二期深化。
3. **Postman/Newman 或 Apifox/OpenAPI + skill + AI**：协作展示友好，但复杂断言灵活性一般。

接口推荐顺序：

- 一期试点：`Playwright API > Pytest > Postman/Apifox`
- 长期深化：`Pytest > Playwright API > Postman/Apifox`

### 7.3 综合推荐

一期综合推荐：

> **Playwright(UI) + Playwright(API) + skill + AI**

原因：

- 投入最低，见效最快。
- 最适合先跑通 `Prds -> Codes -> Tests` 闭环。
- 最便于沉淀统一目录、模板、skill 和回填机制。
- 一期不直接选用 `Pytest(API)`，核心原因是避免首期进入双技术栈治理，降低落地阻力。

二期演进方向：

> **Playwright(UI) + Pytest(API) + skill + AI**

建议在以下条件出现后再演进：
- 接口自动化数量明显增加
- 复杂断言与数据编排场景增多
- 需要更细的接口分层治理与更强的 Python 测试生态支持

## 8. 汇报与落地交付物

本次方案应输出两份正式文稿：

1. `docs/需求开发测试一体化-领导汇报版.md`
2. `docs/需求开发测试一体化-落地蓝图版.md`

其中：

- 领导汇报版强调背景、目标、总体方案、收益、风险和阶段计划。
- 落地蓝图版强调目录、编号、流程门禁、agent/skill 分工、测试方案、元数据设计与推进步骤。

## 9. 风险与边界

- AI 生成质量依赖模板规范、页面语义和接口信息质量。
- UI 自动化稳定性依赖前端可测性规范，如 `data-testid` 和稳定 DOM 标识。
- 接口自动化稳定性依赖测试环境、账号、测试数据和权限配合。
- 增量需求回写需要流程约束，不能只依赖工具。
- 正式试点项目当前保持“待定”，在汇报会上讨论，不在本方案内写死。

## 10. 实施建议

### 10.1 第一阶段：规范落地

- 统一目录、编号、模板、TRACE 元数据结构。
- 调整 `Templates` 中交付物模板与 guide 的职责边界。
- 明确 `01a/01b/01c` 触发条件。

### 10.2 第二阶段：业务域试点

- 在已具备小范围验证经验的基础上，选定一个正式试点项目。
- 跑通一条真实需求从 `01` 到 `03`、再到 UI/API 自动化与结果回填的闭环。

### 10.3 第三阶段：能力复制

- 沉淀通用 skill、agent、映射模板、执行报告模板。
- 复制到更多业务域。

## 11. 结论

这套方案的本质不是新增一个测试工具，而是建立一套以“需求路径 + 功能点编号”为主线、由 AI 辅助编排的需求—开发—测试一体化协同体系。它既服务于流程治理，也服务于后续的平台化复用。
