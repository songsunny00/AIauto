# 增量需求文档模板设计

## 1. 背景

当前 `framework/` 已经具备完整需求文档模板 `01-需求文档.md`，并且在其中定义了稳定的功能点编号、版本字段、需求类型、当前状态、验收编号与追踪矩阵。这解决了全量基线的问题，但对于增量需求场景仍有两个缺口：

1. 缺少一份专门面向“本次改动”的输入文档，导致每次增量评审都要在全量文档里定位变化，阅读成本高。
2. 缺少一套结构化的“回写全量 01”规则，导致增量需求虽然能被讨论，但不容易稳定合并回全量需求基线，也不利于后续 04 详细设计、开发和测试聚焦本次变化。

本设计的目标是新增一份适配增量场景的文档模板，同时保持 `01-需求文档.md` 仍然是全量需求的唯一稳定基线。

## 2. 目标

### 2.1 设计目标

- 为增量需求提供一份独立、轻量、可评审的输入文档。
- 明确增量需求如何回写到全量 `01-需求文档.md`。
- 让 `04-详细设计文档.md` 在增量场景下既能聚焦本次变化，又不丢失全局上下文。
- 让开发、测试可以快速识别本次需求对路由、接口、字段、权限、状态的影响范围。

### 2.2 非目标

- 不替代现有全量 `01-需求文档.md`。
- 不新增第三套需求编号规则。
- 不在增量文档中展开数据库表结构、后端接口完整定义、前端组件实现细节。

## 3. 方案结论

采用“**独立增量文档 + 回写全量 01 规则**”方案。

### 3.1 文档定位

新增文档：

- 模板：`framework/templates/01a-增量需求文档.md`
- Prompt：`framework/prompts/01a-增量需求文档.prompt.md`
- 产出：`docs/01a-增量需求文档.md`

定位如下：

- `01-需求文档.md`：全量需求基线，沉淀当前版本系统完整业务事实。
- `01a-增量需求文档.md`：本次迭代变更合同，只描述“改了什么、为什么改、影响什么、如何回写基线”。

### 3.2 为什么不用另外两种方案

#### 方案 B：直接在全量 01 中表达本次增量

优点是只有一个文档，但会把“基线事实”和“本次改动”混在一起，使增量评审、AI 生成和开发阅读都难以聚焦本次变化。

#### 方案 C：只做变更清单，不展开正文

优点是最轻，但信息太薄，无法稳定指导后续 04 详细设计，也不足以支撑开发和测试评估影响面。

因此保留全量基线 + 独立增量输入的双文档结构更稳妥。

## 4. 文档链路调整

### 4.1 全新需求链路

`01 → 02（可选）→ 03 → 04 → 06`

### 4.2 增量需求链路

`01a → 回写 01 → 02（必要时）→ 03 → 04 → 06`

补充说明：

- 对于增量需求，`01a` 是本次变更输入。
- 回写后的 `01` 仍然是后续全局追踪与下游设计的稳定基线。
- `01a` 的主要作用是帮助回写 `01`，并在 `03/04` 生成时作为本次差异范围的辅助参考。
- `03` 与 `04` 在增量场景下的主要上游应为已回写后的 `01`；如需聚焦本次变化，可额外参考 `docs/01a-增量需求文档.md` 做差异审计。
- 如果本次增量不影响数据流、状态机、权限过滤等复杂关系，则 `02-数据流转设计.md` 仍为可选；需要时再补充进入链路。
- `04b-后台文档.md` 与 `04c-前端文档.md` 的定位不变，仍然是 `04` 之后的可选实现阶段文档。

## 5. 编号与版本规则

`01a` 完全复用 `01` 已有的编号和版本规则，不新增新的编码体系。

### 5.1 功能点编号规则

- 一级页面功能：`REQ-{模块编码}-{一级页面编码}-{序号}`
- 二级页面 / Tab / 弹窗 / 抽屉功能：`REQ-{模块编码}-{一级页面编码}-{二级页面编码}-{序号}`

### 5.2 增量场景下的使用规则

- **新增功能**：创建新编号。
- **修改功能**：必须沿用原编号。
- **删除功能**：表示本次版本明确移除某项能力；仍必须沿用原编号，不得直接删行。
- **废弃功能**：表示该能力不再推荐继续使用或演进；仍必须沿用原编号，不得直接删行。

### 5.3 版本字段规则

- `引入版本`：功能首次出现的版本，新增时填写本次版本，修改/删除/废弃时保持原值。
- `最近变更版本`：本次涉及变更的版本。
- `需求类型`：新增 / 修改 / 删除 / 废弃。
- `当前状态`：草稿 / 已确认 / 已实现 / 已废弃。
- 删除场景的统一口径：`需求类型=删除`，`当前状态=已废弃`。

## 6. 01a 模板结构设计

`01a` 不照搬全量 `01` 的完整结构，而使用“变更导向”的章节组织，使其既适合评审，又适合后续回写与设计展开。

### 6.1 第 0 章 使用说明

应明确：

- 上游输入：用户原始变更诉求、当前全量 `01`、必要时已有 `03/04`。
- 下游消费者：全量 `01` 回写、`04` 详细设计、开发、测试。
- 产出原则：只描述本次变化，不重写无关基线事实；所有字段口径与角色编码必须沿用现有基线。
- 命名约定：输出到 `docs/01a-增量需求文档.md`。

### 6.2 第 1 章 变更概述

建议字段：

- 需求标题
- 所属版本
- 变更背景
- 变更目标
- 变更类型（可多功能点分别体现）
- 影响模块
- 是否影响数据流 / 状态 / 权限
- 是否需要补充 `02 / 04b / 04c`
- 本次 `03-原型文档` 需要覆盖的页面/交互范围

这一章负责帮助读者快速判断本次变更的复杂度和需要触发的下游文档。

### 6.3 第 2 章 本次范围与边界

建议包含：

- 本次包含
- 本次不包含
- 容易被误解但明确不在范围内的边界

这一章的目的，是防止增量需求在后续详设与开发阶段被顺手扩张。

### 6.4 第 3 章 变更清单

这是 `01a` 的核心索引章节。每条记录对应一个功能点的变更动作。

建议字段：

- 变更操作（新增 / 修改 / 删除 / 废弃）
- 功能点编号
- 菜单名
- 一级页面
- 二级页面/区域
- 功能名称
- 变更摘要
- 变更原因
- 影响角色
- 影响验收编号
- 是否影响详设
- 是否影响测试用例
- 是否影响前端路由
- 是否影响后端接口
- 是否影响字段契约
- 是否影响权限/数据范围

本章的作用是让 AI、开发、测试能快速获得影响面总览。

### 6.5 第 4 章 逐功能点增量说明

每个功能点必须单独展开，标题格式为：

`#### {功能点编号} {功能名称}`

每个功能点建议固定包含：

- 变更类型
- 引入版本
- 最近变更版本
- 当前状态
- 变更前
- 变更后
- 不变部分
- 业务规则变化
- 交互变化
- 业务字段变化
- 业务状态变化（如有）
- 权限变化
- 对历史数据影响
- 对路由/接口/呈现形式的影响
- 关联验收编号

其中 **变更前 / 变更后 / 不变部分** 是增量场景下最关键的结构：

- `变更前` 用于说明当前基线事实是什么。
- `变更后` 用于说明本次目标状态是什么。
- `不变部分` 用于显式约束 AI 和开发不要误改无关行为。

### 6.6 第 5 章 回写全量 01 说明

该章是 `01a` 成为“可合并文档”的关键。

建议按规则写清楚：

- 新增功能：回写到全量 `01` 第 5 章功能清单，并补充第 6 章对应功能点正文。
- 修改功能：在全量 `01` 中定位原编号，更新功能描述、业务规则、字段、状态、验收关联，并刷新 `最近变更版本`。
- 删除功能：在全量 `01` 中保留原编号，将 `需求类型` 更新为 `删除`、`当前状态` 更新为 `已废弃`，不删除原记录。
- 废弃功能：在全量 `01` 中保留原编号，将 `需求类型/当前状态` 更新为废弃相关值，不删除原记录。
- 如果本次新增或修改验收标准，同步更新全量 `01` 第 10 章。
- 如果字段口径变化，同步更新全量 `01` 附录字段映射。
- 只要本次涉及的功能点发生变化，就必须同步更新全量 `01` 附录 A 需求功能点追踪矩阵。

### 6.7 第 6 章 增量验收标准

应针对本次变更单独给出验收编号、关联需求编号和验收条件，确保后续 `04` 与 `06` 可以聚焦本轮改动。

### 6.8 附录：回写任务清单 / 一致性检查清单

建议至少包含两类附录：

1. **回写任务清单**：列出本次需要更新全量 `01` 的章节和功能点编号。
2. **一致性检查清单**：检查编号复用、版本字段、角色/权限口径、影响面标记、回写项是否完整。

## 7. 对 04 详细设计与开发者的友好性要求

为了让 `01a` 不只对产品评审友好，也能直接帮助后续详设和开发，需要在模板中强制表达“技术影响方向”，但不进入实现细节。

建议固定要求每条变更说明回答以下四个问题：

- 是否新增或调整前端路由？
- 是否新增或调整后端接口？
- 是否新增或调整字段契约？
- 是否影响权限或数据范围？

这样 `04` 可以快速判断本次变更属于：

- 纯业务规则变更
- 页面交互变更
- 接口契约变更
- 权限/数据范围高风险变更

开发者也能据此更快定位是否需要联动 `04b`、`04c`、测试用例或数据迁移。

## 8. 与现有模板的协同规则

### 8.1 与 01-需求文档 的关系

- `01` 是全量稳定基线。
- `01a` 是本次增量变更合同。
- 任何增量需求最终都必须回写 `01`，不能只停留在 `01a`。

### 8.2 与 03-原型文档 的关系

- `03` 在增量场景下只需要覆盖本次受影响页面或交互。
- `01a` 需要明确指出哪些功能点需要补原型。

### 8.3 与 04-详细设计文档 的关系

- `04` 在增量场景下的主要上游应为已回写后的 `01`。
- `01a` 用于帮助 `04` 快速识别本次受影响功能点与差异范围，但不替代全量 `01` 的基线角色。

### 8.4 与 06-测试用例文档 的关系

- `06` 依然主要依据 `04` 生成。
- 但 `01a` 提供本次变更功能点清单、影响验收编号和高风险影响面，可帮助测试缩小重点回归范围。

## 9. README 与 Prompt 的配套修改建议

如果实施本方案，需要同步修改：

1. `framework/README.md`
   - 增加 `01a-增量需求文档` 的定位。
   - 增加“增量需求链路”说明。
   - 在模板/Prompt 总览表中增加 `01a`。
   - 明确 `01` 仍是全量基线，`01a` 是差异输入与回写来源。

2. `framework/templates/01-需求文档.md`
   - 补充增量场景下的基线回写规则，明确全量 `01` 的更新来源是“现有全量 01 + 已批准的 01a”。
   - 在一致性检查中加入增量回写后的版本字段、需求类型、追踪矩阵同步要求。

3. `framework/templates/01a-增量需求文档.md`
   - 承载增量规则主体，包括变更清单、逐功能点增量说明、回写全量 01 说明、回写任务清单、一致性检查清单。
   - 明确必须复用已有需求编号规则，只写本次变化，不重写无关基线。

4. `framework/templates/03-原型文档.md`
   - 明确增量场景下的主要输入为“已回写全量 01”，必要时参考 `01a` 聚焦差异范围，`02` 为可选输入。
   - 明确只覆盖本次受影响页面、弹窗、抽屉、Tab 和关键交互，不按全量 `01` 全量重写原型。

5. `framework/templates/04-详细设计文档.md`
   - 明确增量场景下的主要输入为“已回写全量 01”，必要时参考 `01a` 做差异审计，`02` 为可选输入。
   - 保持 `04b/04c` 仍为 `04` 之后的可选实现阶段文档。

6. `framework/prompts/01-需求文档.prompt.md`
   - 与模板保持一致，只补充增量场景下的输入说明：不能直接根据原始变更诉求重写全量 `01`，而应基于“现有全量 01 + 已批准的 01a”生成更新后的全量基线。

7. `framework/prompts/01a-增量需求文档.prompt.md`
   - 与 `01a` 模板保持一致，强调复用编号规则、只写本次变化、必须产出回写说明与回写任务清单。

8. `framework/prompts/03-原型文档.prompt.md` 与 `framework/prompts/04-详细设计文档.prompt.md`
   - 只同步输入优先级与增量适用范围，不在 Prompt 中重复扩展模板已经定义的主体规则。
   - Prompt 保持轻量，只负责角色、输入、任务、约束和输出编排，不复制模板章节结构。

## 10. 实施验收标准

方案落地后，应满足以下标准：

- 存在独立的 `01a-增量需求文档` 模板与 Prompt。
- README 中清楚说明全新需求链路与增量需求链路。
- `01a` 明确要求复用现有功能点编号和版本规则。
- `01a` 包含结构化的变更清单、逐功能点增量说明、回写全量 01 规则、增量验收标准。
- `01a` 能让读者明确识别路由、接口、字段、权限、数据范围的影响方向。
- `01a` 生成后，能据文档内容稳定回写到全量 `01`，且不丢失历史编号与版本信息。
- `04` 与后续开发、测试可以仅聚焦本次受影响功能点，同时保留对全局基线的引用。

## 11. 最终决策

最终采用以下规则：

1. `01-需求文档.md` 是全量需求基线。
2. `01a-增量需求文档.md` 是本次变更输入与评审文档。
3. 增量需求下，必须先产出 `01a`，再将变化回写到 `01`。
4. `04` 在增量场景下以已回写后的 `01` 为主要上游，必要时参考 `01a` 进行本次差异审计。
5. 修改/删除/废弃功能必须沿用原需求编号，新增功能才新建编号。
6. `01a` 只写变化和影响，不重写无关基线内容。
