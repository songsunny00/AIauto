# 版本封版与 Git 标记设计

## 1. 背景与目标

当前需求—开发—测试流程在版本关闭阶段要求回写版本文档和 `Prds/CHANGELOG.md`，但没有统一约束 Git 提交和版本 Tag。与此同时，`Prds/CHANGELOG.md` 中混有版本过程性变更，无法直接作为已封版版本台账。

本设计新增独立的 `version-release` Skill，提供版本封版入口，确保封版动作完成以下闭环：

- 校验版本交付物和主文档回写状态；
- 将 `Prds/CHANGELOG.md` 收敛为已封版版本台账；
- 汇总并精确提交可归属当前版本的文档、代码、测试和治理变更；
- 创建并推送 annotated Tag，例如 `Tag-V1.6.1`；
- 对无法归属当前版本的变更、Tag 冲突和远程操作失败进行安全拦截。

## 2. 已确认的决策

### 2.1 独立 Skill

新增 `skills/version-release/SKILL.md`，不把封版职责并入现有 `prd-git-commit`。现有 Skill 继续面向 `Prds/` 文档日常提交；新 Skill 面向完整版本封版，允许处理版本相关的 `Prds/`、`Codes/`、`Tests/` 和治理文档。

### 2.2 Tag 规则

版本号以 `Vx.y.z` 形式传入并规范化。Tag 固定为 `Tag-Vx.y.z`，使用 annotated tag，指向封版 commit，并在用户确认后推送当前分支和 Tag。已有同名 Tag 时停止，禁止覆盖或强推。

### 2.3 CHANGELOG 规则

`Prds/CHANGELOG.md` 只记录已经封版的版本，不记录需求变更过程。文件必须使用现行固定表头，列名和顺序均不得变更：

```text
版本号 | 变更日期 | 变更类型 | 影响模块 | 主需求文档 | 详细变更记录 | 主文档回写状态 | 测试状态 | 发布状态 | 备注
```

其中 `变更日期` 在最终封版行中表示正式封版日期。封版时按 Markdown 表格解析记录：第一列 `版本号` 必须是规范化版本号的精确匹配，`发布状态` 列必须存在且为单元格文本的精确值。

普通封版模式执行以下规则：

1. 只处理第一列与目标版本号完全相等的记录，不按前缀、模糊文本或备注内容匹配；
2. 目标版本记录中，`发布状态` 不等于 `已封版` 的记录视为过程性记录并删除；
3. 目标版本记录中，`发布状态=已封版` 的记录视为已封版冲突，普通模式停止；
4. 目标版本存在重复的最终记录、缺少必需列、列数不一致或无法解析的行时停止，不尝试猜测或重排；
5. 保留其他版本的记录，不在本次封版中迁移或清理历史台账；
6. 写入目标版本唯一的一条最终封版记录；
7. 需求变更过程继续保留在版本目录下的 `05-变更记录.md`。

如果目标版本已经存在带目标 Tag 名的记录，普通模式同样停止。这样可以避免按版本号误删历史记录，也避免重复封版。

最终记录至少包含上述固定表头的全部字段；其中 `发布状态` 为 `已封版`，`备注` 包含目标 Tag 名。

## 3. 用户流程

### 3.1 触发

普通封版支持以下意图：

- `/version-release V1.6.1`
- `封版 V1.6.1`
- `关闭版本 V1.6.1`

缺少版本号时不推断"当前版本"，要求用户明确指定。

如果上一次封版已创建本地 commit 或 Tag，但在推送阶段中断，只允许通过显式恢复入口继续：

- `/version-release --resume V1.6.1 --commit <完整 commit hash>`

恢复入口必须同时提供完整 commit hash；Skill 校验该 commit 的 subject、父提交、目标版本文件清单、CHANGELOG 最终内容和本地 Tag 指向均与封版预览/记录一致。恢复入口不重新生成 CHANGELOG 或 commit，只处理尚未完成的 Tag/分支推送；任一校验不一致都停止并要求人工处理。

### 3.2 三阶段执行

#### 阶段一：检查

只读检查，不修改文件：

- 确认当前目录位于 Git 工作区；
- 读取当前分支、其 upstream 对应的远程和 Git 用户；没有 upstream 时停止，不猜测推送远程；如果 upstream 无法唯一解析，或配置多个远程但目标不明确，停止并要求用户显式指定唯一推送远程；
- 在任何写操作前记录 `HEAD`、索引状态、工作区状态、目标远程名称、upstream 分支和远程 Tag 状态；
- 要求 Git 索引为空（`git diff --cached --name-status` 无输出）。已有暂存变更必须由用户先提交、取消暂存或明确处理，Skill 不会为了封版擅自改写既有索引；
- 定位 `Prds/V1.6.1/` 及其实际存在的版本资产；
- 读取 `01`、`03`、`04b`、`04`、`05`、`Prds/CHANGELOG.md` 等相关文档；
- 检查主需求文档回写、测试结论、变更记录和 REQ/测试关联；
- 检查 `Tag-V1.6.1` 在本地和上游远程是否已经存在；
- 检查版本归档是否已完成：读取目标版本涉及模块的基线目录下 `INDEX.md`，确认其存在且"最后回写版本"等于目标版本号；不满足时停止并提示"请先执行版本归档：归档 V1.6.1"。详见 `docs/superpowers/specs/2026-08-13-version-archive-design.md`。

任一封版门禁不满足时停止，不自动修改需求、设计、测试报告或代码。

#### 阶段二：预览

向用户展示并请求一次明确确认：

- 版本资产和门禁结果；
- `CHANGELOG` 过程行清理及最终行预览；
- 纳入提交的文件清单；
- 排除的文件清单和排除原因；
- 无法判断归属、需要用户处理的文件；
- commit subject/body；
- Tag 名、Tag message 和推送目标。阶段二预览结果必须持久化到当前仓库的 `.claude/version-release/` 目录，并纳入 `.gitignore`；文件至少记录版本号、原始 HEAD、预览文件清单及其 blob/status 摘要、CHANGELOG 预览摘要、封版 commit 预期 subject、目标 commit 预期父提交、目标 Tag、目标远程和 upstream ref。该文件只用于本地恢复校验，不得提交到版本 commit。

如果仓库不允许写入该本地状态目录，则禁止执行可跨会话恢复的推送流程，只能在当前会话完成或停止。

用户确认后按顺序执行：

1. 再次读取并比对 `HEAD`、索引、工作区、目标远程和远程 Tag 状态；如果自预览后发生变化，回到检查阶段，不使用过期清单；
2. 更新 `Prds/CHANGELOG.md`；
3. 使用精确路径暂存版本相关文件；
4. 暂存后重新读取 index，确认 index 只包含预览清单中的文件，且不含敏感文件、其他版本或未归属文件；发现异常立即停止并恢复本次新增暂存，不触碰检查前已有状态；
5. 创建一次封版 commit；
6. 创建 annotated Tag；
7. 重新读取本地和目标远程 Tag；普通封版要求目标远程不存在同名 Tag，否则停止；仅显式 `--resume` 恢复模式允许在确认远程同名 Tag 与本地 Tag 解引用后指向同一 commit 时补推或视为已同步；先推送当前分支到预览中记录的 upstream，再推送同一远程上的 Tag；
8. 验证 commit、Tag、工作区和远程状态；
9. 输出结果报告。

推送 Tag 属于远程可见且难以撤销的操作，必须经过预览确认。

## 4. 版本文件归属

### 4.1 默认纳入范围

- `Prds/V1.6.1/**`；
- `Prds/CHANGELOG.md`；
- 当前治理仓库内 `Codes/**` 中可通过 `prd-to-code.yaml`、路径、REQ 或模块引用关联到 `V1.6.1` 的变更；
- 当前治理仓库内 `Tests/**` 中可通过路径、文件名、测试报告、REQ 或模块引用关联到 `V1.6.1` 的变更；
- 用户在预览前明确指定且可说明与本版本关联的当前仓库治理文档。

### 4.2 归属证据与优先级

文件纳入必须至少满足一项可复核证据：

1. 文件路径位于目标版本目录；
2. 文件路径、文件名或内容包含目标版本号、目标模块或已存在的 `REQ`；
3. `Codes/mappings/prd-to-code.yaml` 将文件映射到目标 `REQ`；
4. 用户在预览阶段明确指定文件并说明关联原因。

证据优先级为：版本目录/显式版本号 > REQ 映射 > 模块引用 > 用户说明。多个证据冲突时列入待确认清单，不自动纳入。重命名和删除按 Git 的源路径与目标路径分别展示，只有两端都能建立关联时才纳入；否则暂停处理。

本 Skill 只操作当前治理仓库的工作区。若 `Codes/`、`Tests/` 是外部仓库或路径映射，不在当前 Git 工作区内，Skill 只在封版报告中列出其状态，不跨仓库提交、创建 Tag 或推送；外部仓库必须在各自仓库单独执行对应封版流程。

### 4.3 默认排除范围

- `.env`、认证态、缓存、`node_modules` 和临时测试工件；
- 无法通过上述证据建立关联的变更；
- 其他版本目录的变更。

归属不明确的文件进入待确认清单，不得由 Skill 猜测并自动提交。禁止使用 `git add .` 或 `git add -A`。

## 5. Git 操作设计

### 5.1 提交信息

采用单一封版 commit：

- subject：`release: 封版 V1.6.1`；
- body：版本范围、测试结论、文档回写状态和 Tag 名。

### 5.2 Tag

封版 commit 成功后，必须显式将 Tag 创建在该 commit 上：

```text
git tag -a Tag-V1.6.1 <封版 commit hash> -m "封版 V1.6.1"
```

创建后校验 `Tag-V1.6.1^{}` 与封版 commit hash 完全一致，再按预览中记录的唯一目标远程推送当前分支和 Tag。禁止强推、覆盖 Tag、删除分支或为了恢复失败而执行破坏性回滚。

### 5.3 失败状态与幂等恢复

- CHANGELOG 更新失败：不执行 Git 操作；
- 暂存后发现 index 不符合预览清单：停止并只取消本次新增暂存，保留检查前已有状态；
- commit 失败：保留未提交变更并报告；
- Tag 创建失败：保留本地 commit 并报告；
- 分支推送失败：保留本地 commit/Tag，并报告目标远程分支未同步；重试前重新检查目标远程分支是否已包含该 commit，禁止盲目重复推送；
- Tag 推送失败：保留本地 Tag，并报告目标远程 Tag 未同步；重试前重新检查目标远程同名 Tag，只有目标远程不存在或指向同一对象时才允许继续；
- 远程同名 Tag 在检查与推送之间出现且指向不同对象：停止，保留本地状态，要求人工处理；
- 用户取消确认：不修改文件。

封版恢复以显式 `--resume <version> --commit <完整 hash>` 为唯一入口：Skill 先验证该 hash 的 commit subject、父提交、文件清单、CHANGELOG 最终内容、目标本地 Tag 指向和预览时记录的目标远程完全一致，再根据远程实际状态补推尚未完成的分支或 Tag；普通封版遇到已封版记录直接停止，不自动转入恢复。恢复不重复创建 commit，不覆盖已有 Tag。

## 6. 验证策略

执行完成后至少验证：

- `git diff --check` 通过；
- 当前版本在 `Prds/CHANGELOG.md` 中只有一条最终记录；
- Tag 存在且解引用后的 commit 与封版 commit hash 完全一致；
- commit 文件列表不含敏感文件、其他版本文件和未归属变更；
- 本地分支、远程分支和远程 Tag 状态符合预期；
- 版本文档之间的回写和 REQ/测试关联仍可追溯。

仓库没有现成文档结构校验脚本时，不新增无关测试工程，只执行 Git 和文本级验证。

## 7. 与现有流程的边界

- `version-release` 只响应明确包含"封版/关闭版本"和版本号的指令；普通"提交需求""更新 PRD"继续由 `prd-git-commit` 处理。
- `version-archive` 负责版本归档与基线回写，在封版前执行；`version-release` 阶段一检查归档是否完成，未完成时阻断封版。两个 skill 独立触发，不互相调用。
- 两个 Skill 不互相调用，也不重复追加 `05-变更记录.md`；封版只消费已完成的 `05`，不把日常提交流程改造成封版流程。
- 若当前仓库配置了外部 `Codes/`、`Tests/` 映射，阶段 7 只核对其可见状态和关联证据，不能把外部仓库的 commit/tag/push 假设为当前仓库已完成。
- `04b-测试执行记录.md` 提供逐项执行事实，`04-测试报告文档.md` 提供版本结论；封版门禁要求二者存在时相互一致，若只有 `04b` 而没有版本汇总结论，不能直接判定测试完成。

## 8. 需要同步的文档

实现阶段同步以下入口：

- 新增 `skills/version-release/SKILL.md`；
- 更新 `skills/README.md`，登记职责和边界；
- 更新 `docs/需求开发测试一体化-落地蓝图版.md`，将 commit、Tag 和 CHANGELOG 最终台账纳入阶段 7；
- 更新 `Templates/README.md` 和 `Prds/README.md`，统一封版台账口径；
- 按实际封版执行更新 `Prds/CHANGELOG.md`。

本设计不改变现有 `prd-git-commit` 的职责，也不自动迁移历史版本台账。

## 9. 非目标

- 不自动修复未完成的需求、设计、测试或代码；
- 不替代日常需求文档提交；
- 不自动推断当前版本；
- 不覆盖已存在的 Tag；
- 不清理与本次封版无关的工作区变更；
- 不将需求变更过程复制到系统级 `CHANGELOG.md`。
