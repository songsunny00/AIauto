# 需求-开发-测试一体化协同方案（领导汇报版）

## 一、背景与问题

当前团队在需求、开发、测试协同上已经积累了部分基础能力，但仍存在几个典型问题：

1. **需求不够清晰**：需求描述、边界、验收口径有时不够统一，导致后续理解偏差。
2. **沟通成本较高**：需求、开发、测试之间经常需要反复确认，信息在多人之间来回传递。
3. **查找对应需求点困难**：从页面、代码、测试脚本回查到具体需求点不够直接，影响定位和追踪效率。
4. **开发质量不够稳定**：同类需求在实现质量、交付完整性、回写程度上容易出现波动。
5. **测试问题较多**：测试执行中经常暴露出理解偏差、遗漏场景、环境依赖、回归不充分等问题。
6. **人力重复性测试投入高**：大量回归、重复验证仍主要依赖人工，效率和稳定性都受影响。

## 二、建设目标

本方案聚焦两个方向：**流程治理** 与 **平台化复用**。

### 目标 1：统一需求主线
以“目录路径 + 功能点编号”串联需求、设计、代码、测试资产。

### 目标 2：建立交付闭环
让需求、开发、测试三类资产持续回填、可追踪、可审计。

### 目标 3：沉淀平台能力
把标准模板、自动化助手、测试脚本组织方式沉淀为可复制框架。

## 三、总体方案

### 1. 双主线治理
- **目录路径主线**：解决模块归属问题，例如 `CONFIG / REPORTCFG / TYPECFG`
- **功能点编号主线**：解决具体需求追踪问题，例如 `REQ-CONFIG-REPORTCFG-TYPECFG-001`

### 2. 文档体系收敛
- 必选主文档：`01-需求文档.md`、`02-详细设计文档.md`、`03-测试用例文档.md`
- 可选补充文档：`01b-数据流转设计.md`、`01c-原型文档.md`
- 系统级版本目录默认直接维护 `01-需求文档.md`，不要再并行维护额外的版本需求正文
- 其中 `01c-原型文档.md` 用于在已有独立 HTML 原型或设计稿时，说明原型路由与需求模块映射、前端交互要求和界面风格约束
- 原型脚手架资源不进入正式编号体系

### 3. 代码与测试资产治理
- `Codes` 保持工程组织，不强制镜像需求目录
- `Tests` 尽量与 `Prds` 对齐，便于按需求回查测试资产
- 通过映射文件建立 `需求 -> 代码 -> 测试` 的结构化关系

### 4. AI 的定位
AI 不替代业务决策和最终审核，主要承担：
- 文档校验
- 影响分析
- 任务拆解
- 测试骨架生成
- 失败分析
- 结果回填

## 四、目录与资产结构

建议围绕下列目录建立统一分工：

```text
AIauto/
├─ Prds/        # 需求、增量、原型、详设源头资产
├─ Codes/       # 前后端代码与映射
├─ Tests/       # 用例、UI 自动化、接口自动化、报告
├─ Agents/      # 角色型 agent
├─ skills/      # 过程技能
├─ Templates/   # 交付物模板、治理模板、原型脚手架
└─ docs/        # 方案、专项说明、全局台账
```

重点不是“多建几个目录”，而是让每类目录承担稳定职责，并通过索引与映射文件串起来。

### 4.1 推荐协作载体：IDE + Git 多仓协作

建议整个流程以 **TRAE / qOder / 其他支持 AI 的 IDE + Git 仓库** 为统一协作载体。

推荐原因：

- 需求、开发、测试可以在同一工作区查看同一套公共信息，减少信息分散带来的沟通成本。
- 需求文档、代码、测试脚本、版本记录可以通过 Git 持续留痕，便于追踪责任、变更和回归状态。
- 多仓模式既能兼容前端仓、后端仓、测试仓独立管理的现实，也能通过系统治理仓保留统一入口。
- 对 AI 而言，统一工作区比零散聊天记录和私有文档更容易形成稳定上下文，便于做影响分析、脚本生成和结果回填。
- 借助成熟 IDE 落地更简单：这类 IDE 的配套能力更成熟、更新更快，需求、开发、测试团队可以直接站在现成能力和生态之上推进，而不是从零自建一整套协作与智能辅助工具。
- 对管理侧而言，更容易沉淀公共规则、共享模板和项目级总览台账，而不是依赖个人经验推动协作。

推荐口径：

- 一个系统优先使用一个系统治理仓
- `Prds/`、`Codes/`、`Tests/`、`Templates/`、`skills/`、`Agents/`、`docs/` 继续作为统一理解需求、代码、测试关系的逻辑视图
- 其中 `Codes/`、`Tests/` 在物理落地时可以分别映射到外部仓，例如 `repos/frontend-repo`、`repos/backend-repo`、`repos/test-repo`
- 需求、开发、测试都在同一工作区里理解同一套资产关系，再通过各自仓库的分支和 PR 管理变更
- 公共信息默认沉淀在系统治理仓路径中，尤其是 `Prds/` 下的需求文档、版本文档和 `docs/` 下的总览台账

### 4.2 三类角色工作台

这里的“工作台”不是给三类角色分别建三套系统，而是让他们在**同一个 IDE 工作区**里，各自有默认关注的工作区、主要动作和 AI 辅助入口。

**需求角色工作台**
- 主要目标：把需求说清楚、编号定下来、影响范围看明白。
- 默认打开的工作区：`Prds/`、`Templates/`、`docs/`。
- 主要动作：编写主需求、补充增量需求/原型说明、确认功能点编号和回写范围。
- AI 支撑方式：更适合用在需求完整性检查、增量影响分析、原型与测试点映射检查上。

**开发角色工作台**
- 主要目标：把需求稳定转换成可实现的任务、代码和映射关系。
- 默认打开的工作区：`Codes/`、`Prds/`、`Codes/mappings/`、`Tests/`。其中 `Codes/` 可映射到 `repos/frontend-repo`、`repos/backend-repo`。
- 主要动作：读取 `01/02`、拆开发任务、完成代码实现、补齐需求到代码映射。
- AI 支撑方式：更适合用在任务拆解、受影响接口/页面定位、联调前一致性自查上。

**测试角色工作台**
- 主要目标：把需求转换成测试覆盖，并把执行结果回填到需求点。
- 默认打开的工作区：`Tests/`、`Prds/`、`Templates/`、`docs/`。其中 `Tests/` 可映射到 `repos/test-repo`。
- 主要动作：编写 `03`、生成测试点、维护 UI/API 自动化脚本、回填执行结果。
- AI 支撑方式：更适合用在测试点生成、自动化骨架生成、失败归因和结果回填上。

这样设计的重点，不是强调每个人要记多少目录和配置，而是让三类角色都围绕同一套资产协作：需求看得见、代码对得上、测试回得去。

### 4.3 Git 仓库设置建议

推荐口径：**一个系统治理仓 + 多个外部执行仓**。

- 所有人默认可读系统治理仓中的 `Prds/`、`Templates/`、`docs/`，确保需求文档和公共规则透明可见
- `Codes/`、`Tests/` 在当前方案中继续保留为逻辑入口，但物理上可分别映射到 `repos/frontend-repo`、`repos/backend-repo`、`repos/test-repo`
- 系统治理仓负责公共信息与映射规则；前端仓、后端仓、测试仓分别按各自分支和 PR 管理实现变更
- 版本关闭前必须检查版本 `01-需求文档.md`、`04` 测试记录、`TRACE` 状态更新

这样既保留了统一理解目录结构的好处，也兼容前后端与测试独立仓管理的现实。

## 五、流程闭环设计

将需求到测试设计为 7 个阶段：

1. 需求基线化
2. 补充设计（按需触发增量 / 数据流转 / 原型说明）
3. 详细设计
4. 开发实现
5. 测试设计与自动化生成
6. 回归执行与结果回填
7. 版本关闭与主文档回写

### 5.1 流程跑通流程图

```text
需求提出
  ↓
需求梳理与基线确认：形成主需求文档、功能点编号、追踪台账
  ↓
按需补充说明：增量需求说明 / 数据流转设计 / 原型说明
  ↓
详细设计与任务拆解：围绕同一功能点编号拆设计单元、开发任务和映射关系
  ↓
开发实现：前后端完成编码并提交 PR，代码实现持续关联同一功能点编号
  ↓
测试设计与自动化准备：围绕同一功能点编号形成测试用例、测试点和 UI/API 自动化脚本
  ↓
执行测试：手工测试 + UI 自动化 + API 自动化
  ↓
是否发现问题？
  ├─ 是 → 提交缺陷并挂接同一功能点编号 / 开发修复 / 测试回归验证 / 继续围绕同一功能点编号更新状态
  └─ 否 → 结果回填：按功能点编号更新测试执行记录与追踪台账状态
  ↓
版本关闭：回写主需求文档、更新变更台账、按需产出正式版本说明
```

说明：整个闭环建议直接在 IDE 中围绕同一 Git 仓执行，让需求文档、代码、测试和执行结果都留在同一套可追踪资产里。

补充说明：这里的“功能点编号”就是贯穿全流程的统一主键。需求用它定义范围，开发用它关联任务和 PR，测试用它组织测试点与脚本，缺陷修复与回归也继续挂在同一个编号下，最终才能稳定回答“这个功能点现在做到哪一步、测到哪一步、修到哪一步”。

### 5.2 一页式汇报表达（PPT 口径）

如果在汇报页中需要更短、更横向的表达，可直接使用：

```text
需求确认
（建立功能点编号）
   → 设计拆解
（编号进入设计与开发任务）
   → 开发实现
（代码 / PR 关联编号）
   → 测试设计
（用例 / 脚本关联编号）
   → 缺陷修复
（缺陷单挂接同一编号）
   → 回归验证
（结果继续回到同一编号）
   → 版本关闭
（回写主需求与变更台账）
```

也可以配一句总述：

> 一个功能点编号，贯穿需求、开发、测试、缺陷修复、回归验证和版本关闭全流程。

### 闭环的关键要求
- 所有产物都挂同一条路径主线
- 所有可验收颗粒都挂功能点编号
- 测试结果必须能回填到功能点层
- 增量需求必须同步回主需求文档

### 硬门禁

| 门禁项 | 检查节点 | 责任角色 | 通过证据 |
| --- | --- | --- | --- |
| 无功能点编号和验收标准，不进入详细设计 | 需求转详细设计前 | 产品 / 架构 | `01-需求文档.md` 已含功能点编号与验收条件 |
| P0/P1 功能点没有对应测试点，不进入测试完成状态 | 测试设计评审与回归前 | 测试负责人 | `03-测试用例文档.md` 中测试点编号与功能点编号对应完整 |
| 版本正式需求未完成更新，不关闭版本 | 版本关闭前 | 产品 / 治理角色 | 版本 `01-需求文档.md` 已更新，并有 `CHANGELOG`/`TRACE` 留痕 |

### 落地前提
- 测试环境、测试账号、权限账号需提前准备
- UI 自动化依赖前端可测性规范，如稳定定位标识
- 接口自动化依赖可复用的测试数据与环境访问能力
- 还需要明确最小治理责任：编号/映射规则谁维护、主文档回写谁签收、试点阶段固定由哪些角色参与

## 六、测试技术选型

### 1. UI 自动化三方案对比

| 方案 | 实施成本 | 维护成本 | 稳定性 | 复杂场景能力 | AI 协同 | 适用边界 |
| --- | --- | --- | --- | --- | --- | --- |
| Playwright + AI | 中低 | 中低 | 高 | 高 | 高 | 企业后台、复杂交互、多浏览器回归 |
| Cypress + AI | 低 | 中 | 中高 | 中 | 中高 | 前端主导、快速上手、交互相对单一 |
| Selenium/WebDriver + AI | 中高 | 高 | 中 | 中高 | 中 | 有历史资产、已有成熟 Selenium 体系 |

UI 自动化推荐顺序：**Playwright > Cypress > Selenium/WebDriver**。

### 2. 接口自动化三方案对比

| 方案 | 实施成本 | 维护成本 | 复杂断言能力 | 同栈复用 | AI 协同 | 适用边界 |
| --- | --- | --- | --- | --- | --- | --- |
| Playwright API + AI | 低 | 中低 | 中 | 高 | 高 | 一期快速打通闭环、强调 UI/API 联动 |
| Pytest + requests/httpx + AI | 中高 | 中 | 高 | 低 | 中高 | 接口规模大、断言复杂、数据编排要求高 |
| Postman/Newman 或 Apifox/OpenAPI + AI | 中 | 中 | 中 | 低 | 中 | 更强调接口契约展示与跨角色协作 |

接口自动化推荐顺序分两阶段：
- **一期试点**：Playwright API > Pytest > Postman/Apifox
- **长期深化**：Pytest > Playwright API > Postman/Apifox

### 3. 综合推荐
第一阶段建议采用：

> **Playwright(UI) + Playwright(API) + AI 辅助助手体系**

原因：
- 投入最小，见效最快
- 最适合先跑通真实需求闭环
- 最容易沉淀统一测试资产和自动化助手能力
- 一期不直接选择 Pytest(API)，核心原因不是能力不足，而是为了避免首期就进入双技术栈治理，提高落地速度并降低协同成本

后续如果接口规模扩大、复杂断言增多、测试数据编排变重，再演进为：

> **Playwright(UI) + Pytest(API) + AI 辅助助手体系**

## 八、预期收益

### 1. 规范收益
需求、开发、测试围绕同一主线协同，减少口径偏差。

### 2. 效率收益
通过 AI 辅助生成测试点、脚本骨架和失败分析，提高产出效率。

### 3. 质量收益
测试覆盖可以回到需求点层查看，增量影响可以被识别和回填。

### 4. 复用收益
试点完成后，模板、skill、agent、自动化目录结构可复制到其他业务域。

## 九、风险与边界

- 不是所有需求都适合直接自动生成测试脚本
- AI 生成质量依赖模板质量、页面语义、接口信息质量
- UI 自动化稳定性依赖前端可测性规范
- 接口自动化稳定性依赖测试环境、账号、数据和权限配合
- 第一阶段不追求历史资产一次性治理完毕

## 十、实施建议

### 阶段一：规范落地
统一目录、编号、模板和 TRACE 元数据结构。

### 阶段二：正式试点
选择一个项目跑通真实需求闭环。

### 阶段三：能力复制
沉淀通用模板、agent、skill 和测试方案，推广到其他业务域。

## 十一、结论

这套方案不是单独引入一个 AI 测试工具，而是建立一套以“需求路径 + 功能点编号”为主线、由 AI 辅助编排的需求—开发—测试一体化协同体系。其价值既在于提升当前交付效率，也在于为后续平台化复用建立统一底座。
