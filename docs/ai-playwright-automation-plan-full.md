# AI + UI 自动化 + 接口自动化测试方案（完整版）

## 1. 文档定位

本文档用于把当前项目中的 **UI 自动化测试方案** 与 **接口自动化测试方案** 收敛为一份可落地、可汇报、可实施的完整版方案。

这份方案重点解决四类问题：

1. UI 自动化和接口自动化如何放到同一条需求治理主线里。
2. 自动化资产如何和 `REQ` 功能点编号、测试点编号、测试执行记录、缺陷修复记录形成闭环。
3. 一期为什么推荐 `Playwright(UI) + Playwright(API) + skill + AI`，二期又如何演进。
4. 需求、开发、测试三类角色如何围绕同一套文档、目录、脚本和结果回填方式协同。

说明：

- 本文档是 **自动化测试专项完整版**，口径与 [需求开发测试一体化-落地蓝图版.md](需求开发测试一体化-落地蓝图版.md) 保持一致。
- 本文档默认 `Codes/`、`Tests/` 是**逻辑协作视图**；物理落地时可映射到外部仓，例如：`repos/frontend-repo`、`repos/backend-repo`、`repos/test-repo`。
- 本文档默认测试关联关系直接通过 `REQ / FT / IT / ATS` 编号主线、`03-测试用例文档.md`、脚本命名、`04-测试执行记录.md`、`TRACE.yaml` 回溯。

## 2. 目标与约束

### 2.1 总体目标

建立一套围绕 **同一个功能点编号** 运转的自动化测试体系，让需求、开发、测试、缺陷修复、回归验证可以稳定闭环。

本期目标：

1. 建立统一的 UI / API 自动化治理口径。
2. 建立统一的目录、编号、脚本命名、执行、报告、回填规则。
3. 建立 AI / skill / agent 参与自动化生成与失败分析的标准链路。
4. 先用一套最小方案跑通闭环，再按规模演进。

### 2.2 约束与前提

1. 当前优先目标是**先跑通闭环**，不是一开始就把平台能力做得很重。
2. UI 自动化必须依赖前端可测性规范，尤其是稳定定位标识。
3. 接口自动化必须依赖稳定环境、可复用账号、可管理测试数据。
4. 自动化结果必须能回填到系统级版本文档与模块级追踪文件，而不是只留在测试报告里。
5. AI 只负责提效，不替代测试判断、需求判断和最终审核。

## 3. 四条核心原则

### 3.1 一个 `REQ` 贯穿到底

同一个 `REQ` 是贯穿需求、开发、测试、缺陷修复、回归验证的统一主键。

它至少要贯穿到：

- `01-需求文档.md`
- `02-详细设计文档.md`
- `03-测试用例文档.md`
- UI 测试点 `FT-*`
- API 测试点 `IT-*`
- 自动化脚本 `ATS-*`
- PR / commit / tag
- 缺陷单
- `04-测试执行记录.md`
- `05-变更记录.md`
- `TRACE.yaml`

### 3.2 自动化执行必须确定性

- UI 自动化的执行主引擎是 Playwright 确定性脚本。
- 接口自动化的执行主引擎是一套确定性 API 脚本。
- 不能把正式回归执行交给 AI 自主操作。
- AI 只参与：需求解析、测试点整理、脚本骨架生成、失败归因、回填建议。

### 3.3 先统一治理，再分化专业能力

一期优先：

> **Playwright(UI) + Playwright(API) + skill + AI**

二期在接口规模、数据复杂度、断言复杂度明显增加后，再演进为：

> **Playwright(UI) + Pytest(API) + skill + AI**

### 3.4 测试关联关系直接走编号主线

测试关联关系直接通过编号与文档回溯。

说明：

- `FT` / `IT` 编号本身就是由 `REQ` 派生而来。
- UI / API 自动化脚本也沿用同一功能点编号主线。
- 因此测试关联关系可以直接通过 `03-测试用例文档.md`、脚本命名、`04-测试执行记录.md`、`TRACE.yaml` 回溯。

## 4. 总体方案架构

自动化专项建议分成四层：

### 4.1 治理层

负责统一规则，不直接负责执行。

治理层资产包括：

- `Prds/` 下需求、设计、测试基线文档
- `TRACE.yaml`
- `prd-to-code.yaml`
- `04-测试执行记录.md`
- `05-变更记录.md`
- 项目级总览文档

### 4.2 设计层

负责把需求点转换成测试设计和自动化资产。

设计层动作包括：

- 从 `01-需求文档.md` 和 `02-详细设计文档.md` 中抽取功能点
- 在 `03-测试用例文档.md` 中形成 `FT` / `IT`
- 识别哪些测试点适合 UI 自动化、哪些适合接口自动化、哪些只能手工验证
- 生成自动化脚本骨架和目录骨架

### 4.3 执行层

负责真正运行 UI / API 自动化。

执行层资产包括：

- `Tests/ui/...`
- `Tests/api/...`
- fixtures / data / pages / clients / schemas / reports
- Playwright 报告、日志、截图、trace

### 4.4 反馈层

负责结果归因、缺陷闭环、回写与版本结论。

反馈层动作包括：

- 失败分类
- 区分真实缺陷、环境问题、脚本问题、数据问题、变更未同步
- 提交缺陷并挂接同一 `REQ`
- 修复后回归验证
- 回填 `04`、按需回写 `05`、更新 `TRACE.yaml`

## 5. UI 自动化与接口自动化的关系定位

### 5.1 UI 自动化负责什么

UI 自动化优先承担：

- 页面主路径回归
- 核心功能验收
- 跨页面关键业务流程验证
- 权限显隐、保存结果、页面交互闭环验证
- 发布前 smoke / 回归验证

### 5.2 接口自动化负责什么

接口自动化优先承担：

- 接口正确性验证
- 权限、状态流、边界条件验证
- 造数、清数、前后置准备
- UI 难以稳定覆盖但接口容易验证的业务规则验证
- UI 自动化前置数据准备和后置校验支持

### 5.3 二者如何协同

推荐关系不是“二选一”，而是分工协同：

- **UI 自动化** 更适合验证用户视角的主路径结果。
- **接口自动化** 更适合验证规则、数据、权限、异常和批量场景。
- **同一个 `REQ`** 可以同时派生：
  - `FT-*`：功能/UI 测试点
  - `IT-*`：接口测试点
  - `ATS-*.spec.ts`：UI 自动化脚本
  - `ATS-*.api.spec.ts`：接口自动化脚本

## 6. 技术选型对比与结论

### 6.1 UI 自动化四种方案对比

#### 6.1.1 Playwright + AI

技术简介：

- Playwright 是微软维护的现代浏览器自动化框架，支持 Chromium、Firefox、WebKit，多浏览器一致性较好。
- 原生支持等待、trace、截图、录像、网络拦截、storageState 等能力，比较适合企业后台和复杂交互场景。
- 与 AI 结合时，适合做页面结构分析、脚本骨架生成、失败定位和回归问题复盘。

优点：

- 稳定性较高，自动等待机制较成熟。
- 多浏览器支持完整，适合回归验证。
- 对弹窗、iframe、上传下载、权限显隐、复杂交互支持较好。
- 报告、trace、调试链路完整，利于 AI 做失败分析。
- 便于与 Playwright API 共栈，适合一期统一 UI/API 自动化。

缺点：

- 相比 Cypress，上手成本略高。
- 如果前端没有稳定定位规范，脚本仍会不稳定。
- 为了保持可维护性，需要控制页面对象和公共封装的复杂度。

适用场景：

- 企业后台系统
- 复杂表单、表格、弹窗、抽屉、审批流
- 需要多浏览器回归的场景
- 希望 UI 与 API 自动化统一技术栈的项目

#### 6.1.2 Cypress + AI

技术简介：

- Cypress 是前端测试领域常见的浏览器端自动化框架，开发体验友好，交互式调试能力较强。
- 更偏前端团队日常开发联调和页面行为验证，适合快速起步。

优点：

- 上手快，前端同学接受度通常较高。
- 本地调试体验较好，适合快速看页面行为。
- 对中等复杂度页面流程验证比较友好。
- 与 AI 配合时，适合快速生成冒烟脚本和页面级校验脚本。

缺点：

- 多浏览器和复杂企业场景的综合能力通常不如 Playwright。
- 在跨页面、复杂权限链路、复杂上传下载等场景下，治理和扩展性相对弱一些。
- 如果目标是同时统一 UI 与 API 自动化主栈，整体协同性不如 Playwright。

适用场景：

- 前端主导的中小型项目
- 需要快速搭建页面级自动化的团队
- 交互复杂度中等、回归链路较短的系统

#### 6.1.3 Selenium / WebDriver + AI

技术简介：

- Selenium / WebDriver 是历史最久、生态最广的一类浏览器自动化方案，语言生态和历史资产较多。
- 更适合已有 Selenium 体系、已有大量旧脚本、已有配套平台的团队继续演进使用。

优点：

- 历史生态成熟，跨语言支持广。
- 如果团队已有大量存量脚本和平台，迁移成本较低。
- 对标准浏览器自动化场景仍然可用。

缺点：

- 工程化体验、调试体验、现代前端复杂交互支持通常不如 Playwright。
- 脚本维护成本通常更高。
- 新项目从零起步时，不是当前阶段最优解。
- 与 AI 配合可以做分析和生成，但整体效率通常不如更现代的框架。

适用场景：

- 已有大量 Selenium 存量资产
- 团队已有成熟 WebDriver 平台和维护经验
- 不希望在短期内迁移既有自动化体系的场景

#### 6.1.4 Browser Use + AI

技术简介：

- Browser Use 可以理解为一类面向 AI Agent 的浏览器操作方案，核心思路不是先把所有步骤写成固定脚本，而是让 AI 结合页面结构、浏览器状态和任务目标动态决定下一步操作。
- 它更适合“探索页面、理解页面、快速试走流程、辅助定位问题”这类偏探索式任务，而不是直接替代确定性回归脚本。
- 从工程落地视角看，它更适合作为 Playwright 这类主执行框架的补充能力，而不是企业正式回归的唯一执行引擎。

优点：

- 面对陌生页面或页面变化较快的场景，探索效率较高。
- 对“先理解页面，再决定怎么测”这类任务比较友好。
- 适合做页面探索、原型验证、探索式冒烟、辅助失败分析。
- 与 AI 协同天然更强，适合把页面结构理解、操作尝试、问题复盘串起来。

缺点：

- 确定性和可重复性通常不如 Playwright 固定脚本。
- 执行结果更依赖模型判断，稳定性受页面波动、提示词、运行环境影响更大。
- 成本、时延和调试复杂度通常高于普通脚本回归。
- 不适合直接承担 CI 主回归、发布门禁、严格审计型验证这类场景。

适用场景：

- 迭代开始前的关键页面探索
- 原型页面或新页面的快速试走
- 自动化脚本编写前的页面结构摸底
- 页面异常时的辅助定位与失败复盘
- 探索式测试、轻量级冒烟验证

定位建议：

- Browser Use 更适合放在“页面探索层、分析层、辅助执行层”。
- Playwright 更适合放在“正式回归执行层、发布门禁层”。
- 如果两者结合，推荐顺序是：**先用 Browser Use/`browser_snapshot` 做页面理解和摸底，再用 Playwright 落正式脚本**。

#### 6.1.5 综合对比表

| 方案 | 技术特点 | 主要优点 | 主要缺点 | 更适合的场景 | 推荐度 |
|---|---|---|---|---|---|
| Playwright + AI | 现代化、多浏览器、调试与追踪能力完整 | 稳定性高、复杂交互支持强、与 API 可同栈 | 上手成本略高于 Cypress | 企业后台、复杂交互、统一 UI/API 治理 | 高 |
| Cypress + AI | 前端友好、调试体验好、上手快 | 快速启动、前端接受度高 | 复杂链路和长期治理能力弱于 Playwright | 前端主导、中小型项目、快速冒烟 | 中 |
| Selenium/WebDriver + AI | 历史生态成熟、跨语言广 | 存量资产可复用 | 维护成本高、现代体验弱 | 有大量旧资产的团队 | 低 |
| Browser Use + AI | 面向 AI Agent 的动态浏览器操作与页面探索 | 探索效率高、适合页面摸底与辅助分析 | 确定性弱于固定脚本，不适合主回归门禁 | 页面探索、原型验证、探索式测试、辅助分析 | 补充型 |

UI 自动化推荐顺序：

1. **Playwright + AI**
2. Cypress + AI
3. Selenium/WebDriver + AI
4. Browser Use + AI（更适合作为补充能力，不建议替代正式回归主方案）

### 6.2 接口自动化三种方案对比

| 方案 | 实施成本 | 维护成本 | 复杂断言能力 | 数据编排能力 | 同栈复用 | 推荐阶段 |
|---|---|---|---|---|---|---|
| Playwright API + AI | 低 | 中低 | 中 | 中 | 高 | 一期 |
| Pytest + requests/httpx + AI | 中高 | 中 | 高 | 高 | 低 | 二期 |
| Postman / Newman / Apifox / OpenAPI + AI | 中 | 中 | 中 | 中低 | 低 | 补充工具 |

接口自动化推荐顺序：

- **一期试点**：Playwright API > Pytest > Postman/Apifox
- **长期深化**：Pytest > Playwright API > Postman/Apifox

### 6.3 综合推荐结论

第一阶段建议采用：

> **Playwright(UI) + Playwright(API) + skill + AI**

原因：

1. UI 与 API 同栈，便于统一执行入口、目录结构、报告方式。
2. 团队可以先用一套 TypeScript / Playwright 能力把闭环跑通。
3. 更容易统一 `REQ -> FT/IT -> ATS -> 结果` 的治理链路。
4. skill / AI 在解析需求、生成骨架、失败分析时上下文更一致。
5. 能更快在试点阶段形成可复制方法。

当接口自动化进入大规模、强参数化、强数据编排阶段后，再演进 API 侧到 Python 生态。

## 8. 编号与追踪规则

### 8.1 编号规则

| 资产 | 编号规则 | 说明 |
|---|---|---|
| 需求功能点 | `REQ-{L1}-{L2}-{L3}-{NNN}` | 需求主键 |
| UI/功能测试点 | `FT-{L1}-{L2}-{L3}-{NNN}` | 来源于 `03-测试用例文档.md` |
| 接口测试点 | `IT-{L1}-{L2}-{L3}-{NNN}` | 来源于 `03-测试用例文档.md` |
| UI 自动化脚本 | `ATS-{L1}-{L2}-{L3}-{NNN}.spec.ts` | UI 自动化脚本 |
| API 自动化脚本 | `ATS-{L1}-{L2}-{L3}-{NNN}.api.spec.ts` | 接口自动化脚本 |

示例：

- `REQ-CONFIG-REPORTCFG-TYPECFG-001`
- `FT-CONFIG-REPORTCFG-TYPECFG-001`
- `IT-CONFIG-REPORTCFG-TYPECFG-001`
- `ATS-CONFIG-REPORTCFG-TYPECFG-001.spec.ts`
- `ATS-CONFIG-REPORTCFG-TYPECFG-001.api.spec.ts`

### 8.2 追踪规则

自动化链路建议按下面方式理解：

```text
REQ
 ├─ FT → UI 自动化脚本 → UI 执行结果
 ├─ IT → API 自动化脚本 → API 执行结果
 ├─ PR / commit / tag
 ├─ 缺陷单
 └─ 04 / 05 / TRACE 回填状态
```

### 8.3 测试关联关系说明

测试关联关系建议按下面方式维护：

- 在 `03-测试用例文档.md` 里按 `REQ` 维护 `FT` / `IT`
- 在脚本命名中保留同一功能点编号
- 在 `04-测试执行记录.md` 中记录 `REQ / FT/IT / ATS / result`
- 在 `TRACE.yaml` 中记录当前阶段状态与回写记录

### 8.4 测试脚本编写时机建议

测试脚本不建议等到“开发结束、正式转测前”才开始写，更合理的方式是分阶段推进。

建议节奏：

1. 需求 / 详设阶段：先完成 `03-测试用例文档.md`，形成 `FT-*` / `IT-*`，明确哪些场景做手工、哪些场景做 UI 自动化、哪些场景做接口自动化。
2. 开发联调阶段：优先落接口自动化脚本、UI 自动化骨架、测试数据准备、鉴权与公共 fixture。
3. 转测前：再集中补齐 UI 主场景脚本、稳定等待、关键断言、回归集和执行口径。

补充说明：

- 接口自动化通常可以更前置，只要接口定义、入参出参、鉴权方式基本稳定，就可以先写、先跑、先发现问题。
- UI 自动化更适合“半前置半后置”：可以先根据 `REQ` / `FT` 搭骨架，但完整脚本建议在页面结构、关键交互和稳定定位点基本确定后再补齐，避免页面频繁变动带来大量返工。

## 9. UI 自动化详细方案

### 9.1 UI 自动化适用范围

优先纳入：

1. P0 / P1 主业务路径
2. 页面结构稳定、定位稳定的场景
3. 断言口径清晰的场景
4. 数据可回收、可重复执行的场景
5. 发布前需要高频回归的场景

首批建议覆盖：

- 列表查询
- 新增保存
- 编辑保存
- 详情查看
- 权限显隐
- 成功提示 / 空状态 / 错误提示

不建议优先纳入：

- 强依赖第三方系统的末端链路
- 高频改版页面
- 拖拽、画布、富文本等高不稳定交互
- 验证码、短信、邮件等强外部依赖流程
- 高度依赖人工视觉判断的验收场景

### 9.2 UI 自动化目录建议

```text
Tests/ui/
└─ CONFIG-配置中心/
   └─ REPORTCFG-报告配置/
      └─ TYPECFG-报告类别配置/
         ├─ specs/
         │  ├─ ATS-CONFIG-REPORTCFG-TYPECFG-001.spec.ts
         │  └─ ATS-CONFIG-REPORTCFG-TYPECFG-002.spec.ts
         ├─ fixtures/
         │  └─ typecfg.fixture.ts
         ├─ data/
         │  └─ typecfg.data.ts
         ├─ pages/
         │  └─ typecfg.page.ts
         ├─ snapshots/
         └─ README.md
```

### 9.3 UI 脚本分层建议

| 层 | 作用 | 说明 |
|---|---|---|
| `specs/` | 场景脚本 | 面向需求点或测试点 |
| `fixtures/` | 登录态、前后置动作、数据装配 | 避免脚本重复登录或重复准备数据 |
| `data/` | 输入参数、断言数据 | 保证数据集中管理 |
| `pages/` | 页面对象或页面片段封装 | 控制页面层复用边界 |
| `snapshots/` | 页面结构快照、调试辅助 | 可选 |

### 9.4 UI 定位规范

定位优先级建议：

1. `getByTestId`
2. `getByRole + name`
3. `locator` + 稳定属性
4. 最后才用脆弱 CSS 路径

前端配合要求：

- 关键按钮、表单项、弹窗、表格操作列增加稳定标识
- 避免依赖易变文案和动态 DOM 层级
- 权限显隐要有明确的可观察行为

### 9.5 页面探索方式建议：前端代码 vs `browser_snapshot`

在开始一轮 UI 自动化之前，不建议只依赖单一信息源。

两种方式各自适合解决的问题不同：

| 方式 | 更适合看什么 | 优点 | 局限 |
|---|---|---|---|
| 直接看前端代码 | 路由、页面结构意图、组件来源、接口依赖、稳定定位点设计 | 能理解页面为什么这样渲染，便于提前判断哪些元素适合做稳定定位，也更容易识别可复用页面对象和公共逻辑 | 看到的是实现意图，不一定等于运行后的真实结构；对权限显隐、异步渲染、组件库包裹后的最终 DOM 感知不够直接 |
| `browser_snapshot` | 页面运行后的真实结构、可访问性树、最终可交互元素、弹窗层级、权限显隐结果 | 能看到浏览器里实际呈现出来的结果，适合验证定位是否真实可用，也更容易发现运行态问题 | 不容易解释元素为什么出现或消失，也不容易直接看出组件复用关系、数据来源和代码侧约束 |

结论：

- 如果只追求“理解页面设计与实现意图”，前端代码通常更准确。
- 如果只追求“确认自动化运行时到底能看到什么、点到什么”，`browser_snapshot` 更接近执行真相。
- 因此更合理的做法不是二选一，而是**先看前端代码定范围和定位策略，再用 `browser_snapshot` 校验运行态结构**。

推荐顺序：

1. 先看前端代码：确认路由、页面入口、关键组件、接口依赖、可补的 `data-testid`。
2. 再看 `browser_snapshot`：确认实际可见元素、名称、层级、显隐状态、弹窗和动态区域。
3. 最后再写脚本：基于代码理解和运行态真相一起确定定位方式、断言点和等待策略。

### 9.6 UI 编写与执行流程

1. 读取 `01-需求文档.md`、`03-测试用例文档.md`
2. 锁定目标 `REQ` / `FT`
3. 页面观察与定位点确认
4. 生成 Playwright 脚本骨架
5. 人工补齐等待、断言、前后置处理
6. 本地执行并修正
7. 输出报告与失败归因
8. 回填 `04` 与 `TRACE.yaml`

## 10. 接口自动化详细方案

### 10.1 一期方案：Playwright API

一期优先使用 Playwright API，目标不是做到接口自动化的最终形态，而是先让接口自动化与 UI 自动化使用同一套治理方式。

适用场景：

- 中小规模接口回归
- 登录态串联
- UI 前后置造数与校验
- 与页面功能强绑定的接口验证

### 10.2 二期演进：Pytest + requests/httpx

当出现以下信号时，建议把 API 自动化演进到 Python 生态：

- 接口数量显著增加
- 复杂参数化、复杂 fixture 需求变强
- 数据编排与造数逻辑明显变重
- 契约校验、Mock、批量回归能力要求变高

### 10.3 接口自动化目录建议

```text
Tests/api/
└─ CONFIG-配置中心/
   └─ REPORTCFG-报告配置/
      └─ TYPECFG-报告类别配置/
         ├─ specs/
         │  ├─ ATS-CONFIG-REPORTCFG-TYPECFG-001.api.spec.ts
         │  └─ ATS-CONFIG-REPORTCFG-TYPECFG-002.api.spec.ts
         ├─ clients/
         │  └─ typecfg.client.ts
         ├─ fixtures/
         │  └─ auth.fixture.ts
         ├─ data/
         │  └─ typecfg.data.ts
         ├─ schemas/
         │  └─ typecfg.schema.ts
         └─ README.md
```

### 10.4 接口自动化分层建议

| 层 | 作用 | 说明 |
|---|---|---|
| `specs/` | 接口场景脚本 | 面向 `IT` 编号 |
| `clients/` | 接口访问封装 | 统一请求入口 |
| `fixtures/` | 鉴权、前置数据、清理逻辑 | 统一复用 |
| `data/` | 请求参数与断言数据 | 统一管理测试数据 |
| `schemas/` | 结构校验 | 做响应字段与类型校验 |

### 10.5 环境、鉴权、数据、断言规范

#### 环境分层

至少区分：

- `local`
- `test`
- `staging`

建议抽离配置：

- `baseURL`
- 登录地址
- 用户名密码来源
- 代理 / 证书配置
- 数据清理开关

#### 鉴权分层

建议统一三层：

1. 账号层：角色账号、权限账号清单
2. 登录层：token 获取与刷新
3. 调用层：业务接口自动附带鉴权头

#### 数据分层

| 数据类型 | 说明 | 建议 |
|---|---|---|
| 固定基线数据 | 长期复用 | 统一维护 |
| 临时造数 | 执行前动态创建 | 由 fixture 创建和清理 |
| 受限共享数据 | 并发风险高 | 明确隔离规则 |

#### 断言分层

接口断言至少包含四层：

1. 状态码断言
2. 业务码断言
3. 结构断言
4. 业务断言

不建议只断言 `status = 200` 或 `code = 0`。

### 10.6 接口编写与执行流程

1. 读取 `01-需求文档.md`、`02-详细设计文档.md`、`03-测试用例文档.md`
2. 锁定目标 `REQ` / `IT`
3. 确认依赖接口、权限、环境、前置数据
4. 生成 API 脚本骨架
5. 人工补齐断言、造数、清理逻辑
6. 本地执行
7. 产出报告
8. 回填 `04` 与 `TRACE.yaml`

## 11. AI / skill / agent 协同方案

### 11.1 总体定位

AI、skill、agent 的职责边界建议如下：

| 能力 | 主要职责 |
|---|---|
| skill | 固定流程触发、目录脚手架、命名校验、文档回填骨架 |
| agent | 读取需求/详设/原型/用例并整理场景、接口、断言点 |
| AI | 生成脚本初稿、补齐 schema、分析失败、给出修复建议 |
| 人 | 审核需求口径、确认场景边界、审核脚本与执行结果 |

### 11.2 推荐的六个能力模块

#### 模块 1：需求与测试点解析

输入：

- `01-需求文档.md`
- `02-详细设计文档.md`
- `03-测试用例文档.md`

输出：

- 目标 `REQ`
- 对应 `FT` / `IT`
- UI 自动化候选场景
- API 自动化候选场景

#### 模块 2：页面探索与 UI 场景整理

输入：

- 页面 URL 或页面结构
- 原型说明文档 `01c-原型文档.md`（如有）

输出：

- 页面关键区域清单
- 操作路径
- 稳定定位建议
- 断言点建议
- 易翻车点提示

#### 模块 3：接口分析与 API 场景整理

输入：

- 详细设计文档
- 接口定义
- 现有前后端代码或接口说明

输出：

- 接口清单
- 请求参数
- 响应结构
- 前置数据需求
- 断言点建议

#### 模块 4：自动化骨架生成

输出类型：

- UI Playwright `spec`
- API Playwright `api.spec`
- fixture / data / page / client / schema 骨架

要求：

- 文件名必须带原始需求编号
- 不得脱离 `REQ` 自造本地编号
- 默认只生成最小可运行骨架，不生成过重抽象

#### 模块 5：失败归因与分析

输入：

- 报错信息
- 截图 / trace / 日志
- 当前脚本
- 需求与测试点上下文

输出：

- 失败分类
- 初步根因
- 修复建议
- 是否需要提交缺陷
- 是否需要同步 `03` / `04` / `05` / `TRACE`

#### 模块 6：结果回填建议

输出：

- `04-测试执行记录.md` 逐项明细建议
- `05-变更记录.md` 需要补充的变更项建议
- `TRACE.yaml` 状态更新建议

### 11.3 一条推荐链路

```text
需求 / 详设 / 测试用例
    ↓
skill：识别目标 REQ 与 FT/IT
    ↓
agent：整理页面/接口/断言点
    ↓
AI：生成 UI/API 脚本骨架
    ↓
人工补齐与审核
    ↓
Playwright 执行
    ↓
AI 辅助失败分析
    ↓
回填 04 / 05 / TRACE
```

### 11.4 AI 可做与不可做的事

AI 可以做：

- 解析需求与测试点
- 生成脚本骨架
- 生成 schema 与断言初稿
- 分析截图、日志、trace 中的失败原因
- 生成结果回填建议

AI 不应直接做：

- 未经审核直接改主干脚本
- 没有需求依据时自发增加断言
- 自主跳过失败用例
- 绕过规范乱写定位方式或接口断言

## 12. 执行闭环与缺陷修复机制

### 12.1 流程主线

```text
需求确认
  ↓
形成 01-需求文档.md 与 REQ 编号
  ↓
按需补 01a / 01b / 01c
  ↓
完成 02-详细设计文档.md
  ↓
完成 03-测试用例文档.md，形成 FT / IT
  ↓
生成 UI / API 自动化脚本骨架
  ↓
手工测试 + UI 自动化 + API 自动化执行
  ↓
是否发现问题？
  ├─ 是 → 提交缺陷并挂接同一 REQ → 开发修复并关联同一 REQ → 测试回归验证并更新同一 REQ 状态
  └─ 否 → 回填测试结果
  ↓
更新 04-测试执行记录.md / TRACE.yaml
  ↓
按需更新 05-变更记录.md
  ↓
版本关闭
```

### 12.2 失败分类建议

建议统一至少六类：

| 分类 | 说明 |
|---|---|
| `ENV` | 环境不可用、服务异常、网络异常 |
| `AUTH` | token、权限、登录态问题 |
| `DATA` | 测试数据、前置数据不成立 |
| `SCRIPT` | 脚本本身问题 |
| `DEFECT` | 产品 / 前后端真实缺陷 |
| `CHANGE` | 需求、页面、接口变更后脚本未同步 |

### 12.3 缺陷闭环要求

当自动化发现真实问题时：

1. 缺陷单必须挂接 `REQ`
2. 修复 PR / commit 继续挂接同一 `REQ`
3. 回归验证继续围绕同一 `REQ`
4. `04-测试执行记录.md` 中记录修复前后结果变化
5. 若属于版本正式变化，按需更新 `05-变更记录.md`

## 13. 报告与结果回填规范

### 13.1 最低回填要求

每次批量执行后，至少回填：

1. `Prds/Vx.y.z/04-测试执行记录.md`
2. 模块叶子目录 `TRACE.yaml`
3. 若测试点口径变化，则回写 `03-测试用例文档.md`
4. 若版本正式变化需要说明，则更新 `Prds/Vx.y.z/05-变更记录.md`

### 13.2 `04-测试执行记录.md` 需要能回答什么

至少能回答：

- 本轮测了哪些模块、哪些 `REQ`
- 对应哪些 `FT` / `IT`
- 对应哪些脚本
- 结果是 PASS / FAIL / BLOCKED / NOT RUN
- 失败是脚本问题还是产品缺陷
- 是否需要重跑
- 是否影响发布结论

### 13.3 `05-变更记录.md` 什么时候更新

建议在以下情况更新：

- 本版形成正式发布说明
- 页面或接口调整导致脚本、测试点、执行口径变化
- 需要向业务或项目组明确说明本版影响范围

### 13.4 `TRACE.yaml` 需要更新什么

至少更新：

- 当前状态
- 关联代码路径
- 关联测试路径
- 回写记录
- 版本增量记录

## 16. 风险与边界

### 16.1 主要风险

| 风险 | 影响 | 缓解方式 |
|---|---|---|
| 前端缺少稳定定位标识 | UI 自动化不稳定 | 推动 `data-testid` 规范 |
| 环境、账号、权限准备不足 | UI/API 都难稳定执行 | 先准备最小测试环境与专用账号 |
| 测试数据不可重复使用 | 回归不稳定 | 建立造数与清数规则 |
| AI 生成脚本质量不稳定 | 误导脚本实现 | 坚持人工审核 |
| 试点阶段范围过大 | 推进节奏失控 | 首批只选最能跑通闭环的模块 |

### 16.2 不建议的做法

- 一开始就追求全量自动化覆盖
- UI 与 API 各自独立建设、编号脱节
- 只保留测试报告，不回填版本文档与追踪文件
- 把 AI 当成正式执行引擎
- 在一期同时引入过多技术栈

6. Playwright API 最小执行框架
7. 登录态 / 鉴权 fixture
8. 首批 5~10 个 P0/P1 自动化场景
9. `04-测试执行记录.md` 回填规范
10. `TRACE.yaml` 状态更新规范
11. 缺陷单挂接 `REQ` 的闭环要求
12. AI 参与脚本骨架生成与失败分析的最小流程

---

## 18. 结论

这套方案的重点不是单独引入一个测试工具，而是把 **需求、开发、UI 自动化、接口自动化、缺陷修复、回归验证** 放进同一套编号与追踪体系中。

当前阶段最推荐的落地路线是：

> **Playwright(UI) + Playwright(API) + skill + AI**

它最适合当前目标：

- 先统一栈
- 先统一治理
- 先统一执行入口
- 先统一结果回填方式
- 先把一个真实试点模块跑通

在这条主线稳定之后，再把接口自动化逐步演进到更专业的 Python 生态，就能兼顾当前落地速度和后续规模化能力。
